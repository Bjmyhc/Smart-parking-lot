## 2. B 类｜三处歧义的确定性做法

### 2.1 节点「单命令通道」状态机（拍照 + 探活**共用**，含探活态）

方案 §4.6 说"共用同一条状态机"，但那里的 `IDLE → SENT → DONE/TIMEOUT` 没有探活的位置。**照下面这张表实现**：

| 状态              | 在等什么                                                                                                                                                                                                                                                                                                                                                                                                                        | 超时                            | 迁移                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PC_IDLE`       | 无在途命令                                                                                                                                                                                                                                                                                                                                                                                                                      | —                              | ① 有拍照请求`captureReq` → **清 RX 缓冲** + 发 `AT+RUN\r\n` → `PC_RUN_SENT`（记 tick、`captureSeq++`）② 否则到探活点（距上次探活 ≥ `PLATE_PROBE_MS` 且 `PC_IDLE` 已停留 ≥ 2s）→ **清 RX 缓冲** + 发 `AT+INFO\r\n` → `PC_PROBE_SENT` |
| `PC_RUN_SENT`   | `$PLATE` 行 | `PLATE_TIMEOUT_MS`(2000) | 收到 `$PLATE,` → 解析入 `PlateCache`，置 `g_plateFetchPending=1`，清 `captureReq` → `PC_IDLE`收到 `ERR:` → `camPreempted++`，清 `captureReq` → `PC_IDLE`收到 `+INFO:` / `+CFG:` / `OK` → 丢弃，**继续等**超时 → 重试计数 < `PLATE_RETRY_MAX` 则在 `PLATE_RETRY_GAP_MS`(3s) 后重发，否则 `camTimeout++`、清 `captureReq` → `PC_IDLE` |                                 |                                                                                                                                                                                                                                                                         |
| `PC_PROBE_SENT` | 任意一行                                                                                                                                                                                                                                                                                                                                                                                                                        | `PLATE_PROBE_TIMEOUT_MS`(500) | 收到**任何一行** → `g_camOnline=1`、`probeFail=0` → `PC_IDLE`超时 → `probeFail++`；`probeFail ≥ PLATE_PROBE_FAIL_MAX`(3) → `g_camOnline=0` → `PC_IDLE`                                                                                        |

**5 条不变量（违反任何一条都会出古怪故障）**

1. **同一时刻只有一个状态 ≠ `PC_IDLE`** —— 半双工口只允许一条在途命令。
2. **拍照优先、但不许打断**：正在等 `AT+INFO` 回复时来了拍照请求，**等本轮探活超时/收尾后**再发 `AT+RUN`（不做抢占式打断，否则两条回复会互相污染）。
3. **每次发命令前清空 USART3 接收缓冲**（`Usart3_FlushRx()`），丢掉上一条的残字节。
4. **绝不阻塞**：`Plate_Task()` 每轮只做"取缓冲 → 喂状态机 → 查超时"，一毫秒都不许死等 —— 否则网关 PING 的 500 ms 超时会被踩死（方案 §6 要点 1，这是硬要求）。
5. **超时值按状态取**（2000 / 500），用同一个超时检查函数，别无脑写死 2000。

```c
/* Plate_Task(): 主循环每轮调用一次, 全程非阻塞 */
void Plate_Task(void)
{
    uint8_t buf[64];
    uint16_t n;

    /* ④ 取数据(非阻塞), 逐行喂给行缓冲 */
    while ((n = Usart3_GetData(buf, sizeof(buf))) > 0)
        Plate_FeedBytes(buf, n);        /* 按 '\n' 切行 -> Plate_OnLine() */

    /* ⑤ 查超时 */
    switch (s_state) {
    case PC_RUN_SENT:
        if (Elapsed(s_sentAt) > PLATE_TIMEOUT_MS) Plate_OnRunTimeout();
        break;
    case PC_PROBE_SENT:
        if (Elapsed(s_sentAt) > PLATE_PROBE_TIMEOUT_MS) Plate_OnProbeTimeout();
        break;
    case PC_IDLE:
        Plate_TryNextCommand();          /* 见状态表: 拍照优先, 其次探活 */
        break;
    default: break;
    }
}
```

### 2.2 `$PLATE` 归属判定（保证拿到的是"本次触发"那一行）

**机制**：节点本地代际计数 `s_captureSeq` + 发送前清缓冲，**完全不依赖摄像头帧号**。

1. 发送 `AT+RUN` 前：`Usart3_FlushRx()`，并 `s_captureSeq++`，记 `s_sentSeq = s_captureSeq`。
2. 只接受**本次窗口内的第一行**以 `$PLATE,` 开头的行作为结果；之后的 `$PLATE,` 行一律丢弃并 `strayPlate++`（说明摄像头被设成了 `AT+TRIG=0` 在自己发）。
3. 切行规则：按 `\n` 切；单行超过 **127 字节**直接丢弃整行（摄像头单行上限 95 字节，超长必是噪声）。
4. `$PLATE,-,0,42` → `valid=0`，`plate="-"`
5. `ERR:` 开头 → `camPreempted++`，**不算"未识别"**，不许当 `-` 上报（否则"被抢占"会被伪装成"没认出来"）
6. 超时 → `camTimeout++`，按重试规则重试
7. **帧号只进日志**（`LoraPlate_t.frameNo`），不参与判新 —— 摄像头重启后帧号归零

**解析宽容度（照做）**：同时容忍 `-`、空字段、以及尾巴上的 `,img=<档位>`；**只读前 3 段**（车牌 / 置信度 / 帧号）。

### 2.3 网关「有牌待取」→ 发 `AT+PLATE` 的落点

1. **置位**：`updateNodeFromRaw()`（`node_data.cpp`）里解 `CamFlags`：

```c
nodes[slot].capturePolicy  = (uint8_t)(raw->CamFlags & 0x03);
nodes[slot].cameraOnline   = (uint8_t)((raw->CamFlags >> 3) & 0x01);
if (raw->CamFlags & 0x04) nodes[slot].plateFetchPending = true;   /* bit2 有牌待取 */
```

2. **消费**：照抄 `thresholdNeedsUpdate` 现成那两处（`lora_handler.cpp:325` / `:348`），在 `lora_tick()` 的"处理待发控制命令"之前加一段：`plateFetchPending && certSent` → 把 `AT+PLATE\r\n` 入队 → `plateFetchPending = false`（**等 `0xF1` 帧回来才算真取到；超时下一轮重新置位**）。
3. ⚠️ **纠正方案 §7 的两处**（方案写错了，照手册来）：
   - **没有 `pendingCmd` 单槽这回事**。真实机制是环形队列 `cmdQueue[CMD_QUEUE_SIZE=8]` + `cmdQueueHead/Cnt`（`lora_handler.cpp:239~247`）。所以"三类命令抢一个槽"是伪问题，改成**入队顺序**问题：手动触发把 `AT+CAPTURE` 直接入队即可（FIFO，先入先发）。
   - **`lora_sendControl()` 发不出无参命令**：它固定拼 `"AT+%s=%d\r\n"`（`lora_handler.cpp:1419`）。`AT+PLATE` / `AT+CAPTURE` 都没有参数 → 用现成的 `sendAT(nodeId, prefix, 0, /*hasValue=*/false)`（`lora_handler.cpp:525`，已支持无参），把它暴露成公开函数（或给 `lora_sendControl` 加无参重载）。
4. ✅ **不用给 `AT+PLATE` 回 ACK**：网关收到**任何完整帧**（含 `0xF1`）就会清 `waitingResp` / `waitingCmdReply` 并恢复 `pollPhase`（`lora_handler.cpp:1033` → `:1036` → `:1046`）。前提是新的 `case LORA_FRAME_PLATE` 里**置了 `gotData = true`**（照 `case LORA_FRAME_ACK` 写）。车牌帧本身就是应答。
5. ⚠️ **`ackKeyMatches()` 要补两条**：它末尾是"未知内容保底放行"（`lora_handler.cpp:520`）。不改的话对这两条命令等于**关键字归属校验失效**——典型后果是：`AT+CAPTURE` 的回执迟到（网关已超时前移），却仍被保底放行、误当成本轮命令的回执（这就是 S33 拦的那类坑）。补成：

```c
if (strstr(ack, "CAPTURE") != NULL) return strcmp(lastCmdKey, "CAPTURE") == 0;
if (strstr(ack, "PLATE")   != NULL) return strcmp(lastCmdKey, "PLATE")   == 0;
```

> `CAPTURE` 与 `CapturePolicy` 靠**大小写**区分（`strstr` 区分大小写），这是方案 §5.2 立的硬约束：**新增命令名不得包含既有命令名作子串，且不许把 `AT+CAPTURE` 改成全大写以外的写法**。

## 6. 源码编码约定（节点 · 必读，2026-10-09 定）

**唯一目标态：`UTF-8 带 BOM`。** 节点所有 `.c/.h` 都必须停在这个状态。

### 6.1 为什么（实测结论，不是推测）

- Keil 的 **armcc V5 只在文件带 UTF-8 BOM 时**才按 UTF-8 读源码；**没有 BOM 就按系统 ANSI 读**（中文 Windows = GBK/936）。
- 于是"UTF-8 无 BOM + 中文"会被误解析。一个汉字在 UTF-8 占 3 字节，而 GBK 是 2 字节一配 —— **汉字个数为奇数**时最后会剩"半个字"，它去找结尾的引号配对，把 `"` 吃掉：

  ```
  app_tasks.c(214): error:  #8: missing closing quote
        case PARK_ZOMBIE:   return "鍍靛案杞?";
  ```

  个数为偶数时**不报错**，但字符串内容已经乱码（串口打印是乱的）——这是更隐蔽的坑。
- 对照实验（本机 armcc V5.06，逐条实测）：

  | 文件编码                          | 结果                            |
  | --------------------------------- | ------------------------------- |
  | UTF-8**无** BOM             | ❌`#8: missing closing quote` |
  | UTF-8**有** BOM             | ✅                              |
  | GBK                               | ✅                              |
  | 纯 ASCII（中文写成`\xNN` 转义） | ✅                              |

  （"GBK 也能编过"是真的，但**源码编码会一比一变成串口输出字节**：GBK 源码 → 节点日志是 GBK 字节，和摄像头 ESP32(UTF-8) 不一致，串口助手看两个设备要来回切编码。因此统一到 UTF-8+BOM，顺带把输出编码也统一了。）
- `armcc --help` 里**没有任何 charset / encoding / multibyte / locale 选项** —— 想让编译器直接读无 BOM 的 UTF-8，没有这种开关。

### 6.2 谁在保证它

`Tool/fix_src_encoding.py` + **Keil 的 Before Make 钩子**（`App.uvprojx` / `Boot.uvprojx` 都已接上）。每次编译前自动跑一趟：

| 文件当前状态                       | 处理                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------- |
| 已是 UTF-8+BOM / 纯 ASCII          | **不动**（不改 mtime → 不会触发无谓重编）                        |
| UTF-8 无 BOM 且有非 ASCII          | 只补**3 字节 BOM**，内容一字不动                                  |
| 判为 GBK（比如被 Keil 编辑器存过） | 整体转成 UTF-8+BOM                                                      |
| 判不准                             | **非零退出** + 打印原因（但见下面 §6.4 的坑：Keil 不会因此停下） |

**效果**：你用 Keil 存盘、用 VS Code 存盘、AI 直接写文件 —— 谁来都不会再炸。

### 6.4 接钩子的坑（**已踩过，别再踩**）

Keil 工程文件里 `BeforeMake` 的 `<nStopB1X>` **必须填 `0`**。

- 填 `1` → 构建会在跑完钩子后**瞬间中止**：输出里只有钩子的日志，然后直接
  `"..\Output\firmware.axf" - 1 Error(s), 0 Warning(s). Target not created.`
  `Build Time Elapsed: 00:00:00`，**一个文件都不编译**，看起来像钩子把构建搞坏了。
  实测（2026-10-09）：钩子脚本自身退出码是 0、输出也正常，但这个开关一开就会这样。
- 填 `0` → 钩子照跑（日志里能看到 `Before Build - User command #1`），编译/链接全部正常。

代价：`nStopB1X=0` 时 uVision **不会**因为脚本非零退出而中止构建，所以脚本报错时，
你会在 Build Output 里看到它的中文警告，但构建会继续（可能接着报 `#8`）——**看日志，
别只看最后一行**。

### 6.3 使用与注意

- 手工跑：`python Tool\fix_src_encoding.py`（执行）/ `python Tool\fix_src_encoding.py --check`（只报告）
- **新建 Keil 工程**：`python Tool\fix_src_encoding.py --wire <工程.uvprojx>` —— 一条命令把钩子接上（幂等；顺带会把害人的 `nStopB1X` 修正为 0）
- **交工程给别人 / 上公共仓库**：`python Tool\fix_src_encoding.py --unwire <工程.uvprojx>` —— 摘掉钩子（同样幂等；只摘属于本脚本的那条命令，别人占用的槽一字不动）。摘了之后按 `--wire` 可以再装回来

> 挂进 Keil 的 `Tools → Customize Tools Menu`（用 `#P` = 当前工程文件完整路径当参数，全局可用）时的取舍：
>
> - **`--wire` 值得挂**：点一下 → **立刻编译一次**验证（看到 `Before Build - User command #1` 才算成功）。
> - **`--unwire` 不建议挂**：菜单项只能在"Keil 开着工程"时点，而那时脚本改的 `.uvprojx` 会被 uVision 的内存副本覆盖（§6.6 有实测记录）。摘钩子请用 §6.6 那两条可靠做法——IDE 里 `Options for Target → User` 手动去勾，或先完全关掉 Keil 再跑命令行。

- 扫描范围**自动跟随 Keil 工程**：`Node/` + `shared/` + 仓库里每个 `.uvprojx` 的工程根。所以新建工程不用改脚本；`Gateway/`、`PlateRecognitionIDF/` 是 GCC 工具链，默认按 UTF-8 读，故意不扫
- `Tool/gbk_cn.ps1`（"转义 → GBK 中文"）是**历史遗留**，方向与本约定相反，**不再用于节点源码**
- 唯一的手感差异：在 Keil 编辑器里存过文件后，下次编译会把它转回 UTF-8+BOM；在 Keil 里重新打开该文件即可正常显示

### 6.5 能"全局"到什么程度（2026-10-09 实测）

分两层看，一层是全局的，一层是工程级的：

| 层                          | 全局吗    | 说明                                                                                                              |
| --------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------- |
| **脚本的扫描范围**    | ✅ 全局   | 自动发现仓库里**每个** `.uvprojx` 的工程根，不由工程清单决定；新工程放进仓库就被覆盖                      |
| **编辑器侧**          | ✅ 仓库级 | `.editorconfig` 里 `[*.{c,h}] charset = utf-8-bom` —— VS Code / Trae 保存时直接写 BOM，从源头上不产生危险态 |
| **Keil 的编译前钩子** | ❌ 工程级 | uVision 的`User → Before Build` 命令**存在工程文件里**，没有全局开关；新建工程必须 `--wire` 一次       |

所以三道防线是叠加的：编辑器尽量不写错 → 万一写错，编译前脚本兜住 → 万一编译前也没兜住（比如绕过 Keil 直接从命令行编），`--check` 能查出来。

> 真·全局（不依赖任何工程配置）只有一种做法：文件系统常驻监听/或 git 提交钩子。**没做**——多一个常驻进程和"背后改文件"的行为，收益不抵复杂度。真要的话告我。

### 6.6 ⚠️ 用脚本改 `.uvprojx` 不可靠（2026-10-09 实测踩过）

**结论：`.uvprojx` 归 uVision 所有。** 你在外面（脚本 / 编辑器）改它，只要 Keil 还开着那个工程，它随时会用自己的内存副本覆盖回去。

实测记录（`Node/Firmware/Project/App.uvprojx`）：

| 时刻     | 现象                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 12:46:12 | 点"摘除编码钩子" → 磁盘上**确实摘掉了**（当场查过）                     |
| 12:47:22 | 不重启 Keil，直接按 F7 → 文件被**复原**成带钩子的版本，钩子照跑         |
| 12:49:46 | 又来一次；期间弹出`Project File '…' has been modified externally, Reload ?` |

> 那个弹窗里路径**偶发显示成乱码**——是 uVision 自己的渲染问题，磁盘上的路径是纯 ASCII 且文件完好（查过：非 ASCII 字符数 = 0，与仓库版本逐字节一致）。别被它吓到。

**所以按目的选做法：**

| 目的                                      | ✅ 可靠                                                                                                 | ❌ 不可靠                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **接线**（新工程装钩子）            | 点工具菜单 →**立刻编译一次**，看到 Build Output 出现 `Before Build - User command #1` 才算成功 | 点完不管                     |
| **摘钩子（临时）**                  | Keil 里`Project → Options for Target → User`，去掉 `Before Build/Rebuild` 的 `Run #1` 勾 → OK  | 用脚本改工程文件（会被覆盖） |
| **摘钩子（交给别人 / 上公共仓库）** | **先完全关掉 Keil**，再跑 `--unwire <工程>`                                                     | Keil 开着就改                |

弹窗 `has been modified externally, Reload ?` 的选法：**选「是」**（采用磁盘版本，让 IDE 与磁盘一致，之后不再反复问）。

| `noplate` | 回`$PLATE,-,0,<n>`                                                          | "拍到了没认出来"                                   |
| `timeout` | 不回（静默）                                                                  | 2s 超时 + 重试 2 次                                |
| `garbage` | 回畸形行 + 半行 + 超长行                                                      | 解析健壮性（不崩、不吞后续）                       |
| `err`     | 回`ERR:没有权限: 现在是调试模式, 控制权在电脑手里`                          | 被抢占识别                                         |
| `trig0`   | 每 2s**主动**发一行 `$PLATE,...`，收 `AT+RUN` 时的行为同 `normal` | 非预期行被丢弃                                     |
| `flaky`   | 70% 成功率（其余静默）                                                        | 重试与冷却                                         |

**要求**：只用标准库 + `pyserial`；`Ctrl+C` 干净退出；每行收发都带时间戳打印，方便和节点日志对齐。

## 附录 B｜OneNET 物模型字段级规格（照填）

子产品 `04kjwU9TC7` → 子设备 `Park001` / `Park002`

| 属性       | 标识符              | 数据类型 | 取值范围         | 读写 | 说明                                                                |
| ---------- | ------------------- | -------- | ---------------- | ---- | ------------------------------------------------------------------- |
| 车牌号码   | `PlateNumber`     | string   | 长度**16** | 只读 | 三态：合法车牌 /`-`（没认出来）/ 从未上报                         |
| 识别置信度 | `PlateConfidence` | int32    | 0 ~ 100          | 只读 | 步长 1；`PlateNumber` 为 `-` 时上报 0                           |
| 拍照策略   | `CapturePolicy`   | int32    | 0 ~ 3            | 只读 | 0 不拍 / 1 有车拍 / 2 僵尸车拍 / 3 都拍；以**节点**回报值为准 |
| 摄像头在线 | `CameraOnline`    | bool     | true / false     | 只读 | 探活能回 = true                                                     |
| 车牌颜色   | `PlateColor`      | int32    | 0 ~ 5            | 只读 | **已建、一期不上报**（预留；将来启用不必改协议）              |

| 服务             | 标识符               | 入参                         | 出参                                                                                                                                           |
| ---------------- | -------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 手动触发拍照识别 | `TriggerCapture`   | 无                           | `Result` (int32 0/1) = **本次是否识别出车牌**；`ActualValue` (int32 0/1) = **动作是否真的执行**（0=节点忙/未触发/9s 死线超时） |
| 设置拍照策略     | `SetCapturePolicy` | `PolicyValue` (int32, 0~3) | `Result` (int32 0/1)、`ActualValue` (int32, 0~3)                                                                                           |

> 平台对超出范围的值会**拒收**（历史坑 `code=2213`）→ 节点/网关侧必须先夹取（§1.2.4）。
> 车牌属性**不得早于首帧业务数据帧上报**（`hasDataFrame` 门控）。
> `PlateNumber`/`PlateConfidence` **只在收到新的 `0xF1` 车牌帧后上报一次**（网关 `plateNeedPost` 门控）；无新识别结果时整帧不带这两项，平台保留旧值且 `time` 不前进 —— 这样 `PlateNumber.time` 才等于"车牌最后更新时间"，App 才能据此判新旧。
> ⚠️ **回执类型按平台既有约定用 `int32`（0/1），不是 `bool`** —— 本产品现有的 `SetLed` / `SetSensorDistance` / `SetZombieThreshold` 回执全是 int32 0~1，App 侧也是按数字解析的；新增两个服务跟它们保持一致，别照旧摄像头产品（`4enONCu0Y7`）那份用 bool。
> **可直接导入的成品**：`Doc/Park_物模型.json`（本产品全量物模型：13 属性 + 5 服务，含上述新增）。
