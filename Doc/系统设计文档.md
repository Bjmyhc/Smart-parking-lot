## 二、核心交互逻辑：老师点名

> 用课堂场景类比整个系统的通信原理，帮助理解网关轮询、代上线、超时等核心概念。
> 如果你是第一次看这个项目，建议先读这一节。

### 2.1 角色对应

| 系统角色 | 课堂比喻 |
|----------|----------|
| **网关 (ESP8266)** | **老师** |
| **节点 (STM32 车位检测器)** | **学生** |
| **LoRa 无线** | **教室里的传话** |
| **OneNET 云平台** | **学校教务处** |

### 2.2 为什么是"老师点名"，而不是"学生抢答"？

因为 LoRa 无线通信有个致命问题——**同时说话就撞车**。如果两个节点同时发数据，LoRa 信号在空中碰撞，两个都收不到，就像教室里两个学生同时大喊，老师谁也听不清。

所以方案是**网关轮询**：老师一个个点名——先喊"节点1，报数据"，节点1回答；再喊"节点2，报数据"，节点2回答。同一时刻只有一个人说话，永远不会撞车。

### 2.3 完整交互流程

#### 第一步：老师认识学生（查询证书）

老师刚进教室，谁都不认识，得先认人：

```
老师喊: "节点1，报上你的学号姓名！"      (AT+CER)
节点1回: "我是 Park001，学号 04kjwU9TC7"  (0xA1 + 证书)
老师记下: 哦，节点1叫 Park001，属于 04kjwU9TC7 班
```

老师记下来后，去教务处（OneNET）登记：

```
老师 → 教务处: "报告，Park001 来了，让他上线吧"   (thing/sub/login)
教务处 → 老师: "好的，Park001 已上线"              (code:200)
```

> 注：证书拿到后会写入 Flash（`/certs.dat`），**重启后免 LoRa 重新上报**，直接恢复轮询。

#### 第二步：老师查作业（查询数据）

认完人后，老师开始定时查作业：

```
老师喊: "节点1，汇报你的数据！"           (AT+DATA)
节点1回: "我这边车位有车，超声波3cm，地磁感应到1"  (0xB1 + 10字节二进制数据)
老师记下: 节点1有车，然后把数据报给教务处
```

关键细节：10 字节的数据是**直接二进制拷贝**（memcpy），不是转成字符串。速度快、省空间。

#### 第三步：老师报给教务处（代子设备上报）

老师拿到节点1的数据后，用 MQTT 发给 OneNET：

```
老师 → 教务处: "Park001 的数据是: 车位状态=有车，超声波=3cm，..." (thing/pack/post)
```

注意这里发的 Topic 是**老师的名字**（`$sys/9YIs0S7V11/PGW001/thing/pack/post`），但数据里带的是**学生的身份**（`identity: {productID: 04kjwU9TC7, deviceName: Park001}`）。

## 三、核心通信协议

### 3.1 LoRa 定点传输协议

**帧格式：**

```
[目标地址高1B][目标地址低1B][目标信道1B] + [数据内容]
```

**命令帧（网关 → 节点，ASCII，经定点传输按地址定向送达）：**

| 命令 | 内容 | 说明 |
|------|------|------|
| 查询证书 | `AT+CER\r\n` | 查询节点的 OneNET 证书 |
| 查询数据 | `AT+DATA\r\n` | 查询节点的传感器数据 |
| 心跳探测 | `AT+PING\r\n` | 探测节点是否在线（快速，500ms 超时） |
| 控制开关 | `AT+LedEnable=<v>\r\n` | 设置节点的 LED 使能，v=0/1 |

**数据帧（节点 → 网关，二进制帧头）：**

| 帧头 | 数据内容 | 说明 |
|------|----------|------|
| `0xA1` | LoraNodeCert_t (79字节) | 子设备证书(ProductKey/DeviceName) |
| `0xB1` | LoraNodeData_t (10字节) | 传感器数据 |
| `0xC1` | ASCII 字符串 | 命令执行确认(ACK)，如 PONG/AT+LedEnable |

**NodeData 结构体（10字节 packed）：**

```c
typedef struct {
    uint8_t  ParkStatus;      // 车位状态: 0=空闲, 1=有车, 2=僵尸占用
    uint8_t  GeoMagnetic;     // 地磁: 0/1
    uint16_t Ultrasonic;      // 超声波距离: 0~400 cm
    uint32_t OccupiedTime;    // 占用时长: 秒
    uint8_t  LED;             // LED 状态: 0/1
    uint8_t  LedEnable;       // LED 使能: 0/1
} LoraNodeData_t;             // 共 10 字节
```

**NodeCert 结构体（79字节 packed）：**

```c
typedef struct {
    uint8_t  valid;           // 有效标志
    char     ProductKey[12];  // OneNET 产品ID
    char     DeviceName[33];  // OneNET 设备名称
    char     AccessKey[33];   // 留空 (OneNET 代上线无需签名)
} LoraNodeCert_t;
```

### 3.2 OneNET 网关子设备协议

**Topic 表：**

| 方向 | Topic | 说明 |
|------|-------|------|
| 子设备上线 | `$sys/{pid}/{网关}/thing/sub/login` | 发布，代子设备上线 |
| 上线响应 | `$sys/{pid}/{网关}/thing/sub/login/reply` | 订阅，code=200 成功 |
| 子设备下线 | `$sys/{pid}/{网关}/thing/sub/logout` | 发布，代子设备下线 |
| 批量上报 | `$sys/{pid}/{网关}/thing/pack/post` | 发布，params 带子设备 identity |
| 上报响应 | `$sys/{pid}/{网关}/thing/pack/post/reply` | 订阅 |
| 属性设置(下行) | `$sys/{pid}/{网关}/thing/sub/property/set` | 订阅，identity + params |
| 设置回复 | `$sys/{pid}/{网关}/thing/sub/property/set_reply` | 发布 |

> 注：`{pid}` = 网关产品ID (9YIs0S7V11)，`{网关}` = 网关设备名 (PGW001)
> 子设备上线无需签名，平台按拓扑绑定校验。
> 一次只能发一条上线/下线请求（回复不携带子设备身份）。

## 四、网关运行逻辑详解

> 本章是当前代码的实际运行逻辑梳理，覆盖启动到日常运行的每个环节。

### 4.1 启动流程（setup）

```
setup()
 ├─ 1. 串口初始化     DEBUG_SERIAL.begin(115200)
 ├─ 2. OLED 初始化    oled_init()              → 显示 WIFI CONNECTING
 ├─ 3. LoRa 初始化    lora_init()              → 串口就绪, 状态机复位, currentNode=1
 ├─ 4. 节点表复位     resetAllNodes()          → nodeCount=0
 ├─ 5. 证书加载       loadCertsFromLittleFS()  → 从 /certs.dat 恢复已注册节点
 │                      (恢复的节点: online=false, loginPending=true)
 ├─ 6. 开机扫描       lora_triggerDiscovery()  (每次开机都扫一轮)
 │                      → 对每个地址 PING 探测: 无证书通 → CER注册;
 │                        有证书通 → 跳过; 不通 → 下一个
 ├─ 7. MQTT 初始化    onenet_init()            → 服务器/回调/缓冲 2048/keepalive 60s
 │
 ├─ 8. 阶段1 网络连接 oled_showStartupPhase(1) + wifi_init()
 │        wifi_init(): 读 /wifi.cfg → 有则覆盖默认; 无则 runConfigPortal() 阻塞配网
 │        WiFi.begin() 后最多等待 15s (每 0.5s 刷新 OLED + 打状态)
 ├─ 9. 阶段2 服务器   wifi 连上 → oled_showStartupPhase(2) → onenet_connect()
 ├─ 10. 阶段3 扫描    oled_showStartupPhase(3) → oled_scanStart() (扫描画面计时)
 └─ 进入 loop()
```

### 4.2 主循环（loop）

```
loop()
 ├─ 1. checkConfigKeyLongPress()   ← 按键检测 (每轮都调)
 │       短按(<3s) → lora_triggerDiscovery()  触发节点发现
│       长按(5s)  → runConfigPortal()         进入配网 (阻塞)
 ├─ 2. oled_refresh()              ← OLED 刷新 (非阻塞)
 │       在线 2s 间隔; WiFi/MQTT 重连中 450ms 加速动画
 ├─ 3. passiveEvent()              ← 被动事件 (外部数据到达立即处理)
 │       ├─ lora_tick()            LoRa 轮询 + 收帧 (最优先)
 │       ├─ checkNodeTimeout()     节点超时离线检测
 │       └─ onenet_loop()          MQTT 保活 + 收下行 (MQTT 已连时)
 ├─ 4. wifi_handleReconnect()      ← WiFi 断线重连状态机
 ├─ 5. MQTT 连接管理
 │       WiFi 已连 且 MQTT 未连:
 │         到 MQTT_RETRY_DELAY(5s) → onenet_connect() → 成功立即 onenet_uploadAll()
 │       MQTT 已连: → activeEvent()  ← 主动事件 (定时任务)
 └─ 6. delay(1)                    ← 给软串口中断执行时间
```

**被动事件与主动事件的分工（借鉴参考项目）：**

| | passiveEvent() | activeEvent() |
|---|---|---|
| 触发 | 每轮 loop 都跑 | MQTT 已连时每轮 loop 跑 |
| 内容 | LoRa 收发/轮询、节点超时、MQTT 保活 | 定时/事件上报 |

### 4.3 事件驱动架构与系统事件标志位

使用 32 位 `sysEventFlag` 标志位（借鉴参考项目 main.h），O(1) 判断系统状态：

```c
#define SYS_EVENT_MQTT_CONNECTED    0x80000000  /* MQTT 已连接(CONNACK收到) */
#define SYS_EVENT_CONFIG_PORTAL     0x20000000  /* AP 配网模式 */
/* 低16位: 节点在线位, 每位对应一个节点 (1 << (nodeId-1)) */
```

- **MQTT_CONNECTED**：连接成功置位；断开（mqtt.connected() 变 false / WiFi 掉线）清位。标志位由 onenet_handler 收口维护（置位/清除统一走 connect/disconnect/loop）
- **CONFIG_PORTAL**：进入配网置位，OLED 显示配网画面
- **节点在线位**：收到节点数据/证书置位；节点超时离线清位

> MQTT 保活不占标志位：底层由 PubSubClient keepalive 负责（见 4.7 节）。

### 4.4 LoRa 轮询调度状态机

`lora_tick()` 每轮执行一次，核心是"一收一发"：

```
lora_tick()
 ├─ 1. 吃干净串口数据 (帧解析状态机)
 │       RX_WAIT_HEADER → 识别帧头(0xA1/0xB1/0xC1) → RX_FRAME_*
 │       - 0xA1 证书(79B) → updateNodeCert()   → 标记待代上线
 │       - 0xB1 数据(10B) → updateNodeFromRaw() → 缓存+dataChanged+在线位
 │       - 0xC1 ACK字符串  → 打印日志 (如 PONG / AT+LedEnable)
 │       收到当前轮询节点的回复 → 结束本轮等待:
 │         PONG → pollPhase=2 (下一轮发真实命令)
 │         DATA/CER/ACK → advanceNextNode() 前移
 │
 ├─ 2. 控制命令优先插入
 │       有 pendingCmd 且没在等响应 → 立即发出 (3s 超时), 不算节点轮询
 │
 ├─ 3. 在等响应 → 判断超时
 │       - 控制命令 / DATA / CER: LORA_RESPONSE_TIMEOUT_MS = 3000ms
 │       - PING 探测:             PING_TIMEOUT_MS = 500ms
 │       超时 → 打印"节点N 超时(跳过)" → advanceNextNode() 前移
 │
 └─ 4. 发下一条轮询命令 (按当前节点状态分派)
      │  节流: 正常模式一轮(回绕起算)未满 LORA_POLL_ROUND_MS(2s) 不发命令,
      │        防止节点响应快导致连发占满 LoRa 空口; 搜索模式不节流
      slot = findNode(currentNode)
      ├─ pollPhase==2 (PONG已收) → 发真实命令:
      │      搜索模式: 无证书 → AT+CER 注册; 有证书 → 跳过(探测在线即可)
      │      正常模式: 未注册发 AT+CER / 已注册发 AT+DATA
      ├─ 搜索模式                → 对每个地址(无论注册与否)先发 AT+PING
      ├─ 已注册 && 在线           → 直接发 AT+DATA (快速路径, 不经 PING)
      │                              (每 50 次夹发一次 AT+CER 校验证书, 发现换节点)
      ├─ 空槽位(非搜索模式)       → 直接跳过 (advanceNextNode), 不打扰
      └─ 离线节点(正常模式)       → 发 AT+PING (500ms 超时, pollPhase=1)
```

**离线节点探测退避**：离线节点不是每轮都 PING，而是"越离线越稀疏"——PING 每超时一次，探测档位 +1，下次探测间隔按**指数退避**逐档翻倍 `2s → 4s → 8s → 16s → 32s → 64s`（封顶，`OFFLINE_BACKOFF_STAGES` 档，间隔表在 lora_handler.cpp）。未到下次探测时刻（`offlineProbeAt`）直接跳过该节点。收到任何有效帧（数据/证书/PONG）即证明节点存活，档位归零立即恢复快节奏。目的：防止坏节点/长期断电节点空耗空口、并拖慢整轮轮询（每多一个离线节点一轮多等 500ms）。

**已注册在线节点的快速路径**：在线节点每轮直接收 DATA，不经过 PING 探测，节省空口。

**轮询节流（周期轮询）**：`advanceNextNode()` 回绕到起始地址时记下 `roundStartAt`，正常模式下下一轮必须等满 `LORA_POLL_ROUND_MS`（默认 2000ms）才发首条命令。LoRa 是半双工共享信道，若不节流，节点响应越快网关连发越密（约 100ms 一次），空口会被占满、碰撞丢包率上升；2s 一轮对停车地磁检测完全够用。控制命令不受节流限制（随时优先插入）。

### 4.5 节点搜索模式（discoveryMode）

设计目标：**平时只轮询已注册节点，不打扰空槽位；搜索新节点只在特定时机发生。**

| 触发时机 | 行为 |
|---|---|
| 每次开机 | 自动进入搜索模式扫一轮，确认各地址在线 + 补录新节点 |
| 短按 FLASH 按钮 (<3s) | `lora_triggerDiscovery()` 进入搜索模式重头扫 |
| 正常轮询（默认） | 空槽位直接跳过，只和已注册节点交互 |

搜索模式标志 `discoveryMode`：
- 置位后，**对每个地址（无论是否有证书）逐一发 `AT+PING` 探测**
- PING 通 (PONG) 即确认节点存活 → 置在线状态 + 刷新活性时间（作为代上线前提）
- PING 通 + **无证书** → 下一轮发 `AT+CER` 注册（绑定证书存 Flash，待代上线）
- PING 通 + **有证书** → 直接跳过（证书已有，代上线由 loginPending + uploadAll 定时处理）
- 不通（500ms 超时）→ **同地址重试 PING**（总尝试 `DISCOVER_PING_ATTEMPTS` 次，默认 3 = 首次 + 2 次重试）：
  LoRa 上电首帧易丢，一轮只 PING 一次常因首帧丢失误判"不在线"；重试几次可显著
  提高搜索阶段发现成功率。全部尝试仍不通 → 换下一个地址
- **扫完一轮全部地址自动复位**（`advanceNextNode()` 回绕到起始地址时），恢复正常轮询
- 搜索阶段每个地址最多耗时 `500ms × DISCOVER_PING_ATTEMPTS`（默认约 1.5s）；扫描画面不设最长展示上限（一轮必会扫完退出）

**节点注册（registerNode）**：收到数据或证书时自动注册（`nodeId 1..LORA_MAX_NODES`，满则拒绝）；注册后节点进入正常轮询列表。

### 4.6 节点超时与离线检测

`checkNodeTimeout()` 每轮执行，**动态超时**：

```
timeoutMs = NODE_DATA_TIMEOUT_BASE(3s) + nodeCount × NODE_PER_NODE_TIMEOUT(3s)
```

| 已发现节点数 | 离线判定阈值 |
|---|---|
| 1 | 6 秒 |
| 2 | 9 秒 |

节点超过阈值未收到数据 → 标记离线：
- `online = false`，清除该节点在线事件位
- 若已代上线过 (`subLogin`) → `logoutPending = true`，等待代下线
- 之后轮询转为"离线节点"路径：先 PING 探测，通了恢复数据交互

> 超时阈值刻意大于"轮询一圈最坏耗时"，避免在线节点被误判离线。

### 4.7 MQTT 保活与假死检测

**问题**：WiFi 还连着、但 MQTT 底层 TCP 已半开（NAT 超时/运营商掐连接）时，`mqtt.connected()` 可能仍为 true，数据实际发不出去 —— 假死。

**机制（依赖 PubSubClient 库 keepalive，`mqtt.setKeepAlive(60)`）**：

```
mqtt.loop() (passiveEvent 里每轮调用):
 ├─ 60s 无任何活动 → 库自动发 PINGREQ
 ├─ 120s 无任何数据 (PINGRESP/业务回复都算) → 库判定掉线, mqtt.connected()=false
 └─ onenet_loop() 检测 connected()==false → onenet_disconnect() 收口清标志 → 走重连

断线清理收口: WiFi 断线边沿 / onenet_loop / 主动断连 全部统一走 onenet_disconnect()
```

> 说明：早期参照参考项目实现过 PING_SENT 标志位的业务级假死检测（60s 手动组 PINGREQ 包 +
> 60s 内无平台回复即判定），与库 keepalive 双轨冗余且定时重合，已于 2026-08-10 移除。
> 现在完全依赖库 keepalive 一条通道：60s 自动 PINGREQ + 120s 无数据自动断开。

### 4.8 WiFi / MQTT 断线重连状态机

**WiFi（wifi_handleReconnect）**：

```
WiFi 在线:
  已拿到 IP → 从断线恢复打印"重连成功"
  未拿 IP   → 打印"获取IP中..."
WiFi 断线:
  ├─ 断线边沿 → 立即 onenet_disconnect() 清 MQTT 标志 (防假死, 双保险)
  ├─ begin() 在途 → 10s 连接窗口内不打扰 (wifiBeginInFlight/wifiBeginAt)
  │                窗口超时未连上才重新发起
  └─ 每 2s 节流 (lastWifiRetry) → WiFi.disconnect() + WiFi.begin()
状态变化通过 wifi_printStatusChange() 打串口 (空闲/找不到SSID/连接失败/连接丢失...)
```

**MQTT（loop 中）**：
- WiFi 已连 且 MQTT 未连 → 每 5s 重试 `onenet_connect()`，成功立即 `onenet_uploadAll()`
- `onenet_connect()` 失败时按 CONNACK 错误码输出中文日志（超时/TCP/未授权/Token 错误等）
- **重连成功后平台会话重置** → 所有已注册节点**先统一代下线一遍**（`logoutPending=true`，清掉平台可能残留的子设备在线标记，防止网关重启/断线期间出现过期伪在线），再置 `loginPending=true`（仅在线节点会被重新代上线，离线节点保持离线）

### 4.9 代上线 / 代下线 / 批量上报状态机

`onenet_uploadAll()` 周期调用（每 15s 或 `dataChanged`），执行顺序：

```
1. 待代下线 (logoutPending) → subLogout() 一次一条, 发完返回
2. 正在等上线回复 (awaitingLogin):
     超过 SUB_LOGIN_TIMEOUT_MS(5s) 未收到 reply → 重新排队
3. 待代上线 (loginPending && online) → subLogin() 一次一条, 发完返回
4. 已上线节点 (online && subLogin) → subPost() 批量上报
```

**登录前提（在线才上线）**：只有"确认存活"的节点（`online=true`）才会被代上线。
存活 = PING 通(PONG) 或收到数据/证书。离线节点不登录 → **平台在线列表始终与真实状态一致**；
节点掉线 → 代下线；恢复（PING 通）→ 重新进入待上线队列，自动重新登录。

**为什么上线/下线一次只发一条**：OneNET 的回复 `{"code":200}` **不携带子设备身份**，同时发多条无法对应。所以串行：发一条 → 等回复 → 发下一条。

**代上线回复处理**（mqtt_callback）：
- code==200 → `subLogin=true`，**立即 subPost() 上报一次**
- code!=200 → `loginPending=true` 稍后重试

### 4.10 下行控制命令流程

```
OneNET 平台推送 → $sys/.../thing/sub/property/set
  → mqtt_callback() 识别 topic
  → handleSubPropertySet():
      ├─ 取 productID/deviceName/params
      ├─ 按 deviceName 匹配节点 (找不到 → 回复 404)
      └─ 解析属性: LedEnable → lora_sendControl(nodeId, "LedEnable", v)
  → 回复 set_reply (code:200)
  → dataChanged = true

网关侧:
  lora_sendControl() 组 "AT+LedEnable=<v>\r\n" 存入 pendingCmd 单槽队列
  下一轮 lora_tick() 优先发出 (控制命令优先于轮询)
  节点收到执行 → 回 ACK (0xC1)
```

### 4.12 OLED 集中显示

**启动画面**（setup 依次切换，单行居中，无 STEP 序号）：

```
1/3  WIFI CONNECTING     (WiFi 连接中)
2/3  SERVER CONNECTING   (MQTT 连接中)
3/3  SEARCHING NODES.    (动画圆点 + FOUND: n 节点搜索进度)
```

**扫描画面退出条件**（开机扫描与手动搜索共用同一套）：
- 扫描真实结束（discoveryMode 清除，扫完一轮）
- **且**已展示满最短时长 `OLED_SCAN_MIN_MS`(3s)——保证用户看清搜索过程与 FOUND 数字；搜索（2 地址）约 1.6s 即结束，3s 足够看完整进度跳动
- 刷新节奏：扫描画面期间用快档 `OLED_ANIM_MS`(0.45s) 刷新，FOUND 数字与动画点实时更新（若按 2s 慢刷，会因搜索过早结束而只画到第一帧 0 就被退出逻辑跳走）
- `OLED_SCAN_MAX_MS`(10s) 保险：正常情况下扫描一轮必会结束（节点被动应答，每个地址要么回包要么超时，扫完即清 discoveryMode），该上限几乎用不到，仅防止意外卡死画面

> 短按 FLASH 触发搜索时复用第 3 屏动画（`oled_startManualScan()`），
> 搜索期间全屏显示 SEARCHING NODES + FOUND，结束后自动回主界面。
>
> **FOUND: n 语义**：n = 本次搜索中**确认存活**（收到 PONG/数据/证书，即 online=true）的节点数。
> **不是 Flash 里的证书数**——证书恢复的节点若没插电，不会计入 n，
> 避免"没插电却显示已找到"的假象。只显示数量、不显示扫描范围分母。

**运行主界面**（每 2s 刷新）：

```
Header: PGW001 + WiFi信号条(4格, 重连时逐格跳动) + MQTT云朵(白=在线/闪=重连/空心=断)
节点行: 每页 4 个 (多节点每 5s 翻页)
  #01 EMP   |▄▄  12s     (编号/状态/信号/停车时长)
  离线: 整行白底反显 ERR + "--" 时长
Footer: ↑下行 ↓上行 每分钟消息速率 + 页码 P1/2
```

状态缩写：`EMP`=空闲、`OCC`=有车、`ZOMB`=僵尸车。
节点信号用"距上次刷新时长"模拟（LoRa 帧无 RSSI 字段）。

**配网画面**：`Config Mode / AP:xxx / IP: 192.168.4.1 / Open any URL`

## 六、关键设计决策

### 6.1 为什么用网关轮询（老师点名）而非节点主动上报？

| 方案 | 问题 | 结论 |
|------|------|------|
| **节点主动上报** | 多节点同时发送 → LoRa 空中碰撞 → 数据丢失 | 放弃 |
| **网关轮询** | 同一时刻只有被点名节点回复 → 零碰撞 | **采用** |

### 6.2 为什么用 ESP8266 做主控而非 STM32？

| 方案 | 问题 | 结论 |
|------|------|------|
| **STM32 主控 + ESP8266 透传** | 两芯片间串口通信脆弱、下行命令延迟高、WiFi 协议栈在 AT 指令层不稳定 | 放弃 |
| **ESP8266 主控** | MQTT 库直接在 ESP8266 上跑、事件回调驱动、串口只接 LoRa 模块 | **采用** |

### 6.3 为什么代上线一次只能发一条？

OneNET 的上线回复 `{"code":200}` 不携带子设备身份。如果同时发两条上线，网关无法区分回复对应哪个设备。因此**一次只能发一条，收到回复后再发下一条**。

### 6.4 为什么用二进制结构体传数据而非 JSON/字符串？

| 方案 | 字节数 | 解析方式 | 结论 |
|------|--------|----------|------|
| **JSON 字符串** | ~100 字节 | 解析耗时、浮点精度问题 | 否 |
| **ASCII CSV** | ~40 字节 | 字符串分割易错 | 否 |
| **二进制结构体** | **10 字节** | memcpy 零拷贝 | **采用** |

### 6.5 稳定性保障设计

| 设计 | 说明 |
|------|------|
| **每个操作都有超时** | LoRa 响应 3s、PING 探测 500ms、代上线 5s、离线动态超时(3s 基准+每节点 3s)，不卡死 |
| **状态机驱动** | RX_WAIT_HEADER → RX_FRAME_*，出错可回退；轮询 pollPhase 0→1→2 |
| **自动恢复** | 节点掉线 → 代下线；节点恢复 → 重新代上线 |
| **MQTT 假死检测** | PubSubClient keepalive：60s 自动 PINGREQ + 120s 无数据主动断开重连 |
| **WiFi 双保险** | 断线边沿立即清 MQTT 标志；begin() 连接窗口 10s 防打断 |
| **证书持久化** | 重启后免重新扫描，直接恢复节点列表 |
| **只轮询已注册** | 平时空槽位不打扰，空口干净，LoRa 冲突概率低 |

### C.2 常见问题排查

**Q: 平时串口还能看到 `PING-> 节点N`（空槽位）？**
- 说明网关处于搜索模式。搜索模式在每次开机或短按 FLASH 时进入，扫完一轮自动退出。正常运行时空槽位直接跳过，只有已注册节点会被轮询。

**Q: 串口显示 `SubLogin` 但一直没收到 `login OK`？**
- 检查子设备是否已在平台绑定到 PGW001 拓扑
- 检查 `productID` 和 `deviceName` 是否与平台创建的一致（大小写敏感）

**Q: 节点上报数据了，但平台看不到属性值？**
- 检查物模型属性标识符是否与代码中的 `SUB_PROP_*` 宏完全一致
- 检查 `thing/pack/post` 的 JSON 格式是否包含正确的 `identity` 字段

**Q: 网关 MQTT 频繁断连？**
- 检查 WiFi 信号强度
- PubSubClient keepalive 已设为 60s
- 检查 Token 是否过期（`et` 时间戳）

**Q: LoRa 收不到节点回复？**
- 检查模块配置：`AT+MODE1`（定点）、`AT+MAC`（地址）、`AT+CHANNEL`（信道）
- 检查波特率：网关 SoftwareSerial 9600，节点 USART2 115200（模块内部转 9600）
- 检查信道：两端 `LORA_CHANNEL` 必须一致（当前 0x00=433.15MHz）

**Q: 新节点接入后网关发现不了？**
- 短按 FLASH 键触发一次全量扫描（`[LoRa] 手动触发节点发现`）
- 或确认节点 LoRa 地址在轮询范围（1..LORA_MAX_NODES）内

**Q: OLED 显示哪些内容？**
- 启动: 1/3 WIFI CONNECTING → 2/3 SERVER CONNECTING → 3/3 SEARCHING NODES 扫描画面
- 运行: Header(PGW001+信号+MQTT) + 节点行(编号/状态/信号/时长, 离线反显) + Footer(上下行速率+页码)
- 配网: Config Mode + AP 名 + IP 192.168.4.1
- 接线: I2C SDA=D5 / SCL=D6; 8x8 位图字库放 RAM（加 PROGMEM 会触发 Exception(3) 无限重启）

### C.3 编译注意事项

- **ESP8266 网关**：Arduino IDE 选择 NodeMCU 1.0 (ESP-12E Module)，Flash Size 选 4MB (1M SPIFFS)
- **Gateway 源码编码**：全部 UTF-8 无 BOM（lora_protocol.h 等带 BOM 文件已统一去除）
- **STM32 节点**：Keil MDK 编译，.c/.h 文件编码为 GBK
- 网关端 `platform_cfg.h` 中 `ONENET_TOKEN` 含特殊字符，确保不被编辑器转义

### D.3 参考项目遗留实现细节

#### D.3.1 串口环形缓冲区方案（参考项目串口处理）

参考项目为串口配置了双指针环形缓冲区：

```
UsartRxDataInPtr  写入指针 (中断接收时)
UsartRxDataOutPtr 读出指针 (主循环取出时)
UsartRxDataEndPtr 结束指针 (满时回绕)
```

ESP8266 Arduino 用 Serial 自带环形缓冲区，无需自己实现，逻辑一致。

#### D.3.2 DMA 发送 + 定时器刷新（参考项目串口发送）

参考项目使用 DMA + 100ms 定时器刷新发送：

```c
if((UsartTxDataOutPtr != UsartTxDataInPtr) && (TxCpltflag == 0) && (HAL_GetTick() - TxTimer > 100))
```

ESP8266 SoftwareSerial 不支持 DMA，用每轮 loop 检测待发送缓冲 + 间隔发送，
避免连续占用 LoRa 空口导致丢包。

#### D.3.3 AUX 载波检测方案（参考项目 LoRa 模块）

参考项目用 LoRa 模块 AUX 引脚判断模块状态：

- AUX=1：模块空闲，可发送/接收
- AUX=0：模块忙，正在处理

ESP8266 未使用 GPIO 检测 AUX（模块自带 LBT 载波监听），如需更可靠的
防碰撞可后续接 AUX 引脚检测发送时机。
