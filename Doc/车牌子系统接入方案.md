## 0. 结论速览

| # | 事项 | 结论 |
| --- | --- | --- |
| 1 | 摄像头 | **一行不改**（P5.80 已是合规 AT 从机） |
| 2 | 节点 | 新增 USART3 驱动 + `Plate_Task()`（非阻塞状态机）+ 车位上沿触发 + 策略执行 |
| 3 | LoRa 协议 | **状态量进数据帧**（v4：18→19 字节，新增 `CamFlags` 字节）、**事件量走独立帧**（车牌 `0xF1`）；`LORA_PROTO_VERSION` → **4**；**双端必须同时烧** |
| 4 | 云平台 | 节点物模型新增 **属性 ×4 必用 + 1 预留**（`PlateNumber` / `PlateConfidence` / `CapturePolicy` / `CameraOnline`；另留 `PlateColor` 待二期）+ **服务 ×2**（`TriggerCapture` / `SetCapturePolicy`） |
| 5 | **车牌怎么到 App** | 节点存缓存 + 数据帧挂「有牌待取」旗子 → 网关发 `AT+PLATE` **来取** → 节点回 `0xF1` 帧 → 网关写属性 → App 3s 轮询看到（**详见 §3 D2**） |
| 6 | 触发方式 | **节点自动**（有车/僵尸车那一瞬间，按策略）+ **App 手动**（调节点服务）；手动有回执，**自动没有回执、只有属性** |
| 7 | 设计原则 | **取其精华、去糟粕**（§4.0 逐条对照旧摄像头物模型） |
| 8 | 拍照策略 | 判定归**节点本地**，App 只管**策略**（默认 **1 = 有车即拍**）；**App 永不直接控制摄像头**（§3 D7） |
| 9 | **图片复审** | **可选项、最后做**（§13）：低置信度时可走 LoRa 传**二值 94×24 缩略图**（282 B / 0.4 s）；若走现成 JPEG 则要 3~4 s（不划算）。具体见 §13 |
| 10 | **摄像头在线** | 只要 **bool**（能回=在线）：`CameraOnline` 是**状态量 → 搭数据帧的顺风车**（`CamFlags` bit3），**不新开帧、不加下行命令**；节点用只读的 `AT+INFO` 周期探活（§4.6） |

## 1. 现状与目标

### 1.1 现状（旧链路）

```
App ──服务 TriggerCapture──> OneNET ──> 摄像头 Cam001(产品 4enONCu0Y7, 联网 + 百度OCR)
                                          └─> 属性上报 PlateNumber/PlateColor/PlateConfidence

节点 Park001 ──LoRa(18B 数据帧)──> 网关 PGW001 ──pack/post──> OneNET(子产品 04kjwU9TC7)
       物模型: ParkStatus/GeoMagnetic/Ultrasonic/OccupiedTime/LED
               /ZombieThresholdSec/SensorDistanceCm/SignalRssi   ← 没有车牌
```

由此产生的既有缺陷（文档已记录，非本次新发现）：

| 出处 | 缺陷 |
| --- | --- |
| `技术难点分析报告` 3.5.1 | App 每 3s 从平台重建车位快照，而**节点物模型不含车牌**，拍照写入的车牌在下一轮被冲成 `null` → 「拍照后几秒车牌消失」；现用 `_capturedPlateCache` + 800ms×N 短轮询**绕** |
| `技术难点分析报告` 4.7 | 僵尸车派单需要"现场车牌"，但车牌来自独立摄像头设备且有 1~2s 入库延迟；现用"通知前补牌（最多 3 次）"兜底 |
| `通信架构重构方案` 17.9 | **节点侧解析还没写**；节点不会驱动摄像头 |

### 1.2 目标（新链路）

```
【自动】车位检测(超声波+地磁) 状态上升沿 ──┐
【手动】App 调节点服务 TriggerCapture ────┤
【策略】App 调 SetCapturePolicy ──────────┘(决定"什么时候拍")
                    │
                    ▼
             节点 STM32F103 ── USART3 ──> 摄像头 ESP32-S3 (P5.80)
              │   AT+RUN           <── $PLATE,京Q06666,93,42   (约 1s)
              │   PlateCache(车牌/置信度/帧号/valid) + 「有牌待取」旗子
              ▼
         LoRa 数据帧(v4, 带旗子) ──> 网关
         网关发 AT+PLATE ──> 节点回 0xF1 车牌帧 ──> 网关
              ▼
         OneNET 节点属性(PlateNumber/PlateConfidence/CapturePolicy) ──> App(3s 轮询)
```

| --- | --- | --- |

## 3. 关键设计决策

### D1｜音量分家：**状态量进数据帧，事件量走独立帧**　**【总原则】**

| 量的性质 | 特征 | 去哪 |
| --- | --- | --- |
| **状态量** | 每个快照都该带、值不常变、很小（1~4 字节） | **进数据帧** `LoraNodeData_t`（阈值、拍照策略、待取旗子） |
| **事件量** | 偶发、带负载、较大 | **独立帧类型**（车牌 `0xF1`） |

**本项目的"升级风险"不成立**：节点与网关可以**同时烧录**（实验项目、两台设备都在手），所以"改数据帧需要双端同步"**不是障碍**，只是操作要求。

> ⚠️ **更正记录**：本文档早期版本把"网关按长度严格校验"当成**不能动结构体**的理由 —— 那是**工程风险，不是技术限制**，该论证作废。判据应当是"**状态还是事件**"。

| 量 | 归属 | 理由 |
| --- | --- | --- |
| 车牌 | **独立帧 `0xF1`（事件量）** | 偶发事件、每帧负载 34 字节（含 1 字节预留颜色）；数据帧每约 2.1s 一发 → 塞进去会让**每一帧都白背 30 多字节**（与"怕改结构体"无关） |
| 拍照策略 / 待取旗子 | **进数据帧（状态量）** | 小、不常变、每个快照都该带；进数据帧才能**以节点真实值为准** |

**既然允许同时烧，就要能发现"没烧齐"**（而不是靠纪律）：

- `shared/lora_protocol.h` 的 `LORA_PROTO_VERSION` **由 3 提到 4**；
- 该宏目前**只是个注释、代码里没有任何地方引用**（已核实：全仓仅 1 处定义）→ 本次**真正用起来**：两端**开机横幅打印协议版本**；网关收到**长度不符**的数据帧时明确打印「期望 19 字节(协议 v4)，收到 18 字节 → 疑似节点固件未同步烧录」。
- 效果：混烧症状从"数据静默全丢、查不出原因"变成"日志一眼指明原因"。

### D2｜**车牌上行：统一走「网关来取」**（本版重写，前一版表述有误）

**先说清事实**：车牌**不在数据帧里**。数据帧只装状态量（车位状态、时长、阈值、拍照策略、待取旗子），车牌只走独立帧 `0xF1`。

> ⚠️ **更正记录**：早期版本写"自动触发的车牌**随数据帧一起带走**"，**这是错的**（数据帧里没有车牌字段）；另有一版写"手动触发时节点在回完 ACK 后**抢发**一帧" —— 那是"赌网关此刻在听"，多余且脆弱，**已删除**。

**现在的统一机制**（手动/自动共用一条路径）：

1. 节点拍完 → 车牌存 `PlateCache`，并置「**有牌待取**」旗子（放进数据帧的 `CamFlags` 字节）；
2. 网关看到旗子 → 发 `AT+PLATE`；
3. 节点回一帧 `0xF1`（含车牌/置信度/有效性）并**清旗子**；
4. 网关写属性 → 云平台 → App。

**为什么这是最优**：

| | 网关来取（本方案） | 节点抢发（早期版本） |
| --- | --- | --- |
| 抢麦风险 | **零**（永远"网关问、节点答"） | 赌"网关此刻在不在听" |
| 丢包 | 旗子未清 → 下一轮自然再取，**自带重试** | 丢了就丢了 |
| 代码路径 | **手动/自动共用一条** | 两条时序，要分别测 |
| 时延 | 手动触发时网关收到 ACK **立刻**取；LoRa 单次往返仅几十~几百 ms（2.1s 是**轮询周期**，不是单次往返时延） | 只省一次往返 |

**两条触发路径的完整时序**：

**A｜自动触发**（车停稳）
```
节点: ParkStatus 0→1, 稳定 3s（策略=1）
节点 → 摄像头: AT+RUN
摄像头 → 节点: $PLATE,京Q06666,93,42            (约 1s)
节点: 存 PlateCache, 置「有牌待取」旗子
节点 → 网关: 数据帧 v4(带旗子)                   ← 等网关轮询
网关 → 节点: AT+PLATE
节点 → 网关: 0xF1 车牌帧, 清旗子
网关: PlateNumber 属性变化 → pack/post → 云平台(入库 1~2s)
App: 3s 轮询拉到 → 显示 京Q06666
```

**B｜手动触发**（App 点"拍照"）
```
App → 云平台: 调 TriggerCapture
云平台 → 网关: invoke
网关 → 节点: AT+CAPTURE
节点 → 摄像头: AT+RUN
摄像头 → 节点: $PLATE,京Q06666,93,42
节点 → 网关: ACK(已受理)
网关 → 云平台: invoke_reply{Result=true, ActualValue=true}   ← 回执只表状态, 不带车牌
网关 → 节点: AT+PLATE                        ← 立刻, 不等下一轮
节点 → 网关: 0xF1 车牌帧
网关 → 云平台: 属性上报 → App 拉到 → 显示
```
App 体验：点按钮约 1~2s 拿到"成功"回执，再拉 1~2 次属性即可看到车牌。

### D3｜触发策略与重试参数

| 参数 | 值 | 理由 |
| --- | --- | --- |
| 触发条件 | `ParkStatus` **上升沿**（0→1 有车；1→2 僵尸车，按策略） | 避免占用期间反复拍 |
| 稳定延时 | 连续 3s 满足才拍 | 防过车/毛刺误触发 |
| 冷却时间 | 同一事件类型 60s 内不重复触发 | 去重，保护链路与摄像头 |
| 拍照时机（策略） | **默认 1 = 有车即拍**；可下发 0/2/3（§4.5） | 判定归节点本地，策略归 App 配置 |
| 识别重试 | 未识别（`$PLATE,-,…`）最多重试 2 次，间隔 3s | 换个帧可能就成 |
| 单次超时 | 等 `AT+RUN` 回复 **2s**（一帧约 1s） | 见 `AT指令手册-节点版.md` |
| 上电保护 | 节点上电后**延时再启用触发**（见 §3 D8） | 摄像头开机有预热/自检 |

### D4｜云端数据模型：加在**节点**物模型

车牌是"节点采集的现场信息"，天然属于节点。加在节点物模型后，App 的 3s 轮询**天然拿到车牌**，不必再靠 `_capturedPlateCache` 硬撑。

### D5｜手动触发的回执语义（沿用旧摄像头那套）

| 字段 | 含义 |
| --- | --- |
| `ActualValue` | **动作是否真的执行**：1 = 节点确实发出 `AT+RUN` 并收到回复；0 = 节点忙 / 摄像头超时 / 链路异常 |
| `Result` | **本次是否识别出车牌**：1 = `PlateNumber` 合法；0 = 拍到了但认不出（`$PLATE,-`）或未执行 |

> 二者必须**分开**：`Result=0` 不代表拍照失败（可能只是没认出来），App 文案要能区分「未识别」与「链路异常」。

### D6｜旧摄像头设备 `Cam001` 的处置

摄像头不再上云 → `Cam001`（子产品 `4enONCu0Y7`）会永久离线。

- 物模型**保留不删**（留档、便于回滚旧方案），但**从 App 可用拓扑里摘除**；
- `TriggerCapture` 在**节点**物模型下重建同名服务（App 调用入口改动最小）。

### D7｜App 永不直接控制摄像头；判定归节点，App 只管策略

| 事项 | 归属 | 说明 |
| --- | --- | --- |
| **什么时候拍**（策略） | **App 配置**，节点执行 | 0 不拍 / 1 有车 / 2 僵尸车 / 3 都拍 |
| **判定的那一瞬间** | **节点本地** | `ParkStatus` 上升沿的一刻，节点自己发 `AT+RUN` |
| **拍照动作** | **节点** | 只有节点对摄像头说话 |
| **手动拍一张** | App → **节点服务** → 节点 → 摄像头 | App **不直连**摄像头 |

⚠️ 旧架构的"自动拍照"其实是 **App 定时/策略发起的请求**（触发权在云侧）；本次**整块搬到节点**，App 侧那部分逻辑**删除**。这是最容易"照旧写法"写错的地方。

### D8｜部署纪律与容错（现场必读，来自审查补充）

| 项 | 要求 | 为什么 |
| --- | --- | --- |
| **接线** | 摄像头 TX(GPIO47) → 节点 **PB11**(USART3_RX)；摄像头 RX(GPIO48) → 节点 **PB10**(USART3_TX)；**必须共地**；3.3V TTL，115200 8N1 | 交叉接线、共地是 TTL 串口能通的前提 |
| **供电** | 摄像头**独立供电**（5V/USB）；**严禁从 F103 板取电** | S3 + 相机峰值电流远超 F103 能提供的，会拉垮节点/引起复位 |
| **控制权** | 电脑调试后必须 `AT+CTRL=NODE`（或**重启摄像头**，上电默认 NODE） | 控制权在电脑时，节点的 `AT+RUN` 会收到 `ERR:没有权限` |
| **识别模式** | 部署前确认 `AT+TRIG=1`（只听触发，默认值） | 若被电脑改成 `AT+TRIG=0`，摄像机会**主动连续发** `$PLATE`，节点会收到非预期的行 |
| **图片档位** | 部署前把 `AT+IMG=0`（关图） | 图片只走电脑口（与节点无关），但开着会白占串口带宽 |
| **上电顺序** | 先给摄像头供电、等它就绪，节点再启用触发（**节点上电延时 5s 再启用**） | 摄像头开机有预热/自检，太早触发会超时 |
| **升级方式** | 本版（v4）**只能串口线双端同时烧**，**禁止走 OTA** | OTA 必然一边先一边后 → 中间窗口数据帧长度不符 → 车位数据全丢（见 §11） |

## 4. 云平台物模型变更（按当前架构重新定，不照搬旧物模型）

### 4.0 判断标准：为什么和旧摄像头物模型不一样

旧物模型（`PlateRecognition/ParkCamera_物模型.json`）是在「**摄像头联网 + 百度 OCR**」前提下设计的，很多字段是为当时的约束服务。现在识别已下沉端侧、车牌由**节点**采集，逐条重判一个问题：**它当初存在的原因，现在还成立吗？**

| 旧设计元素 | 当初为什么 | 当前情况 | 结论 |
| --- | --- | --- | --- |
| 车牌放**摄像头设备**属性（跨设备） | 识别在摄像头里，云端只能拼两台设备 | 车牌由**节点**采集，节点物模型天然承载 | **改**：改放节点属性（老缺陷随之消失） |
| 服务回执只回状态、数据走属性 | 同步回执通道窄 | 仍成立（ACK 是 ASCII 行） | **留** ← 要吸收的精华 |
| `Result` / `ActualValue` 双语义 | 区分"没执行"与"没认出" | 仍成立 | **留** |
| `PlateConfidence` = **float 0~1** | 百度 OCR 返回 0~1 | 端侧输出是 **0~100 整数**，且不是校准概率 | **改**：`int32 0~100`（省一次换算，避开平台 float 边界坑） |
| `DeviceStatus`（0空闲/1成功/2失败） | 让 App 知道摄像头状态 | 需求仍在，但**不需要两个字段** | **吸收需求、砍掉冗余**：用 `PlateNumber` 三态语义表达（§4.1） |
| `PlateColor` | 百度 OCR 返回颜色 | **端侧模型不输出颜色**（`$PLATE` 只有 号/置信度/帧号） | **保留为预留**（用户决定，将来可能用）：物模型留字段 + LoRa 车牌帧留 `color` 字节，一期不上报；等摄像头侧能给出颜色时直接启用，**不必再改协议** |
| `CaptureTime`（string） | 摄像头联网可对时 | **节点无 RTC；网关也无对时能力**（已核实：无 NTP/`configTime`） | **砍**：App 用平台「属性更新时间」 |
| App `_capturedPlateCache` | 对抗"节点无车牌 + 3s 轮询把车牌冲成 null" | 车牌进节点属性后**不会被冲掉** | **砍**（§8） |
| App「800ms × N 次短轮询」 | 云端 OCR 入库要 1~2s | App 是 **REST 轮询**（已核实：`http` + `query-device-property`，无推送） | **改**：N 次 → **1~2 次** |
| "通知前补牌最多 3 次" | 云端识别可能失败/慢 | 端侧约 1s 出结果、属性稳定 | **砍** |
| `PlateFrameNo` / `PlateSource` | — | 业务无用（通知车主只看车牌） | **不上云**：只留在 LoRa 帧与日志，排障用 |
| 服务名 `TriggerCapture` | App 已有调用入口 | 入口少改 | **留**（同名同语义） |

**两条当前架构特有、旧设计里没有的规则**：

1. **两条触发路径语义不同**：手动触发有"问的人" → 有回执；**自动触发没有人问 → 没有回执，车牌只能通过属性被看到**。
2. **自动触发必须去重**：上升沿 + 稳定 3s + 冷却 60s（人工触发没有连点问题）。

### 4.1 节点子设备新增属性（4 个必用 + 1 个预留）

**对象**：子产品 `04kjwU9TC7` → 子设备 `Park001` / `Park002`（网关 `pack/post` 代上报，**只读**）

| 标识符 | 名称 | 类型 | 取值 / 口径 | 上报时机 |
| --- | --- | --- | --- | --- |
| `PlateNumber` | 车牌号码 | **string**（UTF-8，**≤16 字节**） | **三态**：合法车牌 = 识别成功；`-` = 拍到了但没认出来；**从未上报** = 从未拍过 | 每次识别完成后（自动/手动都报） |
| `PlateConfidence` | 识别置信度 | **int32（0~100）** | 端侧原始口径，不做换算；`PlateNumber` 为 `-` 时上报 0 | 同 `PlateNumber` |
| `CapturePolicy` | 拍照策略 | **int32（0~3）** | 0 不拍 / 1 有车拍 / 2 僵尸车拍 / 3 都拍（§4.5） | 随**数据帧**上报（节点当前真实生效值） |
| `CameraOnline` | 摄像头在线 | **bool** | 1 = 探活能回（节点↔摄像头链路可用）/ 0 = 连续 3 次探活无回应（§4.6） | 随**数据帧**上报（`CamFlags` bit3），状态变化即生效 |

> **关于 `PlateNumber` 的三个易错点**（App 侧务必按此实现）：
> 1. **它是"最近一次识别结果"，是残留值**：车辆离开后**不会自动清空** → App 必须**只在车位非空闲时**显示车牌，否则会出现"空车位显示上次车牌"（旧设计需要缓存的根因就是这条）；
> 2. **三态渲染**：有值 = 正常显示；`-` = 显示"未识别"并提示靠近/换角度；**从未上报** = 不显示（正常初态）；
> 3. App 是 REST 拉取、**无推送** → 手动触发后靠"再拉 1~2 次"尽快看到。

**范围校验提醒**：平台对超出物模型范围的值会**拒收**（历史坑 `code=2213`，见 `通信架构重构方案` S29）。所以：
- `PlateConfidence` 必须在节点/网关侧夹到 **0~100**；
- `PlateNumber` 上报前按 UTF-8 **安全截断到 16 字节**（不能截成半个汉字，见 §7）；
- `CapturePolicy` 夹到 0~3。

### 4.2 节点子设备新增服务（共 2 个）

| 标识符 | 名称 | 入参 | 出参 |
| --- | --- | --- | --- |
| `TriggerCapture` | 手动触发拍照识别 | **无** | `Result` (int32 0/1) / `ActualValue` (int32 0/1) |
| `SetCapturePolicy` | 设置拍照策略 | `PolicyValue` (int32, 0~3) | `Result` (int32 0/1) / `ActualValue` (int32 0~3) |

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `Result` | **int32（0/1）** | 本次**是否识别出车牌**（`TriggerCapture`）／**是否设置成功**（`SetCapturePolicy`） |
| `ActualValue` | **int32** | **动作是否真的执行**（0 = 节点忙/链路异常；此时 `Result` 必为 0）。`SetCapturePolicy` 下它就是**实际生效的档位**（0~3） |

> ⚠️ **类型更正（2026-10-09，以现有物模型为准）**：回执一律用 **int32（0/1）**，不是 `bool` —— 本产品既有服务 `SetLed` / `SetSensorDistance` / `SetZombieThreshold` 全部如此。旧摄像头产品（`4enONCu0Y7`）那份用 bool，**不要照抄**。
> **成品文件**：全量物模型（13 属性 + 5 服务）见 **`Doc/Park_物模型.json`**，可直接导入控制台。

**为什么回执不带数据（沿用既有模式，不要另发明）**：

1. 旧摄像头物模型 `TriggerCapture` 的 desc 原文：「无入参；空闲则执行拍照+车牌OCR并回 Result/ActualValue，**识别结果仍由属性异步上报**」；
2. 阈值下发是**同一套**：`SetZombieThreshold` → 回 `Result/ActualValue`，值由 `ZombieThresholdSec` **属性**承载；
3. ACK 是 ASCII 行，塞中文会污染网关的关键字匹配与长度判定；属性这条路 App 已有现成逻辑。

**超时**：网关现有服务等待上限 `SUB_SERVICE_DEADLINE_MS = 9000`（`系统设计文档` 4.10）；本链路约 1~2s，**余量充足**（旧方案曾放宽到 15s，现在可收回常规值）。

**保留不动的现有服务**：`SetLed` / `SetZombieThreshold` / `SetSensorDistance`。

### 4.4 触发命令总览

| 触发方式 | 发起方 | 云侧动作 | 网关 → 节点 | 节点 → 摄像头 | 结果怎么被看到 |
| --- | --- | --- | --- | --- | --- |
| **节点自动** | 节点（按策略 + 上升沿 + 稳定3s + 冷却60s） | **无** | 无（节点自主触发） | `AT+RUN\r\n` | 节点置「有牌待取」旗子 → 网关发 `AT+PLATE` **来取** → 属性上报。**没有回执**（没人问） |
| **软件手动** | App / 云平台 | 调 `TriggerCapture` | `AT+CAPTURE\r\n` → 收到 ACK 后**立刻** `AT+PLATE\r\n` | `AT+RUN\r\n` | ① 节点回 ACK → `invoke_reply{Result, ActualValue}`；② 网关取牌 → `0xF1` → 属性上报；③ App 拉 1~2 次属性取牌 |
| **策略配置** | App / 云平台 | 调 `SetCapturePolicy{PolicyValue}` | `AT+CapturePolicy=<0..3>\r\n` | — | ACK → `invoke_reply{Result, ActualValue}`；`CapturePolicy` 属性随数据帧上报 |
| **对账/排障**（不入业务链路） | 网关 / 调试者 | — | `AT+PLATE\r\n` | — | 节点回车牌帧（可能 `valid=0`），供对账 |
| **摄像头探活**（状态量，非业务触发） | 节点（每 30s） | — | 无 | `AT+INFO\r\n` | 只见于 `+INFO:` 回包 → 置 `CamFlags` bit3 → 数据帧带出 → `CameraOnline` 属性（§4.6） |

### 4.5 拍照策略

| 取值 | 含义 |
| --- | --- |
| 0 | 不自动拍（只响应手动触发） |
| 1 | 检测到有车（→OCCUPIED）时拍一次 |
| 2 | 判定为僵尸车（→ZOMBIE）时拍一次 |
| 3 | 有车拍一次 **+** 转僵尸车再拍一次（停车当时留证 + 派单时留证） |

**默认值 = 1（有车即拍）**　【已定 · 2026-10-09】

- 业务上最常见：车一停稳先留一张证，后面派单/通知都有据可依；
- 节点侧写成宏 `CAPTURE_POLICY_DEFAULT = 1`（运行期变量、不落盘，与 `g_zombieThreshold` 同级）；
- 网关侧**持久化 + 补发**，保证节点重启 / 换网关后仍是用户设过的值。

**回读：与阈值同构（进数据帧，以节点为准）**：

| | 阈值类（既有） | 拍照策略（本方案，同构） |
| --- | --- | --- |
| 回读通道 | 节点随数据帧上报 `ZombieThresholdSec` | **同样**随数据帧上报（v4 的 `CamFlags` 字节 bit0~1） |
| 好处 | 以**节点真实值**为准：节点重启回默认、命令没生效，都能从属性看出来 | 同左 —— **单一事实源**，不存在"两份账本不一致" |

**代价（明确接受）**：数据帧结构变了 → **节点与网关必须同时烧**（本项目可行，§3 D1）；混烧由协议版本诊断发现。

**去重**：两种策略事件**各自独立冷却**（"有车拍"与"僵尸车拍"分开计时）。

### 4.6 摄像头在线（探活）　【已定 · 2026-10-09：只要 bool】

**一句话结论**：它是个**状态量** → 就**搭数据帧的顺风车**（v4 的 `CamFlags` bit3），**不新开 LoRa 帧、不加下行命令、不动协议版本**；节点只是额外"每 30s 问摄像头一句"。

| 项 | 定案 | 为什么这么定 |
| --- | --- | --- |
| 探活命令 | **`AT+INFO\r\n`** | ① **只读命令，不看控制权**（`node_link.c:391` 白名单 = `CTRL` / `HELP` / `INFO`，任何口任何模式都放行）；② 回包一行 `+INFO:…` 自带版本/统计，顺手可读 `控制权=` |
| ⚠️ 别用裸 `AT` | 裸 `AT` 属于"**只有主人能发**"（`AT指令手册.md` §4） | 控制权被电脑抢走时，节点口发 `AT` 会被回 `ERR:没有权限…` → 探活会把"被抢占"**误判成"离线"** |
| 周期 | **30s** | 状态变化慢；占用可忽略（回包约 300~400 B，115200 下 ≈35 ms） |
| 超时 | **500 ms** | 探活是**毫秒级**回复，不是 `AT+RUN` 那 1s（§6 要点 1 的 PING 那套口径） |
| 判在线 | 500 ms 内**收到任何一行**（`+INFO:` 或 `+CFG:` 都算） | 不解析内容，只要"有回" |
| 判离线（去抖） | **连续 3 次**失败（≈90s）才置 0 | 单次丢包/摄像头正忙，不该翻状态 |
| 恢复 | 收到一次回复**立即**置 1 | 不必等满 3 次 |
| 上电 | 节点上电 **5s 后**才启用探活 | 与拍照的 `PLATE_ARM_DELAY_MS` 共用同一条延时 |
| 串行化 | 探活与拍照**共用 USART3 的那条状态机**，同一时刻只跑一条；**拍照优先**，探活推迟到下一轮 | 半双工口的天然约束（§9 第 21 条） |

**上报口径（只有一个 bool，不引入三态）**

- 节点把结果塞进 `CamFlags` bit3 → 网关解出 → 写云端只读属性 `CameraOnline`；数据帧每约 2.1s 一发，所以**状态翻转最迟 ≈30s + 2.1s 就能被 App 看到**；
- **被抢占 ≠ 离线**：控制权在电脑时 `AT+INFO` 照样能回 → 判**在线**（链路确实是通的）。此时节点自己发 `AT+RUN` 会失败，那属于**拍照链路诊断**（§9 第 11 条的计数器），不污染"在线"语义；
- **白送的好处**：`+INFO:` 回包里带 `控制权=NODE|PC`，节点顺手就能把"被抢占"记进诊断计数器（只在日志/帧里排障，不上云）。

**明确砍掉（别再长回来）**：不做"未知/在线/被抢占/离线"四态、不做相机硬件自检、不做心跳帧、不做探活重传对账。
用户口径原话：**只要节点发 AT、摄像头能回，就证明在线 —— 我们只需要它在线就行了。**

## 5. 接口契约（可直接落地的协议定义）

### 5.1 LoRa 协议变更（都在 `shared/lora_protocol.h`，单一事实源）

**① 新增：车牌事件帧（事件量）**

```c
#define LORA_FRAME_PLATE        0xF1    /* 节点 -> 网关: 车牌识别结果 */

#pragma pack(push, 1)
typedef struct {
    char     plate[24];   /* UTF-8: 中文 3 字节/字, 24B 够 8 字符车牌(含中点) + null */
    uint8_t  conf;        /* 置信度 0~100 */
    uint8_t  valid;       /* 0=未识别($PLATE,-), 1=有效 */
    uint8_t  source;      /* 1=节点自动 2=软件手动 0=未知 (仅排障, 不上云) */
    uint32_t frameNo;     /* 摄像头帧号($PLATE 第 3 段, 仅排障, 不上云) */
    uint8_t  color;       /* 预留: 车牌颜色 0=未知 1=蓝 2=黄 3=绿 4=白 5=黑 (一期恒为 0, 不上报) */
    uint16_t crc16;       /* CRC16/MODBUS, 覆盖前面所有字节 */
} LoraPlate_t;            /* 34 字节 = 24+1+1+1+4+1+2 (含 1 字节预留颜色) */
#pragma pack(pop)
```

**② 修改：数据帧 `LoraNodeData_t`（状态量，v3 → v4）** —— 在 `seq` **之前**插 1 个 `CamFlags` 字节，其余字段顺序不变：

```c
typedef struct {
    /* ---- 原有字段, 一字不动 ---- */
    uint8_t  ParkStatus;  uint8_t  GeoMagnetic;  uint16_t Ultrasonic;
    uint32_t OccupiedTime; uint8_t  LED;
    uint32_t ZombieThreshold; uint16_t SensorDistanceCm;
    /* ---- v4 新增: 状态标志位 ---- */
    uint8_t  CamFlags;    /* bit0~1 = 拍照策略(0~3)
                             bit2   = 有新车牌待取(网关据此发 AT+PLATE)
                             bit3   = 摄像头在线(节点探活结果, 1=在线)
                             bit4~7 = 预留(以后再要加状态位无需改协议) */
    uint8_t  seq;
    uint16_t crc16;       /* CRC16/MODBUS, 覆盖到 crc16 之前的全部字节(含 CamFlags) */
} LoraNodeData_t;         /* v3: 18 字节 -> v4: 19 字节 */
```

> **命名说明（2026-10-09）**：字节名用 `CamFlags` 而不是笼统的 `flags` —— 因为里面 3 组位（拍照策略 / 有牌待取 / 摄像头在线）全都是**车牌子系统**的状态；同时与既有字段的 PascalCase 风格（`ParkStatus` / `ZombieThreshold`）一致。
> ⚠️ 以后若要加**跟摄像头无关**的状态位，别往 `CamFlags` 里塞（名字会跟内容不符）—— 要么给它单开一个字节（协议跟着涨 v5、双端重烧），要么接受名实不符。

**单一事实源**（已核实，无需人工同步）：网关 `Gateway/lora_protocol.h` 是薄包装 `#include <shared/lora_protocol.h>`；节点 Keil 工程 IncludePath 含 `..\..\..\shared`。

**烧录要求**：本版改了数据帧结构 → **节点与网关必须用串口线同时烧**（**不许走 OTA**，见 §3 D8 / §11）；`LORA_PROTO_VERSION` 同步提到 **4**。

### 5.2 下行命令（网关 → 节点，ASCII 行）

| 命令 | 参数 | 节点行为 | 节点回执 |
| --- | --- | --- | --- |
| `AT+CAPTURE\r\n` | 无 | 转发 `AT+RUN` 给摄像头，等 ≤2s，解析并缓存 | ACK 帧 `0xC1`，内容含 `AT+CAPTURE` |
| `AT+PLATE\r\n` | 无 | 回 `PlateCache` 里的车牌并**清「待取」旗子**；缓存为空则回 `valid=0` 的帧 | 一帧 `0xF1` |
| `AT+CapturePolicy=<0..3>\r\n` | 0~3 | 立即生效；随下个数据帧回报 | ACK 帧，内容含 `AT+CapturePolicy` |

**回执与数据的分工（沿用既有模式，不要另发明）**：

- **服务回执只表达状态**：`invoke_reply{Result, ActualValue}`（与旧 `TriggerCapture`、与阈值下发完全同构）；
- **车牌走属性异步上报**；
- 因此**没有"谁先谁后"的顺序约束**（回执不含数据，先后无所谓）；ACK 是 ASCII 行，本来也塞不下中文。

**命令名安全性检查**（网关 ACK 归属用 `strstr` 关键字包含匹配，见 `通信架构重构方案` S31/S33）：

- 新增关键字 `CAPTURE` / `PLATE` / `CapturePolicy` 与现有 `SetLed` / `ZombieThreshold` / `SensorDistance` **互不为子串**（大小写敏感）；
- ⚠️ 但要注意：`AT+CAPTURE` 与 `AT+CapturePolicy` **是靠大小写区分的**（`CAPTURE` 不匹配 `CapturePolicy`）。**这是脆弱的巧合** —— 因此立一条硬约束：**新增命令名不得包含既有命令名（大小写敏感）作为子串；`AT+CAPTURE` 与 `AT+CapturePolicy` 一律不许改成全大写写法**。

### 5.3 节点 ↔ 摄像头（**已定稿，不改**）

```
上行: $PLATE,<车牌>,<置信度0-100>,<帧号>[,img=<档位>]
下行: AT+RUN\r\n        (触发一帧, 约 1s 后回上行行; 不回 OK)
      AT+CTRL=NODE      (取回控制权; 上电默认就是 NODE)
      AT+TRIG=1         (只听触发; 上电默认就是 1)
约定: 一次触发必定得到一行 $PLATE; 车牌字段 "-" = 拍到了但没认出来
超时: 2s。同一时刻只跑一帧，不要连发
```

**节点侧必须容错的三种"意外回复"**（否则会把异常误判成"未识别"）：

| 收到 | 含义 | 节点该怎么办 |
| --- | --- | --- |
| `ERR:没有权限…` | 电脑用 `AT+CTRL=PC` 抢走了控制权 | 记为**链路被抢占**（诊断计数器 +1），不上报车牌；提示需 `AT+CTRL=NODE` |
| 非本次触发产生的 `$PLATE,…` | 摄像头被设成 `AT+TRIG=0`（连续识别）在自己发 | 丢弃（可按帧号/触发标志过滤），不当作本次结果 |
| 超时（2s 无任何行） | 链路断 / 摄像头忙 / 未就绪 | 重试（≤2 次），仍失败记为"链路异常" |

详见 `AT指令手册-节点版.md`。

**两条实现要点（最容易踩）**：

1. **时序解耦 —— 硬性要求，不是优化项**：等摄像头的那 1~2s 里，`LoRa_Task` **必须照常应答网关轮询**（数据帧内容来自缓存，与拍照无关）。
   → **已查明（2026-10-09）**：网关等回复 —— 普通命令 **3000 ms**（`app_cfg.h:23` `LORA_RESPONSE_TIMEOUT_MS`）、**PING 仅 500 ms**（`lora_handler.cpp:115` `PING_TIMEOUT_MS`）；另有"收帧中途 500 ms 无后续字节即复位"（`lora_handler.cpp:1020`）。
   → 所以：节点**毫秒级**应答时三个超时都绰绰有余；**但一旦把 `AT+RUN` 写成阻塞等待 2s，必然踩死 PING 的 500 ms** —— 这就是"必须非阻塞"的硬理由。
   → 容错余量：离线判定按**轮询轮次**计（`node_data.cpp:358` S13，连续 `NODE_MISSED_ROUNDS_MAX` 轮无响应才判离线），偶发一次应答超时只记一次 miss，**不会立刻判离线**。
2. **判新不要只靠摄像头帧号**：摄像头重启后帧号归零，建议用**节点本地计数**或 (帧号, tick) 组合。

**预算**：RAM 新增约 400B（行缓冲 128B + USART3 环形 256B + 缓存 ~40B）；Flash 新增约 1~2KB。
（`通信架构重构方案` 17.2：节点 RAM 余量约 1.76KB、ROM 余量约 24KB → 够用，编译后再核 `Firmware/Listing/firmware.map`。）

## 11. 回滚与应急

1. **回滚要成对**：车牌帧（`0xF1`）与物模型变更都是**纯加法**，可单独回滚；但**数据帧 v4 是结构性变更**，节点与网关必须**成对升级、成对回滚**。
2. **v4 只能用串口线双端同时烧，禁止走 OTA**：OTA 必然一先一后，中间窗口数据帧长度不符 → 车位数据全丢。（OTA 留给之后不改协议的版本。）
3. 三个固件的基线 bin 全部留档（S0 产物）；必要时可回退到基线版本。
4. 物模型新增属性/服务若引起 App 异常，平台侧直接删除即可，不影响固件。
5. 若 S1 发现节点资源不足或时序冲突 → **停在节点侧，不改网关**（此时原始功能完全未受影响）。

## 13. （可选 · 最后做）图片与人工复审 —— 走 LoRa 传缩略图

> **定位：可选项，非必做。** 必做项（§0 第 1~8 条）落地稳定之后，再评估本节。
> 需求：车牌置信度过低时，人工复审需要"看一眼那张图"。
> 约束（用户 2026-10-09 明确）：**图片必须走 LoRa**（现场无 WiFi / 无 USB 通路），LoRa 不是可选项。

### 13.1 核心结论：能走 LoRa，关键是**换编码**

摄像头现有 `AT+IMG` 三档发的都是 **JPEG**（94×24 那档是"放大后 JPEG" 2.5~3 KB；320×240 档 6~14 KB）。对小图而言 JPEG 的头/分块开销极不划算 ——
**改传"低位深原始位图"，数据量掉一个数量级**（94×24 = 2256 像素）：

| 编码形式 | 字节数 | LoRa 传输耗时（链路 ≈ 1 KB/s） | base64 后（给云端属性用） |
| --- | --- | --- | --- |
| **二值图 1bpp** | **282 B** | **约 0.4 s** | 376 字符 |
| 4 级灰度 2bpp | 564 B | 约 0.7 s | 752 |
| 8 级灰度 3bpp | 846 B | 约 1.0 s | 1128 |
| 16 级灰度 4bpp | 1,128 B | 约 1.3 s | 1504 |
| 8bit 灰度 | 2,256 B | 约 2.5 s | 3008 |
| 二值 + RLE（背景成片，估计） | ~100~200 B | 约 0.2 s | ~140~270 |
| ~~现有 `AT+IMG=3`（放大后 JPEG）~~ | ~~2.5~3 KB~~ | ~~3~4 s~~ | ~~3.3~4 KB~~ |

**链路吞吐口径**：瓶颈是**节点↔LoRa 模块的 UART 波特率**，当前为 **9600**（节点侧 `bsp_lora.h` 固定 9600；网关侧 `hw_cfg.h` 按平台二选一：`#if defined(ESP32)` → 硬串 **115200**、`#else`（ESP8266）→ 软串 **9600**，当前是 ESP8266 软串即 9600）→ 有效约 **1 KB/s**。

### 13.2 分级传输（默认很便宜）

| 级别 | 内容 | 大小 / 耗时 | 什么时候传 |
| --- | --- | --- | --- |
| **L1（默认）** | 二值 94×24 | 282 B / 0.4 s | 每次低置信度自动带一张 |
| **L2（按需）** | 4 级或 8 级灰度 94×24 | 564~846 B / 0.7~1.0 s | App 上人工觉得看不清，点"请求增强" |
| **L3（可选）** | 160×120 二值（带上下文，能看框套得准不准） | 2.4 KB / 约 2.5 s（12 包） | 需要判断"框准不准"时 |

### 13.3 两个必须的改动

**① 摄像头固件加"位图档位"**（例：`AT+IMG=4` 二值、`=5` 灰度）

- 数据源**现成**：推理输入张量（int8，`main.cpp` 手上就有）或 `g_crop_rgb`；只是"比阈值"，**零额外计算**（阈值可用 Otsu）。
- ⚠ **前提修正**：这意味着"**摄像头一行不改**"这个假设**在本节不再成立**（必做项 §0 第 1~8 条里仍然成立）。改动很小：新增一个发图分支 + 一条档位。
- 通道复用：`$IMG,<len>` + 二进制 + CRC32 是现成的，**原始位图与 JPEG 走同一条路** ✓（BY串口助手也能直接收）。

**② 云端用一个 string 属性承载缩略图**（base64）

- 二值 282 B → base64 **376 字符** → **一个属性搞定**，**不需要**对象存储 / 文件通道 / URL，省掉一整套改造。
- ✅ **网关侧容量已查明**：上行批量上报用 `StaticJsonDocument<2048>`（`onenet_handler.cpp:183`，注"与 MQTT 发送缓冲 2048B 对齐"）；现状 8 个只读属性 + identity 仅约 300 字节 → **base64 376（二值）/ 752（4 级灰度）都放得下** ✓。

### 13.4 压缩之后还剩什么约束

| 约束 | L1 二值 282 B | L2 灰度 846 B | L3 160×120 二值 2.4 KB |
| --- | --- | --- | --- |
| 节点 RAM（余量 ~1.76 KB） | ✓ 可整帧缓存 + 重传 | ✓ | ✗ 只能**流式转发**（丢包整张重来） |
| 模块单包上限（约 200 B/包） | 2 包，不需要协议 | 5 包，需简单序号 | 12 包，需**分包重组** |
| 半双工中断 | 0.4 s（无感） | 1.0 s（可接受） | 2.5 s（可接受，但应告知） |
| 云端通道 | 属性 ✓ | 属性 ✓ | 属性放不下 → 需分片或文件通道 |
| 触发频率 | 低频（仅低置信度） ✓ | 同 | 更少 |

### 13.5 App 侧（简单）

base64 → 94×24 位图 → **CustomPainter 画点阵**（每 bit 一个方块，放大 4~8 倍）。不构造 PNG、不依赖图片库。
放在"低置信度复审"弹层里，与车牌、置信度并排显示。
**人工复审看 94×24 是够的**：我们的训练样本就是 94×24，历史缩略图肉眼能读出 7~8 个字符。

### 13.6 可选提速（二期再议）

节点↔模块 UART 从 9600 提到 **115200**（模块支持 `AT+BAUD=115200`）→ 吞吐 ×12，图片几乎无感。
⚠ 网关侧 LoRa 走 **SoftwareSerial**，能否同步提速需单独评估（风险项，先不动）。
