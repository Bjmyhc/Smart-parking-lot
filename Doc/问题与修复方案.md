## 一、OTA 数据包为何在约 501～517ms 被判定超时

### 1. 当前源码不存在“500ms OTA 数据包 ACK 超时”

因此，**使用当前源码正常构建出的网关固件，不可能由这个分支在 501～517ms 判定超时**。

如果现场日志明确显示 OTA 数据包在约 501～517ms进入“等待ACK超时”分支，应优先核对：

- `OTA_WAIT_ACK`进入时间。

- APP区擦除起止时间。
- Flash写入起止时间。
- 节点发送ACK时间。
- 网关 `ota_feedByte()` 收到ACK时间。

最小修正不是盲目继续放大当前2000ms，而是先确认现场二进制是否确实使用500ms。若现场确实是旧版，至少应为首包擦除保留足够裕量，当前源码的2000ms比500ms合理。

## 二、网关长段乱码的代码风险

### 1. LittleFS证书字段未保证 NUL 终止

**高可信代码风险，能够解释长距离垃圾输出。**

持久化结构：

- `g:\All_Project\Trae_Project\Smart-Paring-Iot\Gateway\node_data.cpp:10-17`

```cpp
char productKey[12];
char deviceName[33];
```

加载代码：

- `node_data.cpp:67-121`

从文件读取完整结构后直接复制：

```cpp
memcpy(nodes[slot].productKey, pc.productKey, ...);
memcpy(nodes[slot].deviceName, pc.deviceName, ...);
```

随后直接以 `%s` 打印：

- `node_data.cpp:98-99`

```cpp
DBG_PRINTF("[LFS] 加载证书: 节点%d (%s/%s)\n",
           pc.nodeId, pc.productKey, pc.deviceName);
```

这里没有：

- 强制 `productKey[11] = '\0'`。
- 强制 `deviceName[32] = '\0'`。
- 打印前ASCII/可见字符校验。
- 对文件记录内容做结构级校验。

若 `/certs.dat` 损坏、内容来自不兼容版本或字段恰好没有NUL，`%s` 会继续读取结构之后的栈内存，直到偶然遇到 `\0`，可表现为长段乱码。

当前文件有魔数：

- `node_data.cpp:19`
- `CERTS_MAGIC = 0xA6`

每条记录也验证了读取长度：

- `node_data.cpp:81-83`

这能排除部分旧格式和截断文件，但不能保证字符串内部一定有NUL，也不能抵御内容损坏后魔数仍碰巧有效。

### 2. 证书变更日志中的旧字符串也可能越界打印

证书变更时复制整个旧数组：

- `node_data.cpp:209-216`

```cpp
char oldPk[sizeof(nd.productKey)];
char oldDn[sizeof(nd.deviceName)];
memcpy(oldPk, nd.productKey, sizeof(oldPk));
memcpy(oldDn, nd.deviceName, sizeof(oldDn));
```

随后直接 `%s`：

- `node_data.cpp:245-249`

如果旧数据由损坏的持久化文件加载且没有NUL，`oldPk`、`oldDn`也没有额外补终止符，日志会越过本地数组读取。

这是另一处可产生“长段”垃圾的明确代码条件。

### 3. 普通 ACK 字符串会原样打印污染字节

普通 ACK 接收会在结尾补NUL：

- `g:\All_Project\Trae_Project\Smart-Paring-Iot\Gateway\lora_handler.cpp:749-760`

所以它通常不会无限越界。

但收到的内容会被直接按字符串打印，且代码允许保留ACK中已经接收的异常字节。串口噪声、帧错位或DRSSI残留可能出现在字符串中，从而产生局部乱码。

这更适合解释“某一小段ACK内容异常”，通常不足以单独解释很长的无边界垃圾输出。

### 4. `snprintf` 返回长度误用

存在多处结构性风险。

#### 累加拼接长度

`lora_handler.cpp` 中有：

```cpp
enqItemsLen += snprintf(enqItems + enqItemsLen,
                        sizeof(enqItems) - enqItemsLen, ...);
```

位置约为：

- `g:\All_Project\Trae_Project\Smart-Paring-Iot\Gateway\lora_handler.cpp:231-257`

`snprintf` 截断时返回“本应写入的长度”，可能大于剩余空间。继续累加后：

- 指针可能越过数组。
- 剩余长度计算可能下溢。
- 后续写入可能破坏内存。

当前仅拼接两个受限的短文本，按现有输入通常达不到80字节，因此这是**潜在缺陷，不是已确认的现场根因**。

#### 将截断后的返回值直接作为发送长度

位置包括：

- `g:\All_Project\Trae_Project\Smart-Paring-Iot\Gateway\lora_handler.cpp:417-430`
- `sendAT()`
- `g:\All_Project\Trae_Project\Smart-Paring-Iot\Gateway\ota_handler.cpp:494-500`
- OTA触发命令

模式为：

```cpp
int n = snprintf(buf, sizeof(buf), ...);
if (n > 0)
    send(..., buf, n);
```

若 `n >= sizeof(buf)`，缓冲区实际只包含截断内容，却会按更大的 `n` 从栈后继续读取并发送。

当前前缀和版本字段均受限，静态分析不能证明现场已发生截断；仍建议统一检查：

```cpp
if (n > 0 && (size_t)n < sizeof(buf))
```

**已确认：**

默认架构不是多个线程并发调用调试串口，调试宏直接映射到 `DEBUG_SERIAL.printf/print/println`，未发现自定义共享printf缓冲区。

**未找到证据证明这种重入会把随机二进制写入调试串口。**它可以解释日志交错，但不能作为长段乱码的首要根因。

### 6. 未发现的问题

本次检索未发现：

- OTA的133字节二进制包直接传给调试 `%s`。
- 明确的 `printf` 参数数量或类型不匹配。

### 7. 乱码问题优先修正顺序

1. LittleFS加载后立即强制字段末尾为NUL，并验证可见ASCII。
2. `oldPk`、`oldDn`额外预留一个字节或显式补NUL。

## 排查结论与修正方案

### 1. OTA 重启导致停车状态丢失

### 2. OTA ACK 与“500ms超时”

这里需要纠正：**501/517ms并不是OTA等待ACK超时**。

- OTA包ACK超时实际为2000ms，定义在[lora_protocol.h](file:///g:/All_Project/Trae_Project/Smart-Paring-Iot/Gateway/lora_protocol.h)。
- 501ms来自[lora_handler.cpp](file:///g:/All_Project/Trae_Project/Smart-Paring-Iot/Gateway/lora_handler.cpp)中的普通帧接收状态机，日志显示其卡在`RX_FRAME_ACK`。
- 高概率原因是BootLoader返回裸`0x03` ACK后，LoRa模块追加的DRSSI字节恰好为`0xC1`等合法帧头。网关因此误入普通ACK帧解析，后续OTA ACK被当作字符串内容吞掉，最终在真正的2000ms OTA超时后重发。

**建议方案：**

1. OTA活动期间收到裸ACK/NAK/CAN后，将紧随其后的一个字节明确作为DRSSI消费，不再参与帧头识别。
2. 增加受限原始字节诊断和计数，确认现场是否确实出现类似`03 C1`的序列；限制输出次数，避免大量日志影响时序。
3. 保持当前2000ms超时，不通过继续增大超时掩盖解析错误。
4. 完整OTA验证时检查：
   - 不再出现`RX_FRAME_ACK, 501ms`；
   - 包重发次数明显下降；
   - 普通DATA/CERT/ACK帧不受影响。

这是本轮最重要的可靠性修复。

### 3. 两处严重乱码

目前无法仅靠现有日志唯一确认乱码源头，但已找到两类确定风险：

- [node_data.cpp](file:///g:/All_Project/Trae_Project/Smart-Paring-Iot/Gateway/node_data.cpp)中的LittleFS证书字符串加载后没有强制补`\0`，使用`%s`打印时可能越界读取。
- 证书旧值缓冲区和协议字段长度不一致，相关日志可能继续读取字段外内存。
- 暂未发现OTA二进制数据被直接用`%s`输出，也没有足够证据认定为并发`printf`或终端编码问题。

**建议分两步处理：**

1. 先做确定性安全修复：
   - 所有持久化证书字段加载后强制补`\0`；

2. 增加一次受限十六进制诊断，区分：
   - LoRa串口收到的原始数据异常；
   - 调试串口发送损坏；
