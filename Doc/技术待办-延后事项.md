## 待办 1：OTA 升级中断电自愈机制

**状态**：**核心能力已落地**，本项降级为"增强项"（原"暂缓"判断基于落地前的旧认知，见下方现状核实）
**优先级**：低（原为中）
**影响范围**：节点 BootLoader + 网关 LoRa OTA + OneNET 任务层

> **现状核实（2026-09-10）**：经代码核对，**"升级中断电自愈"已实现**，只是走的是另一套机制——节点来电滞留 Boot 时响应 `AT+PING` 回 `PONG,BOOT`，网关据此经 `ota_autoDispatch()` 自动续传（固件文件保留至 `PONG,APP`，自愈预算 3 次）：
> - 节点侧：Boot 在 OTA 等待期回 `PONG,BOOT`（[main.c#L638-640](Node/BootLoader/User/main.c)）；`APP_PARTIAL` 标志跨断电持久化（[main.c#L684-687](Node/BootLoader/User/main.c)）
> - 网关侧：`PONG,BOOT` → 更新节点态 + `ota_autoDispatch` 自动重发（[lora_handler.cpp#L536-560](Gateway/lora_handler.cpp)、[ota_handler.cpp#L416-441](Gateway/ota_handler.cpp)）
> - 预算/回退：`OTA_SELF_HEAL_MAX_RETRY=3`，超限置 `bootPending` 等平台/人工显式触发（S27）
>
> 因此本文前半段"永久卡死/只能人工 JLink/双向死锁"等描述均为**落地前的历史状态**；本节保留的 `BOOT_READY 0x42` + `OTA_SUSPEND` 方案是该闭环的**更优实现**（主动上报发现更快、SUSPEND 态避免误报 `FAILED`），作为增强项而非缺口。

### 背景问题

路边智能停车场节点设备，OTA 升级过程中若节点突然断电，早期设计下会导致**节点永久卡死，无法自愈，只能人工 JLink 烧录**（该历史缺陷已由两阶段提交、可救活 Boot 与 `PONG,BOOT` 自动续传闭环消除，见上文现状核实）。原设想此场景比"网关不知道节点回来"更严重——节点会自杀式死锁。

### 死锁的精确机制

**触发链路**（正常 OTA 时序）：

1. 网关发 OTA 触发命令给节点 App
2. 节点 App 收到 → 写 `OTA_FLAG_GO`（0xA5A5A5A5）到 Flash 标志页 → `NVIC_SystemReset()` 软复位
3. 节点重启 → BootLoader 读到 GO 标志 → 直接进 `OTA_Process` 等 SOH 包
4. 网关发 SOH + 数据包 → BootLoader 接收写 Flash → 完成

**断电再来电的灾难链路**（注：下述"擦除→死循环"为重进升级模式的最坏路径；两阶段提交与可救活 Boot 已落地，实际影响面已收窄，见文末"现状修订"）：

```
节点升级中断电(App 或 BootLoader 跑到一半)
  ↓ 来电, BootLoader 重新跑 main
  ↓ 读 Flash: OTA_FLAG_GO 还在(Flash 非易失, 写了就在)
  ↓ 直接进 OTA_Process
  ↓ ① 首包阶段先等固件头校验(两阶段提交), 通过后才擦 App 区
  ↓ ② 等 SOH 包(首包超时 / 已擦除后按总超时 180s)
  ↓ 网关已经 FAILED 放弃, 不发 SOH
  ↓ 等超时 → 失败回退
  ↓ 落回可救活 while(1)(L1044-1066): 持续监听按键/AT+OTA
  ↓ 无人工干预时不会自动恢复, 需人工按键或重新下发 OTA 命令
```

**现状修订（2026-09-10）**：早期本段曾描述为"先擦 App → 裸 `while(1)` 死循环 → 只能人工 JLink 烧录"。经代码核对，**两阶段提交**已实现（验证固件头后才擦除，[main.c](Node/BootLoader/User/main.c#L695-L697)），**失败 `while(1)` 已改为持续监听按键/`AT+OTA` 可救活**（[main.c](Node/BootLoader/User/main.c#L1044-L1066)）。因此：
- 首包超时/网关放弃时**旧 APP 完好**，可瞬时回退；
- 极端（已擦除且升级中断）情况下节点**不再永久失聪**：来电回 Boot 后响应 `PONG,BOOT`，网关 `ota_autoDispatch()` 自动续传，**无需人工介入**；
- **剩余差异（增强空间）**：网关靠 PING 轮询发现节点回来（受探测退避 2s→64s 影响，恢复有秒级延迟）；`BOOT_READY` 主动上报 + `OTA_SUSPEND` 挂起可实现"秒级发现 + 失败不上报"，故本待办降级为增强项保留。

**（早期误判）网关为什么探测不到节点回来**：

早期设计中 BootLoader 只等 SOH 包、**不响应 PING**，形成"节点等 SOH、网关等 PONG"的双向死锁。**该问题已消除**：当前 BootLoader 在 OTA 等待期会响应 `AT+PING` 并回 `PONG,BOOT`（[main.c#L638-640](Node/BootLoader/User/main.c)），网关识别节点处于 Boot 后即自动续传（[lora_handler.cpp#L536-560](Gateway/lora_handler.cpp)）。

### 解法设计：BootLoader 主动报告 + 网关挂起重试（原设计稿，已被落地机制替代，仅作增强参考）

困境根源是 BootLoader **被动等 SOH**，不主动通知网关。打通"节点→网关"的主动报告链路即可。

#### ① BootLoader 来电主动发 BOOT_READY

在 `OTA_Process` 开头（[main.c#L402](Node/BootLoader/User/main.c)），先发"我回来了"信号给网关，且等 SOH 期间周期性重发：

```c
static void OTA_Process(void) {
    /* 来电主动报告: 告诉网关我 BootLoader 在等 SOH, 请重新发包 */
    for (int i = 0; i < 3; i++) {          /* 连发3次提高可靠性 */
        OTA_SendResp(0x42);                 /* 'B' = BOOT_READY */
        Boot_Delay(50);
    }
    USART1_PutString("[BOOT] 已发 BOOT_READY, 等待 SOH...\r\n");

    // ... 原有 OTA_Process 逻辑
    // 等 SOH 的 120s 里, 每 10s 周期性重发 BOOT_READY
}
```

#### ② 网关挂起重试态

[ota_handler.cpp](Gateway/ota_handler.cpp) 新增 `OTA_SUSPEND` 态：
- 节点断电重试耗尽 → 不 FAILED，进 `SUSPEND`
- **不删固件**（保留 LittleFS 文件）
- SUSPEND 态监听 LoRa 是否收到 'B'(BOOT_READY)
- 收到 BOOT_READY → 节点回来了 → 重新 `ota_startFromFile`（固件还在，跳过下载）
- 挂起超时（如 10 分钟）才真正 FAILED

#### ③ OneNET 任务层不急着标失败

网关挂起期间，**不上报 status=5**（让 OneNET 任务停在 2/3，APP 显示"升级中"）。等挂起超时或成功才上报。

### 协同效果

```
节点断电 → 网关重试耗尽 → 进 SUSPEND(不删固件, 不上报失败)
节点来电 → BootLoader 发 BOOT_READY ×3
网关收到 BOOT_READY → 重新 ota_startFromFile → 发 SOH
节点收到 SOH → 接收固件 → CRC 校验 → 跳 App → 完成
网关上报 status=4 → APP 显示成功
```

### 暂缓原因

1. **比赛产品**：路边节点断电场景在实际比赛中罕见（设备一旦部署不会随便断电）
2. **改动面中等**：涉及 BootLoader + 网关 + 协议新字节，需要端到端联调
3. **能力已闭环**：两阶段提交 + 可救活 Boot + `PONG,BOOT` 自动续传已覆盖断电自愈场景（见上方现状核实），本方案仅剩"主动上报发现更快、`OTA_SUSPEND` 不误报失败"的增强收益，投入产出比低，故不排期

### 实施建议（若未来要做）

1. 先在 BootLoader 加 BOOT_READY 发送（最简单，节点侧自愈基础）
2. 再在网关加 SUSPEND 态识别 BOOT_READY
3. 最后打通 OneNET 任务层（挂起不上报失败）
4. 测试：升级中拔节点电源 → 等 10s 重新上电 → 验证自动续传

## 待办 2：APP 显示 OTA 具体失败原因

**状态**：暂缓（可查网关串口日志，运维侧已可见）
**优先级**：低
**影响范围**：网关物模型 + APP OTA UI

### 背景问题

网关 OTA 失败上报已修正为正确的 step 值（202/203/204，见 onenet_ota.cpp otaReportStatus），但 APP 端只能显示"升级失败"，显示不出具体原因（下载失败/无在线节点/校验失败/LoRa 分发失败）。

### 根因

- OneNET 的 check 接口（`/fuse-ota/{proid}/{devname}/{tid}/check`）**只返回 status（4成功/5失败），不返回 step 细分值**
- 网关上报的 step=202/203/204 被 OneNET 内部归类成 status=5，具体值不暴露
- [api_service.dart#L546-577](User/lib/core/services/api_service.dart) 的 `getOtaTaskStatus` 只解析 `status` 字段
- 所以 APP 拿不到"为什么失败"

### 信息可见性现状

| 看的地方 | 能看到什么 |
|---------|-----------|
| 网关 debug 串口 | ✅ 具体原因（"无在线节点, 上报失败"） |
| OneNET 控制台 | ✅ 任务 status=5（失败），但无 step 细分 |
| APP | ❌ 只能显示"升级失败" |

### 方案设计：网关物模型属性曲线救国

给网关产品加一个 `OtaFailReason` 物模型属性（int 枚举），网关上报失败时同时写该属性，APP 查询时解析显示。

**属性枚举值**：

| 值 | 含义 |
|----|------|
| 0 | 无/成功 |
| 1 | 下载固件失败（对应 step=203） |
| 2 | 无在线节点（对应 step=202） |
| 3 | 固件校验失败（对应 step=204） |
| 4 | LoRa 分发失败（对应 step=202） |

**网关端**：在 onenet_ota.cpp 的 4 处 `otaReportStatus` 失败上报后，加一行 `otaReportFailReason(n)` 写物模型属性（类似 ota_progressSet 写 OtaProgress）。

**APP 端**：`getGatewayOtaState()` 返回的属性里增加 `OtaFailReason` 解析；固件升级页 status==5 时显示"升级失败：{具体原因}"。

### 改动点清单

| 文件 | 改动 | 复杂度 |
|------|------|--------|
| OneNET 控制台 | 网关产品物模型加 `OtaFailReason` int 属性 | 低（配置） |
| [Gateway/onenet_ota.cpp](Gateway/onenet_ota.cpp) | 4 处失败上报后加写属性 + 新增 otaReportFailReason 函数 | 低（~15 行） |
| [User/lib/core/services/api_service.dart](User/lib/core/services/api_service.dart) | getGatewayOtaState 解析 OtaFailReason 字段 | 极低（~3 行） |
| [User/lib/features/profile/.../firmware_upgrade_page.dart](User/lib/features/profile/presentation/pages/firmware_upgrade_page.dart) | status==5 时显示具体失败原因 | 低（~5 行） |

### 暂缓原因

1. **运维侧已可见**：网关 debug 串口日志已打印具体原因（"无在线节点, 上报失败"等），出问题查日志即可定位
2. **低频场景**：OTA 失败本身不常发生，APP 端显示具体原因的价值有限
3. **改动跨端**：要动 OneNET 物模型 + 网关 + APP 三层，虽然每层改动小但需端到端联调

### 实施建议

1. 先在 OneNET 给网关产品加 `OtaFailReason` int 属性
2. 网关新增 `otaReportFailReason(int reason)` 函数（参考 ota_progressSet 写 OtaProgress 的方式）
3. 4 处 otaReportStatus 失败分支后调用 otaReportFailReason
4. APP getGatewayOtaState 解析 + 固件升级页显示
