# ESP8266 网关开发计划 (v2)

> 基于参考项目"超子说物联网"工业级 LoRa 网关方案重构，整合其成熟设计。

## 一、项目背景与架构

### 1.1 项目背景

智能停车场系统从"单节点直连"架构升级为"多节点汇聚"架构。

```
STM32节点1 (传感器+LoRa, 地址0x0001) ──┐
STM32节点2 (传感器+LoRa, 地址0x0002) ──┼──LoRa定点──→ ESP8266网关 (地址0x0000)
STM32节点N (传感器+LoRa, 地址0x000N) ──┘                 ├──WiFi──→ OneNET (网关+子设备模式)
                                                         └──SoftwareSerial(9600) 接LoRa
```

ESP8266 作为网关主控，承担：LoRa 数据接收、子设备管理、OneNET 子设备代理上线/上报、下行命令转发。

### 1.2 LoRa 通信模式决策（2026-08-08 确定）

| 方案 | 说明 | 健壮性 | 性能 | 扩展性 | 最终选择 |
|---|---|---|---|---|---|
| 透传+ASCII CSV (旧) | LoRa 透传，节点主动发 `$N,1,2,3...` 字符串 | 无碰撞防护，节点数>2 丢包 | ASCII 40字节/帧，占空比高 | 多节点必冲突 | 否 |
| **定点传输+二进制+网关轮询（新，方案A）** | LoRa 定点 [AddrH][AddrL][CH] 地址区分，帧头字节 `0xA1/0xB1` + `#pragma pack(1)` 结构体 memcpy，网关轮流 AT+DATAx 点名回数据 | **零碰撞**（同一时刻只有被点名节点回数据）| 二进制 11 字节/帧，空中用时<1/4 | 50+ 节点也可线性扩展 | **已选** |

## 二、硬件设计

### 2.1 开发板选型

| 方案 | 优点 | 缺点 | 推荐 |
|---|---|---|---|
| NodeMCU 1.0 (ESP-12E) | GPIO多、USB供电、便宜 | 体积稍大 | **首选** |
| Wemos D1 mini | 体积小 | GPIO较少 | 备选 |

> 未来可无痛迁移到 ESP32（3个硬件串口，双核240MHz，520KB RAM），核心代码 90%+ 不用改。

### 2.2 引脚分配

```
ESP8266 (NodeMCU)     LoRa定点模块
D2 (GPIO4)        <-- TX        (LoRa发送端→ESP接收)
D1 (GPIO5)        --> RX        (ESP发送端→LoRa接收)
3.3V              --> VCC
GND               --> GND

USB                --> 调试串口 (Serial, 115200)
```

- LoRa 用 SoftwareSerial (9600bps)，不占用 USB 调试串口
- LoRa 模块需配置为**定点传输模式**（非透传）
- 如需扩展（如本地OLED），可用 D3/D4/D5/D6/D7

### 2.3 LoRa 模块配置 (2026-08-09 实测: DX-LR22-433T22D)

实际使用的 LoRa 模块为 **DX-LR22-433T22D**（深圳大夏龙雀），通过 **AT 指令**配置
（注意: 非参考项目的 0xC0 寄存器命令, 指令体系不同）。

公共配置（网关+节点模块都要执行, USB-TTL 9600 连接, 每条指令加 \r\n）:

| 指令 | 值 | 说明 |
|---|---|---|
| `AT+MODE1` | 定点传输 | 0=透明, 1=定点, 2=广播 |
| `AT+LEVEL6` | 空中速率 37500bps | 接近参考项目 38.4K |
| `AT+CHANNEL00` | 信道 0 = 433.15MHz | 出厂默认 |
| `AT+BAUD3` | 串口 9600 | 出厂默认 |
| `AT+OPENKEY1` | 密钥开 | 出厂默认 |
| `AT+KEY12345` | 密钥 12345 | 出厂默认, 两端一致即可 |
| `AT+RESET` | 重启生效 | 设置完必须重启 |

地址（各模块不同）:

| 模块 | 指令 | 地址 |
|---|---|---|
| 网关 | `AT+MAC00,00` | 0x0000 |
| 节点1 | `AT+MAC00,01` | 0x0001 |
| 节点2 | `AT+MAC00,02` | 0x0002 |

> ?? **DX-LR22 信道编号与参考项目 E19 不同**: DX-LR22 的 `0x17`=468.15MHz,
> `0x00` 才是 433.15MHz。代码 `LORA_CHANNEL` 已同步改为 `0x00`。
> 定点帧格式 `[AddrH][AddrL][CH]+数据` 与代码发送逻辑一致, 无需改动。
> 必改的只有 `AT+MODE1` + `AT+MAC`, 其他保持出厂默认即可。

### 2.4 电源

- USB 供电 (5V → 板载3.3V LDO → ESP8266)
- LoRa 模块从 NodeMCU 3.3V 取电
- 注意: LoRa 发射时瞬时电流较大，若不稳需独立供电

## 三、软件架构

### 3.1 核心设计决策（借鉴参考项目）

| 设计点 | 参考项目方案 | 移植到 ESP8266 | 优势 |
|---|---|---|---|
| **LoRa 传输模式** | 定点传输 | 定点传输 | 可指定目标地址，多节点不冲突 |
| **数据帧区分** | 帧头字节(0xA1/0xB1/0xC1...) | 同样用帧头字节 | 比ASCII命令高效，解析快 |
| **数据序列化** | 结构体直接 memcpy | 结构体 memcpy | 零拷贝，比JSON/字符串高效 |
| **网关轮询** | 27s查上线/10s查数据 | 同样轮询 | 避免多节点同时发送碰撞 |
| **事件驱动** | 被动事件+主动事件 | Arduino loop() 内分时处理 | 非阻塞，响应快 |
| **LBT 防碰撞** | LoRa 模块硬件 LBT | 同样使能 LBT | 发前监听，减少空中碰撞 |
| **OTA 分级分发** | 云→网关Flash→LoRa→子设备 | 规划中（LittleFS 替代 W25Qxx） | 子设备可远程升级 |
| **OneNET 网关模式** | 阿里云网关+子设备 | OneNET 网关+子设备 | 每节点独立设备，扩展性好 |
| **WiFi 配网** | 微信 SmartConfig | **AP+Web 网页配网** | 成功率99%+，不依赖微信，任意手机浏览器 |
| **事件标志位** | 32位整数位操作 | 同样用 32 位标志位 | 位操作高效，O(1) 判断 |
| **心跳掉线检测** | PING_SENT 标志位 | 同样用标志位 | 纯标志位，不需时间差计算 |
| **CONNACK 错误处理** | 6种错误码分别处理 | 同样处理 | 连接失败时打印具体原因 |
| **OTA 完整流程** | 云→Flash→LoRa→子设备 | 云→LittleFS→LoRa→子设备 | 子设备可远程升级 |

```
  ├── registerNode()              注册新节点

onenet_handler.h/.cpp    OneNET 通信层(借鉴 wifi.c/mqtt.c)
  ├── onenet_init()               初始化MQTT客户端
  ├── onenet_connect()            网关连接OneNET+订阅
  ├── onenet_uploadAll()          代子设备上线/下线/批量上报
  ├── onenet_loop()               MQTT保活
  ├── onenet_replySet()           回复属性设置

```

### 3.3 数据流

```
上行 (节点 → 云):
  1. 网关定时轮询: lora_sendCommand(AT+DATA1) → LoRa定点发给节点1
  2. 节点收到查询 → 采集传感器 → LoRa定点回传 [0xB1 + NodeData结构体]
  3. ESP8266 lora_tick() 接收 → lora_handleFrame() 按帧头0xB1处理
  4. updateNodeFromRaw() 更新缓存 → onenet_uploadAll() 代子设备上报OneNET

下行 (云 → 节点):
  1. OneNET → MQTT PUBLISH → mqtt_callback() 收到下行命令
  2. Topic匹配: thing/sub/property/set → identity匹配目标子设备
  3. 解析属性值(如 LedEnable=false)
  4. lora_sendControl(AT+LedEnable=0) → LoRa定点发给目标节点
  5. 节点执行 → LoRa回传 [0xC1 + 命令确认]
  6. 网关收到0xC1 → 上报确认 → onenet_replySet() 回复OneNET

子设备上线流程(借鉴参考项目):
  1. 网关轮询: lora_sendCommand(AT+CER1) → 查询节点1证书
  2. 节点回传 [0xA1 + NodeCert结构体] (ProductKey/DeviceName/AccessKey)
  3. 网关代子设备上线OneNET (thing/sub/login, 无需签名)
  4. OneNET返回 code:200 → 子设备上线成功 → 立即代上报
```

### 3.4 事件驱动时序 (借鉴参考项目 ActiveEvent)

```
每轮 loop() 执行:
  ├── lora_tick()              → 每次循环都检查(非阻塞)
  ├── onenet_loop()            → 每次循环都检查(非阻塞)
  └── activeEvent()            → 定时触发
        ├── 每27s: 轮询所有未上线子设备(发AT+CER1/2/3...)
        ├── 每10s: 轮询所有已上线子设备数据(发AT+DATA1/2/3...)
        └── 每60s: MQTT PINGREQ 心跳 (标志位检测掉线)
```

### 3.5 系统事件标志位设计(借鉴参考项目 main.h)

借鉴参考项目的 32 位标志位设计，O(1) 判断事件状态：

```c
// 系统事件 (高16位)
#define CONNECT_EVENT      0x80000000  // 网关连上MQTT服务器
#define CONNECT_PACK       0x40000000  // MQTT CONNECT报文成功(CONNACK收到)
#define PING_SENT          0x20000000  // PING已发送，等待PINGRESP
#define OTA_EVENT          0x10000000  // OTA升级进行中
#define CONFIG_PORTAL      0x08000000  // AP配网模式启动

// 子设备在线事件 (低16位) 每位对应一个节点
#define NODE1_ONLINE       0x00000001  // 节点1在线
#define NODE2_ONLINE       0x00000002  // 节点2在线
#define NODE3_ONLINE       0x00000004  // 节点3在线
// ... NODE_N_ONLINE = (1 << (N-1)), 最大16个节点
uint32_t sysEventFlag = 0;
```

### 3.6 PING 心跳掉线检测(借鉴参考项目，纯标志位方案)

比之前 `LINK_DEAD_TIMEOUT_MS` 时间差计算更简洁：

```
每60s:
  if (PING_SENT 已置位)
      → 上次 PING 没收到 PINGRESP → MQTT掉线 → 重连
  else
      → 发送 PINGREQ → 置位 PING_SENT

收到 PINGRESP:
  → 清除 PING_SENT
```

不需要 `lastRxTick` 时间差计算，纯标志位判断，逻辑清晰。

### 3.7 CONNACK 错误码处理(借鉴参考项目 wifi.c)

PubSubClient 的 `connect()` 返回 false 时，参考以下错误码打印具体原因：

| code | 含义 | 处理 |
|---|---|---|
| 0 | 成功 | 订阅Topic + 启动轮询 |
| 1 | 协议版本不支持 | 打印错误，重连 |
| 2 | 客户端标识符不合格 | 打印错误，重连 |
| 3 | 服务端不可用 | 打印错误，重连 |
| 4 | 用户名密码无效 | 打印错误，检查Token |
| 5 | 未授权 | 打印错误，检查Token |

### 3.8 AP+Web 配网设计 (替代参考项目 SmartConfig)

```
首次启动 / 长按5秒:
  1. ESP8266 切换到 AP 模式: WiFi.softAP("ParkingGateway_Config")
  2. 启动 Web 服务器: 192.168.4.1
  3. 手机连接热点 → 浏览器访问 192.168.4.1
  4. 网页显示: 扫描到的WiFi列表(SSID+信号强度) + 密码输入框
  5. 用户选择WiFi + 输入密码 → 提交
  6. ESP8266 保存到 LittleFS → 重启 → STA模式连接WiFi
  7. 连接成功: 正常运行; 连接失败: 重新进入配网模式
```

优势对比参考项目的 SmartConfig：
- 成功率 99%+（TCP 直连 vs UDP 广播）
- 不依赖微信（任意手机浏览器）
- 可显示 WiFi 列表和信号强度
- 可扩展状态页面（查看节点在线/MQTT状态）

## 四、通信协议

### 4.1 LoRa 定点传输帧格式

定点模式下，每帧前 3 字节为地址头：

```
[目标地址高][目标地址低][目标信道] + [数据内容]
```

### 4.2 网关 → 节点：命令帧 (ASCII)

| 命令 | 帧格式 | 说明 |
|---|---|---|
| 查询证书 | `[AddrH][AddrL][CH]AT+CER1\r\n` | 查询节点1的OneNET证书 |
| 查询数据 | `[AddrH][AddrL][CH]AT+DATA1\r\n` | 查询节点1的传感器数据 |
| 设置开关 | `[AddrH][AddrL][CH]AT+LedEnable=0\r\n` | 设置节点1的LED使能 |
| OTA版本 | `[AddrH][AddrL][CH]AT+VER1=xxx\x00[sizeH][sizeL]` | OTA完成通知 |

### 4.3 节点 → 网关：数据帧 (二进制帧头)

| 帧头 | 数据内容 | 说明 |
|---|---|---|
| `0xA1` | NodeCert 结构体 | 子设备1证书信息 |
| `0xA2` | NodeCert 结构体 | 子设备2证书信息 |
| `0xA_N` | NodeCert 结构体 | 子设备N证书信息 |
| `0xB1` | NodeData 结构体 | 子设备1传感器数据 |
| `0xB2` | NodeData 结构体 | 子设备2传感器数据 |
| `0xB_N` | NodeData 结构体 | 子设备N传感器数据 |
| `0xC1` | 4字节开关状态 | 子设备1开关回复 |
| `0xD1` | 无附加数据 | 子设备1 OTA接收成功 |
| `0xE1` | 无附加数据 | 子设备1 OTA要求重发 |

> **设计要点**：帧头字节直接区分数据类型，比 ASCII 命令解析快且不会歧义。结构体直接 memcpy 传输，零拷贝。

### 4.4 NodeData 结构体定义(借鉴 Attribute_CB)

```c
#pragma pack(push, 1)
typedef struct {
    uint8_t  ParkStatus;      // 车位状态: 0=空闲, 1=有车, 2=异常
    uint8_t  GeoMagnetic;     // 地磁状态: 0/1
    uint16_t Ultrasonic;      // 超声波距离: 0~400 cm
    uint32_t OccupiedTime;    // 占用时长: 秒
    uint8_t  LED;             // LED状态: 0/1
    uint8_t  LedEnable;       // LED使能: 0/1
} LoraNodeData_t;             // 共 10 字节，LoRa 单包传输
#pragma pack(pop)
```

### 4.5 NodeCert 结构体定义(借鉴 AliyunInfo_CB)

```c
#pragma pack(push, 1)
typedef struct {
    uint8_t  valid;           // 有效标志
    char     ProductKey[12];  // OneNET 产品ID
    char     DeviceName[33];  // OneNET 设备名称
    char     AccessKey[33];   // OneNET 设备密钥(代上线无需签名, 可留空)
} LoraNodeCert_t;
#pragma pack(pop)
```

### 4.6 OTA 固件包格式(借鉴参考项目)

```
[AddrH][AddrL][CH][0x5A][0xA5][包号高][包号低][128字节固件数据]
```

- 每包 128 字节固件 + 7 字节头 = 135 字节，LoRa 240 分包内
- 子设备收到后回复 0xD1（成功，发下一包）或 0xE1（失败，重发）

### 4.7 OTA 完整流程 (借鉴参考项目 wifi.c L223-L444)

#### 网关自身 OTA

```
1. OneNET下发OTA命令 → 解析固件大小/版本号/streamId
2. ESP8266 从OneNET下载固件 (256B/包) → 存入LittleFS
3. 下载完毕 → 同步版本号到OneNET → ESP.restart()
4. ArduinoOTA BootLoader 更新Flash
```

#### 子设备 OTA (分级分发)

```
阶段1: 云端 → 网关
  1. OneNET下发子设备OTA命令 (module=SUB1/SUB2/SUB3)
  2. 解析固件大小/版本号 → 标记 OTA_EVENT
  3. 网关从OneNET下载固件 (256B/包) → 存入LittleFS
  4. 下载完毕 → 计算LoRa分发次数 (128B/包)

阶段2: 网关 → 子设备(LoRa定点分发)
  5. 组包: [AddrH][AddrL][CH][0x5A][0xA5][包号H][包号L][128B固件]
  6. LoRa定点发送 → 等待子设备回复
  7. 收到 0xD1: 成功 → 包号+1 → 发下一包
  8. 收到 0xE1: 失败 → 重发当前包
  9. 超时未回复: 重发当前包(最多3次)
  10. 全部分发完毕 → 同步子设备版本号到OneNET

阶段3: 子设备端
  11. 子设备接收固件包 → 存入W25Qxx
  12. 全部接收完毕 → 重启 → BootLoader更新Flash
```

#### OTA 超时保护 (借鉴参考项目)

- OTA 总超时: 120s，超时自动放弃，清除 OTA_EVENT
- 单包重传: 最多 3 次，3 次失败跳过该包（记录错误包号）
- OTA 期间暂停子设备轮询（避免 LoRa 信道冲突）

### 5.3 OneNET 网关子设备 Topic (2026-08-09 已按官方文档实现)

| 方向 | Topic | 说明 |
|---|---|---|
| 子设备上线请求 | `$sys/{pid}/{网关}/thing/sub/login` | 发布，代子设备上线 |
| 子设备上线响应 | `$sys/{pid}/{网关}/thing/sub/login/reply` | 订阅，code=200 成功 |
| 子设备下线请求 | `$sys/{pid}/{网关}/thing/sub/logout` | 发布，代子设备下线 |
| 批量上报(代子设备) | `$sys/{pid}/{网关}/thing/pack/post` | 发布，params 数组带子设备 identity |
| 批量上报响应 | `$sys/{pid}/{网关}/thing/pack/post/reply` | 订阅 |
| 子设备属性设置(下行) | `$sys/{pid}/{网关}/thing/sub/property/set` | 订阅，identity + params |
| 子设备属性设置回复 | `$sys/{pid}/{网关}/thing/sub/property/set_reply` | 发布 |

> **注意**：`{device-name}` 位置填的是**网关设备名**(PGW001)，不是子设备名。
> 子设备上线**无需签名**，平台按拓扑绑定关系校验。
> 上线/下线/上报均需先把子设备绑定到网关拓扑。

### 6.3 参考项目的关键设计模式

#### 6.3.1 串口三指针环形缓冲(借鉴设计思路)

参考项目每个串口用三指针管理环形缓冲：

```
UsartRxDataInPtr  → 写入位置 (中断中更新)
UsartRxDataOutPtr → 读取位置 (主循环中处理)
UsartRxDataEndPtr → 末尾位置 (循环回退点)
```

ESP8266 Arduino 的 Serial 库已内置环形缓冲，但设计思路值得借鉴——特别是需要管理多帧数据时。

#### 6.3.2 DMA 发送 + 间隔控制 (借鉴设计思路)

参考项目串口发送用 DMA + 100ms 间隔控制：

```c
if((UsartTxDataOutPtr != UsartTxDataInPtr) && (TxCpltflag == 0) && (HAL_GetTick() - TxTimer > 100))
```

ESP8266 SoftwareSerial 没有 DMA，但 100ms 发送间隔控制值得借鉴——避免连续发送导致 LoRa 模块堵塞。

#### 6.3.3 AUX 引脚状态检测(借鉴设计思路)

参考项目通过 LoRa 模块的 AUX 引脚判断模块状态：

- AUX=1：空闲，可以发送/设置
- AUX=0：忙，等待

ESP8266 可以用一个 GPIO 接 AUX，发送前检测状态。如果 GPIO 不够，也可省略（依赖 LBT）。

## 九、已知风险与注意事项

### 9.1 LoRa 信道碰撞

多节点同时发送会碰撞丢包。借鉴参考项目的三重防护：

1. **LBT**（硬件级）：LoRa 模块发前监听，信道忙则等待
2. **网关轮询**（协议级）：网关主动查询，节点不主动发送，天然避免碰撞
3. **重传**（应用级）：超时未收到回复则重发

### 9.2 SoftwareSerial 稳定性

ESP8266 SoftwareSerial 在高波特率下可能丢字节：

- LoRa 串口波特率固定 9600（参考项目也用 9600），稳定
- 如需 115200，必须迁移到 ESP32（3个硬件串口）

### 9.3 MQTT 缓冲区

代子设备批量上报(pack/post)单次 JSON 约 300 字节（identity + 6个属性）。

- 已设置 `mqtt.setBufferSize(2048)`，余量充足（onenet_handler.cpp）
- 下行属性设置(set) payload 一般 < 200 字节，解析缓冲区 768 字节

### 9.4 OneNET Token 过期

当前 Token 的 `et=1815919855` (2027年)，届时需重新生成。

- 网关 Token 在 config.h
- 子设备证书存 LittleFS，可通过平台动态更新

### 9.5 ESP8266 内存

ESP8266 可用堆内存约 40KB。

- 子设备数据数组：10 节点 × sizeof(NodeData) ≈ 100 字节，可忽略
- 子设备证书数组：10 节点 × sizeof(NodeCert) ≈ 1KB
- ArduinoJson StaticJsonDocument<512> ≈ 512 字节
- MQTT + WiFi 协议栈 ≈ 20KB
- 总计约 22KB，余量充足
- 若节点数 > 20，注意监控 `ESP.getFreeHeap()`

### 9.6 未来迁移 ESP32 的改动

| 改动点 | ESP8266 | ESP32 |
|---|---|---|
| WiFi 头文件 | `ESP8266WiFi.h` | `WiFi.h` |
| LoRa 串口 | `SoftwareSerial` | `Serial1` (硬件串口) |
| Flash 存储 | LittleFS (4MB) | LittleFS (8~16MB) |
| WebServer | `ESP8266WebServer` | `WebServer` |
| 其余代码 | 不变 | 不变 |

### 9.7 AP 配网期间 MQTT 断连

AP 配网模式下，ESP8266 切换到 AP 模式，WiFi STA 断开，MQTT 也会断开。

- 配网期间暂停所有子设备轮询、MQTT 操作
- 配网完成后重启，恢复正常 STA 模式
- 子设备在网关配网期间数据暂存，等网关恢复后补发

### 9.8 OTA 期间 LoRa 信道占用

子设备 OTA 分发时，LoRa 信道被大量 128B 固件包占用：

- OTA 期间暂停子设备数据轮询（避免冲突）
- OTA 分发优先级高于数据上报
- 子设备在 OTA 期间不采集传感器数据（固件更新中）
