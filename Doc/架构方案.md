## 二、核心交互逻辑：老师点名

> 用课堂场景类比整个系统的通信原理，帮助理解网关轮询、代上线、超时等核心概念。
> 如果你是第一次看这个项目，建议先读这一节。

### 2.1 角色对应

| 系统角色 | 课堂比喻 |
|----------|----------|
| **网关 (ESP8266)** | **老师** |
| **节点 (STM32 车位检测器)** | **学生** |
| **LoRa 无线** | **教室里的传话** |
| **OneNET 云平台** | **学校教务处** |

### 2.2 为什么是"老师点名"，而不是"学生抢答"？

因为 LoRa 无线通信有个致命问题——**同时说话就撞车**。如果两个节点同时发数据，LoRa 信号在空中碰撞，两个都收不到，就像教室里两个学生同时大喊，老师谁也听不清。

所以方案是**网关轮询**：老师一个个点名——先喊"节点1，报数据"，节点1回答；再喊"节点2，报数据"，节点2回答。同一时刻只有一个人说话，永远不会撞车。

---

### 2.3 完整交互流程

#### 第一步：老师认识学生（查询证书）

老师刚进教室，谁都不认识，得先认人：

```
老师喊: "节点1，报上你的学号姓名！"      (AT+CER1)
节点1回: "我是 Park001，学号 04kjwU9TC7"  (0xA1 + 证书)
老师记下: 哦，节点1叫 Park001，属于 04kjwU9TC7 班
```

老师记下来后，去教务处（OneNET）登记：

```
老师 → 教务处: "报告，Park001 来了，让他上线吧"   (thing/sub/login)
教务处 → 老师: "好的，Park001 已上线"              (code:200)
```

#### 第二步：老师查作业（查询数据）

认完人后，老师开始定时查作业：

```
老师喊: "节点1，汇报你的数据！"           (AT+DATA1)
节点1回: "我这边车位有车，超声波3cm，地磁感应到1"  (0xB1 + 10字节二进制数据)
老师记下: 节点1有车，然后把数据报给教务处
```

关键细节：10 字节的数据是**直接二进制拷贝**（memcpy），不是转成字符串。比如"有车"就是 `0x01` 一个字节，不是字符串 `"有车"`。这样速度快、省空间。

#### 第三步：老师报给教务处（代子设备上报）

老师拿到节点1的数据后，用 MQTT 发给 OneNET：

```
老师 → 教务处: "Park001 的数据是: 车位状态=有车，超声波=3cm，..." (thing/pack/post)
```

注意这里发的 Topic 是**老师的名字**（`$sys/9YIs0S7V11/PGW001/thing/pack/post`），但数据里带的是**学生的身份**（`identity: {productID: 04kjwU9TC7, deviceName: Park001}`）。教务处一看就知道这是老师代 Park001 报的。

---

### 2.4 队列与超时

#### 超时（Timeout）

学生回答是有时间限制的。老师点名后等一会儿，如果没人回答，就跳过，下次再问：

```
老师喊: "节点1，报数据！"
老师等...等...等...（比如 5 秒）
没人回答 → 老师想: "节点1可能出去了，下次再问"
```

#### 为什么代上线一次只发一条？

这是由**协议限制**决定的。教务处的回复只说"好的"，**没说"好的，Park001"**——回复里没有子设备的名字。

如果老师同时发两条：

```
老师: "Park001 上线了"
老师: "Park002 上线了"
教务处: "好的"    ← 老师不知道这个"好的"是回复 Park001 还是 Park002
```

**所以只能一次发一条**，等收到回复确认是"这条"之后，再发下一条。

#### 数据上报为什么不用排队？

数据上报（`thing/pack/post`）**不需要回复**——老师报上去就完了，不管教务处收没收到。所以可以一次性把两个节点都报了，不用排队。

#### 代下线

```
老师发现节点1已经 60 秒没说话了:
老师 → 教务处: "Park001 下线了"  (thing/sub/logout)
```

跟代上线一样，一次只能发一条。

---

### 2.5 连线重连后怎么办？

如果老师突然被叫出教室（WiFi 断线），回来时（重连），教务处已经忘了之前谁在线了。所以老师一回来就把之前认识的所有学生重新登记一遍：

```
"Park001 上线了" → 等回复 → "Park002 上线了" → 等回复 → ...
```

---

### 2.6 典型时间线

两个节点都正常在线：

```
t=0s    老师点名 "节点1，报数据" → 节点1回复 → 网关代上报
t=0.5s  老师点名 "节点2，报数据" → 节点2回复 → 网关代上报
t=15s   老师再次点名 "节点1，报数据" → ...
t=15.5s 老师点名 "节点2，报数据" → ...
t=60s   老师: "教务处，心跳"  (PING)
... 循环 ...
```

如果一个节点坏了（拔电、死机）：

```
t=0s    老师点名 "节点1" → 没人回 → 超时失败
t=0.5s  老师点名 "节点2" → 正常
t=10s   老师再点名 "节点1" → 没人回
t=20s   再点名 → 没人回
t=60s   老师发现 60 秒没收到节点1的数据 →
        标记离线 → 告诉教务处 "Park001 下线了"
        之后不再问节点1，只问节点2
```

## 三、核心通信协议

### 3.1 LoRa 定点传输协议

**帧格式：**

```
[目标地址高1B][目标地址低1B][目标信道1B] + [数据内容]
```

**命令帧（网关 → 节点，ASCII）：**

| 命令 | 内容 | 说明 |
|------|------|------|
| 查询证书 | `AT+CER1\r\n` | 查询节点1的 OneNET 证书 |
| 查询数据 | `AT+DATA1\r\n` | 查询节点1的传感器数据 |
| 控制开关 | `AT+LedEnable=1\r\n` | 设置节点1的 LED 使能 |
| OTA 版本 | `AT+VER1=xxx\x00[sizeH][sizeL]` | OTA 完成通知 |

**数据帧（节点 → 网关，二进制帧头）：**

| 帧头 | 数据内容 | 说明 |
|------|----------|------|
| `0xA1` | LoraNodeCert_t (79字节) | 子设备证书(ProductKey/DeviceName) |
| `0xB1` | LoraNodeData_t (10字节) | 传感器数据 |
| `0xC1` | 4字节开关状态 | 控制命令回复确认 |

**NodeData 结构体（10字节 packed）：**

```c
typedef struct {
    uint8_t  ParkStatus;      // 车位状态: 0=空闲, 1=有车, 2=异常
    uint8_t  GeoMagnetic;     // 地磁: 0/1
    uint16_t Ultrasonic;      // 超声波距离: 0~400 cm
    uint32_t OccupiedTime;    // 占用时长: 秒
    uint8_t  LED;             // LED 状态: 0/1
    uint8_t  LedEnable;       // LED 使能: 0/1
} LoraNodeData_t;             // 共 10 字节
```

**NodeCert 结构体（79字节 packed）：**

```c
typedef struct {
    uint8_t  valid;           // 有效标志
    char     ProductKey[12];  // OneNET 产品ID
    char     DeviceName[33];  // OneNET 设备名称
    char     AccessKey[33];   // 留空 (OneNET 代上线无需签名)
} LoraNodeCert_t;
```

### 3.2 OneNET 网关子设备协议

**Topic 表：**

| 方向 | Topic | 说明 |
|------|-------|------|
| 子设备上线 | `$sys/{pid}/{网关}/thing/sub/login` | 发布，代子设备上线 |
| 上线响应 | `$sys/{pid}/{网关}/thing/sub/login/reply` | 订阅，code=200 成功 |
| 子设备下线 | `$sys/{pid}/{网关}/thing/sub/logout` | 发布，代子设备下线 |
| 批量上报 | `$sys/{pid}/{网关}/thing/pack/post` | 发布，params 带子设备 identity |
| 上报响应 | `$sys/{pid}/{网关}/thing/pack/post/reply` | 订阅 |
| 属性设置(下行) | `$sys/{pid}/{网关}/thing/sub/property/set` | 订阅，identity + params |
| 设置回复 | `$sys/{pid}/{网关}/thing/sub/property/set_reply` | 发布 |

> 注：`{pid}` = 网关产品ID (9YIs0S7V11)，`{网关}` = 网关设备名 (PGW001)
> 子设备上线无需签名，平台按拓扑绑定校验。
> 一次只能发一条上线/下线请求（回复不携带子设备身份）。

**上线 JSON：**

```json
{"id":"1698...","version":"1.0","params":{"productID":"04kjwU9TC7","deviceName":"Park001"}}
```

**批量上报 JSON：**

```json
{
  "id": "1698...",
  "version": "1.0",
  "params": [
    {
      "identity": {
        "productID": "04kjwU9TC7",
        "deviceName": "Park001"
      },
      "properties": {
        "ParkStatus":   {"value": 2},
        "GeoMagnetic":  {"value": 1},
        "Ultrasonic":   {"value": 3},
        "OccupiedTime": {"value": 21},
        "LED":          {"value": true},
        "LedEnable":    {"value": true}
      }
    }
  ]
}
```

**下行属性设置 JSON：**

```json
{"id":"123","version":"1.0","params":{"deviceName":"Park001","productID":"04kjwU9TC7","params":{"LedEnable":"1"}}}
```

## 四、数据流详解

### 4.1 上行数据流（节点 → 云）

```
                        网关轮询 (每节点 10s)
STM32 节点 ●──────────────────────────► ESP8266 网关
  │                                         │
  │ ① 收到 AT+DATA1                          │
  │ ② 采集超声波+地磁                        │ ③ 收到二进制帧 (0xB1)
  │ ③ 打包 NodeData 结构体 (10字节)          │ ④ updateNodeFromRaw()
  │ ④ LoRa 定点回复                          │ ⑤ 缓存数据, 标记 dataChanged
  │                                         │
  │                                         │ MQTT (事件触发 / 15s周期)
  │                                         ├──────────────────► OneNET
  │                                         │ topic: thing/pack/post
  │                                         │ identity: Park001
  │                                         │ properties: 6个属性
```

### 4.2 子设备上线流程

```
                        网关轮询 (首次 27s)
STM32 节点 ●──────────────────────────► ESP8266 网关
  │                                         │
  │ ① 收到 AT+CER1                          │
  │ ② 回复 NodeCert (0xA1)                  │ ③ updateNodeCert()
  │   (productID, deviceName)               │ ④ loginPending = true
  │                                         │
  │                                         │ thing/sub/login (一次一条)
  │                                         ├──────────────────► OneNET
  │                                         │◄── code:200 ───────┤
  │                                         │ ⑤ subLogin = true
  │                                         │ ⑥ 立即 subPost()
```

### 4.3 下行数据流（云 → 节点）

```
OneNET
  │ MQTT 推送 (thing/sub/property/set)
  │ {deviceName:"Park001", params:{LedEnable:"1"}}
  ▼
ESP8266 网关
  │ ① mqtt_callback() 收到
  │ ② 按 deviceName 匹配节点
  │ ③ lora_sendControl("LedEnable", 1)
  │
  │ LoRa 定点
  ├──────────────────────────────────────► STM32 节点
  │                                       │ ④ 收到 AT+LedEnable=1
  │                                       │ ⑤ 执行 LED 控制
  │                                       │ ⑥ LoRa 回传 ACK (0xC1)
  │◄──────────────────────────────────────┤
  │ ⑦ 回复 set_reply (code:200)
  ├──────────────────► OneNET
```

## 五、关键设计决策

### 5.1 为什么用网关轮询（老师点名）而非节点主动上报？

| 方案 | 问题 | 结论 |
|------|------|------|
| **节点主动上报** | 多节点同时发送 → LoRa 空中碰撞 → 数据丢失 | 放弃 |
| **网关轮询** | 同一时刻只有被点名节点回复 → 零碰撞 | **采用** |

### 5.2 为什么用 ESP8266 做主控而非 STM32？

| 方案 | 问题 | 结论 |
|------|------|------|
| **STM32 主控 + ESP8266 透传** | 两芯片间串口通信脆弱、下行命令延迟高、WiFi 协议栈在 AT 指令层不稳定 | 放弃 |
| **ESP8266 主控** | MQTT 库直接在 ESP8266 上跑、事件回调驱动、串口只接 LoRa 模块 | **采用** |

### 5.3 为什么代上线一次只能发一条？

OneNET 的上线回复 `{"code":200}` 不携带子设备身份。如果同时发两条上线，网关无法区分回复对应哪个设备。因此**一次只能发一条，收到回复后再发下一条**。

### 5.4 为什么用二进制结构体传数据而非 JSON/字符串？

| 方案 | 字节数 | 解析方式 | 结论 |
|------|--------|----------|------|
| **JSON 字符串** | ~100 字节 | 解析耗时、浮点精度问题 | 否 |
| **ASCII CSV** | ~40 字节 | 字符串分割易错 | 否 |
| **二进制结构体** | **10 字节** | memcpy 零拷贝 | **采用** |

### 5.5 稳定性保障设计

| 设计 | 说明 |
|------|------|
| **每个操作都有超时** | LoRa 等待 5s、代上线 5s、离线 60s，不卡死 |
| **状态机驱动** | IDLE → RX_HEADER → RX_FRAME，出错可回退 |
| **自动恢复** | 节点掉线 → 代下线，节点恢复 → 重新代上线 |
| **MQTT 重连** | 断线检测 → 自动重连 → 子设备重新登记 |
| **环形缓冲** | USART2 中断收完，主循环处理，不丢字节 |

### C.2 常见问题排查

**Q: 串口显示 `SubLogin` 但一直没收到 `login OK`？**
- 检查子设备是否已在平台绑定到 PGW001 拓扑
- 检查 `productID` 和 `deviceName` 是否与平台创建的一致（大小写敏感）

**Q: 节点上报数据了，但平台看不到属性值？**
- 检查物模型属性标识符是否与代码中的 `SUB_PROP_*` 宏完全一致
- 检查 `thing/pack/post` 的 JSON 格式是否包含正确的 `identity` 字段

**Q: 网关 MQTT 频繁断连？**
- 检查 WiFi 信号强度
- PubSubClient 默认 keepalive 15s，代码已设为 60s，可进一步调整
- 检查 Token 是否过期（`et` 时间戳）

**Q: LoRa 收不到节点回复？**
- 检查模块配置：`AT+MODE1`（定点）、`AT+MAC`（地址）、`AT+CHANNEL`（信道）
- 检查波特率：网关 SoftwareSerial 9600，节点 USART2 115200（模块内部转 9600）
- 检查信道：两端 `LORA_CHANNEL` 必须一致（当前 0x00=433.15MHz）

**Q: 节点端 OLED 显示"LoRa未连接"？**
- 检查 `LoRa_Node_IsOnline()` 返回值（节点端逻辑）
- 检查节点是否收到网关的 AT 命令（串口助手可观察）

### C.3 编译注意事项

- **ESP8266 网关**：Arduino IDE 选择 NodeMCU 1.0 (ESP-12E Module)，Flash Size 选 4MB (1M SPIFFS)
- **STM32 节点**：Keil MDK 编译，注意 .c/.h 文件编码为 GBK（部分中文注释会乱码，不影响编译）
- 网关端 `config.h` 中 `ONENET_TOKEN` 含特殊字符，确保不被编辑器转义
