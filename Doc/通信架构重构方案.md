# 通信架构重构方案：模式感知轮询与状态模型

> 适用范围：智能停车场物联网项目（STM32F103C8T6 节点 + LoRa 半双工链路 + ESP8266 网关 + OneNET 平台）
> 架构背景：Boot 0x08000000 / 配置区 0x08003000 / APP 0x08004000(47KB) / 升级标志页 0x0800FC00
> 关联文档：[OTA升级可靠性优化方案.md](./OTA升级可靠性优化方案.md)（升级过程可靠性兜底，本方案与其正交）
> 状态：**方案草案（待评审）**，评审通过前不实施代码改动

---

## 1. 背景与动机

节点在"业务模式（APP）"与"升级模式（BOOT）"两种运行模式间切换。Boot 模式下节点能回答链路探测，但不能提供业务数据。

当前网关对节点状态认知残缺，导致以下真实故障：

- **DATA 空转僵尸**：已注册在线节点 OTA 进 Boot 后，网关按"快速路径"每轮直接发 `DATA`，节点不回，网关超时跳过、下轮再发——永久空转，且平台看到节点"在线但静默"，无任何异常信号。
- **模式不可感知**：网关发 `AT+PING` 只能得知"活着"，不知道节点处于什么模式，无法针对性交互（索数据 or 救活）。
- **在线语义二义**：`online` 只表示"链路上有响应"，被误当作"业务在线"，Boot 节点被错误地标记为业务在线。

本方案从根本架构出发，把"模式"提升为协议与轮询模型的显式维度，统一网关对节点的状态认知，而不是打补丁。

## 2. 问题根因分析

### 2.1 结构性缺陷清单

| #  | 缺陷                             | 现状证据                                                            | 后果                                                                        |
| -- | -------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| S1 | **节点模式非协议一等公民** | PING 响应仅`PONG`，无模式字段                                     | 网关无法区分 APP/BOOT，靠"命令响应猜模式"                                   |
| S2 | **online 语义二义**        | `nodes[slot].online = true` 是唯一赋值点，从不置 false            | Boot 节点链路活着即被标"业务在线"，平台无异常信号                           |
| S3 | **轮询模型三套分叉**       | 快速路径直发 DATA（`certOk && online`）、离线 PING、搜索模式 PING | Boot 节点落在快速路径的坑里，网关根本不 PING 它，永无感知机会               |
| S4 | **模式变化无同步**         | App→Boot→App 翻转无任何信号源                                     | OTA 状态机与轮询状态机靠`ota_getState()!=OTA_IDLE` 粗暴互斥，结束后无衔接 |
| S5 | **OTA 触发源分散**         | 平台下发触发；自动救活无统一入口                                    | 自动/人工/平台三条触发路径语义不统一，防双轨靠临时判断                      |

### 2.2 根因链（DATA 空转僵尸）

```
节点 App 在线 → 平台下发 OTA → 节点复位进 Boot
  └─> 网关 OTA 流程(暂停轮询) → 失败整链重试耗尽 → 删固件文件 → OTA_IDLE
        └─> 恢复轮询: 节点在 Boot, 但网关内存里 nodes[slot].online 仍为 true(S2)
              └─> 快速路径(S3): 每轮直发 DATA → Boot 不回 → 超时跳过 → 下轮再 DATA
                    └─> 永久空转: 网关不知道节点是 Boot, 平台无异常信号, 无自动救活
```

> 体检结论：S6-S32 与 S1-S5 同源——**状态无单一事实源、逻辑重复、边界靠巧合**。重构不逐一打补丁，而是通过第 4-9 节的三态模型、单轨 OTA、统一资源边界一次性覆盖。

## 4. 目标架构总览

```
┌─────────────────────────── 网关 (ESP8266) ───────────────────────────┐
│  每节点状态模型:                                                     │
│    linkAlive      链路存活 (最近收到任何响应)                          │
│    mode           APP / BOOT / UNKNOWN (由 PING 响应/业务帧更新)      │
│    serviceOnline  业务在线 (mode==APP && 最近有业务数据)               │
│                                                                      │
│  轮询分派 (探测优先):                                                 │
│    mode==BOOT            → 只 PING → 回 PONG,BOOT → OTA 判定器        │
│    mode==UNKNOWN/失联    → PING 探测                                  │
│    mode==APP && 活跃     → 快速路径 DATA/CER (优化, 非默认)           │
│    mode==APP && 失活     → PING 确认后恢复 DATA                       │
│                                                                      │
│  OTA 统一判定器:                                                      │
│    节点 mode→BOOT → 状态非IDLE? 不动作 : 有固件? 自动重发 : 标记待OTA  │
└──────────────────────────────────────────────────────────────────────┘
                                │ LoRa 半双工轮询
┌─────────────────────────── 节点 (STM32F103C8T6) ─────────────────────┐
│  APP 模式: PING 响应 → PONG,APP                                        │
│  BOOT 模式: PING 响应 → PONG,BOOT (空闲态)                            │
│             升级态(等SOH): 不回 PING (网关 OTA 期间暂停轮询, 天然错开) │
│  原则: 是什么模式报什么模式, 不伪装在线                                 │
└──────────────────────────────────────────────────────────────────────┘
```

> 全链路贯穿原则（覆盖 S6-S25）：
>
> - **单一事实源**：协议常量一份（shared 头）、Flash 标志写接口一份、AT 收集一份、阈值下发一份——消灭重复实现（S6/S7/S8/S10/S11）。
> - **显式状态**：节点模式、链路态、业务态全部显式字段，赋值收敛到统一入口（S9/S12/S13/S14；S22 在线位已移除落地）。
> - **防御性边界**：缓冲带长度校验、命令队列化、Xmodem 去重、持久化异步化——不靠巧合（S16/S17/S18/S19/S20）。

## 5. 协议层设计

### 5.1 PING 响应携带模式

- 节点对 `AT+PING` 的响应：`PONG,<MODE>`，`MODE ∈ {APP, BOOT}`
- 帧格式沿用现有字符串 ACK 帧：`[AddrH][AddrL][CH][0xC1] + "PONG,BOOT" + \r\n`（Boot 复用 `OTA_SendAckString`，App 复用 `LoRa_Node_SendAck`，帧构造零改动）

```
节点:  [AddrH][AddrL][CH][0xC1] "PONG,APP"  \r\n    (App 模式)
节点:  [AddrH][AddrL][CH][0xC1] "PONG,BOOT" \r\n    (Boot 模式)
```

### 5.2 网关解析规则

| 收到帧             | 解析结果                         | 动作                         |
| ------------------ | -------------------------------- | ---------------------------- |
| `PONG,APP`       | linkAlive=true, mode=APP         | 下一轮发 DATA/CER            |
| `PONG,BOOT`      | linkAlive=true, mode=BOOT        | 不索要数据 → OTA 判定器     |
| `PONG`（旧固件） | linkAlive=true, mode=APP（默认） | 向前兼容，按 APP 处理        |
| 无响应             | linkAlive=false                  | 退避档位拉长（现有离线逻辑） |

### 5.3 兼容性策略

- **旧 App 固件**（回纯 `PONG`）：网关前缀匹配 `PONG` 判在线，视为 APP——向后兼容，无感知。
- **旧网关 + 新节点**（Boot 回 `PONG,BOOT`）：旧网关 `strcmp("PONG")==0` 失配 → 判无响应 → 离线退避（退化到现状）。**双端需同步升级**，升级顺序：先网关后节点。

## 6. 网关状态模型（三态正交）

```cpp
/* nodes[slot] 新增/调整字段 */
bool   linkAlive;        /* 链路存活: 最近收到过任何响应 */
uint8_t mode;            /* NODE_MODE_APP / NODE_MODE_BOOT / NODE_MODE_UNKNOWN */
bool   serviceOnline;    /* 业务在线: mode==APP 且最近有业务数据 (替代原 online) */
bool   bootPending;      /* 待 OTA: 节点在 Boot 且网关无固件, 等平台下发 */
uint8_t dataMissCount;   /* 连续 DATA/CER 无响应计数 (防快速路径僵尸) */
```

三个字段的正交关系：

| linkAlive | mode    | serviceOnline | 网关行为                                      |
| --------- | ------- | ------------- | --------------------------------------------- |
| true      | APP     | true          | 快速路径 DATA/CER                             |
| true      | APP     | false         | PING 确认后恢复 DATA                          |
| true      | BOOT    | false         | 只 PING 保活 + OTA 判定（**不索数据**） |
| false     | UNKNOWN | false         | 离线退避探测（现有逻辑）                      |

**统一赋值入口（S9）**：`linkAlive` / `mode` / `serviceOnline` 只通过 `updateNodeState(slot, event)` 一个函数更新（事件驱动：收到帧 / 超时 / OTA 状态变化），删除 `online=true` 散落赋值点。置 true 与置 false 的路径在函数内成对出现，编译器与评审都能直接核对对称性。

> 平台/运维看到的"在线"统一用 `serviceOnline`。Boot 节点显示为异常/待 OTA——这是**正确行为**，它当前不是服务提供者。

## 7. 轮询分派逻辑（探测优先）

### 7.1 分派流程（替换现 `lora_handler.cpp` 快速路径直发逻辑）

```
轮询到节点 N:
├─ slot < 0                        → 跳过 (空槽位)
├─ mode==BOOT                      → 发 PING
│     └─ 回 PONG,BOOT → 保持节奏, OTA 判定器
│     └─ 无响应       → linkAlive=false → 退避
├─ mode==UNKNOWN 或 !linkAlive     → 发 PING 探测
│     └─ 回 PONG,APP → mode=APP, 下一轮 DATA
│     └─ 回 PONG,BOOT→ mode=BOOT, 转 OTA 判定器
│     └─ 无响应       → 退避档位拉长 (现有逻辑)
├─ mode==APP && serviceOnline      → 快速路径 DATA/CER (现有逻辑, 前提收紧)
│     └─ dataMissCount>=N 无响应   → serviceOnline=false → 转 PING 探测
└─ mode==APP && !serviceOnline     → 发 PING 确认后恢复 DATA
```

### 7.2 关键语义调整

1. **快速路径收紧**：直发 DATA 的前提从 `certOk && online` 改为 `mode==APP && serviceOnline`——Boot 节点不再走快速路径。
2. **Boot 节点只 PING**：不回 DATA/CER，不退避（`PONG,BOOT` 响应保持正常节奏），让网关持续确认它仍在 Boot，直到 OTA 判定器接手或模式变化。
3. **失活摘除**：快速路径 DATA 连续 N 次无响应 → `serviceOnline=false` → 自动降级为 PING 探测，消灭"在线僵尸"通道。
4. **`online` 字段语义归位**：原 `online` 拆分为 `linkAlive` + `serviceOnline`，赋值点补齐（不能只置 true 不清）。

## 8. OTA 统一触发入口（防双轨的根本保证）

### 8.1 统一判定器

节点 mode 变为 BOOT（收到 `PONG,BOOT`）时，网关进入单一判定：

```
节点 mode=BOOT:
├─ ota_getState() != OTA_IDLE  → 不动作 (现有机制: 触发重发/整链重试/下载中)
├─ OTA_IDLE && OTA_FW_FILE 存在 → ota_startFromFile() 自动重发 (自愈)
└─ OTA_IDLE && 无固件           → bootPending=true, 等平台下发 (平台 ota_start 后自然清除)
```

**判定器配套修正（S15/S21）**：

1. **固件文件保留策略（S15）**：`OTA_COMPLETE` 不再立即删文件；文件保留至（a）被新固件覆盖或（b）目标节点确认离开 Boot（下一次收到 `PONG,APP`）后清理。保证"升级成功后节点滞留 Boot"场景自愈闭环仍成立。
2. **拒绝升级识别（S21）**：网关解析到 `AT+OTA:version_ok` → 标记节点 `otaRefused=true`，终止对 App 的 Xmodem 流（不产生空口噪声），`bootPending` 转为"待人工/平台介入"，上报平台；仅当收到同版本确认或人工重触发时清除标记。
3. **人工触发同路径（S14）**：串口手动 OTA 触发不再直接调 `ota_start`，统一走判定器入口，由判定器先复位轮询上下文再进入 OTA。

### 8.2 单轨保证

- 自动救 / 人工救 / 平台救全部汇入 `ota_start()` / `ota_startFromFile()` 单入口。
- OTA 状态机唯一性（仅 `OTA_IDLE` 可启动）天然防并发，无需额外"防重入"标志。
- 平台下发新固件时，若目标节点 `bootPending`，网关立即下发（无需节点先响应）。

### 8.3 平台联动（后续阶段）

- 网关向平台上报 `serviceOnline=false + mode=BOOT` 语义（节点异常/待 OTA），使平台可自动重新下发固件。
- 具体上报通道（数据点/服务调用）在平台侧方案中定稿，不在本方案实现范围。

### 11.3 优先级分批执行（P0 → P1 → P2）

分批原则：

- **依赖优先**：三态字段（S9）是轮询分派与 OTA 判定器的一切前提，必须最先落地。
- **端到端闭环**：每个优先级都是一条完整功能闭环，独立可验收；前一批全部通过（第 12/14 节验证）再进下一批。
- **可随时中断**：P0 完成后系统已止血（不再空转）；P1 完成后 OTA 场景正确；P2 是加固，时间紧可暂缓。

### 14.2 日志观察点

- 网关调试串口：`DEBUG_SERIAL`（`hw_cfg.h` 61-67 行，硬件串口用 `Serial`、软件串口用 `Serial1`），日志走 `DBG_PRINT`/`DBG_PRINTLN` 宏（`app_cfg.h` 96-98 行）。

- 重点看 4 类日志：
  1. **轮询命令流**：网关每轮发的是 `DATA` / `CER` / `PING` / `AT+OTA`——确认 Boot 节点不再被发 DATA。

## 15. 实施变更记录（2026-09-09）

> 本记录覆盖一次完整根因闭环修复：日志复现"无法擦写 + 双端僵局" → 全链路根因分析 → 实施 8 项修复（Boot 端 5 项 + 网关端 2 项 + 死锁放大器消除 1 项）。全部改动已落盘并通过编译验证（Boot/App Keil 0 Error 0 Warning，网关 arduino-cli exit 0）。

### 15.1 根因链（本批修复针对）

```
用户拔电 → 首次 OTA 中断残留 APP_PARTIAL
  └─> Boot 误判"已擦干净"跳过重擦 (原代码 if(!appErased) 条件)
        └─> 写残留地址触发 PGERR, 且未清标志 → 本次会话永久写失败
              └─> 连续 3 轮整链重试全部"无法擦写" → 重试耗尽 → 删固件文件回 OTA_IDLE
                    └─> 网关判定器空转 bootPending + 节点无限 NAK 催发 = 双端僵局
```

### 15.2 Boot 端（5 项）

| #    | 改动                                                                                       | 解决什么问题                                                                                     |
| ---- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| P0-1 | 固件头验证后**无条件** `OTA_EraseAppArea()`（删除 `if (!appErased)` 条件）       | `APP_PARTIAL` 仅表"APP 区可能残留脏数据"，**绝不代表已擦干净**；直接写残留地址触发 PGERR |
| P0-2 | `OTA_FlashWrite` 每半字写前 `FLASH_ClearFlag(PGERR\|WRPRTERR\|EOP)`，失败清标志重试一次  | PGERR 置位后持续阻断编程，必须清标志才能继续；消除"一次写失败 = 本会话永久写失败"                |
| P1-3 | NAK 催发限次：`nakUrgeCount >= OTA_ERASED_NAK_MAX(5)` 停止催发；收到有效包重置计数       | 网关放弃后节点不再无限刷屏；新增宏`OTA_ERASED_NAK_MAX`（`boot_cfg.h`）                       |
| P2-6 | 3 处日志双前缀修正（`ver=` / ` crc32=` / `@ ` 去掉冗余 `0x`，`PutHex` 自带前缀） | 日志可读性与网关解析对齐                                                                         |
| P2-7 | 双 CAN 确认：`static uint8_t canSeen` 跨调用保持，连续收到 2 个 CAN 才确认取消           | 防单 CAN 帧丢失/误判传输取消                                                                     |

### 15.3 网关端（2 项）

| #    | 改动                                                                                                                                                               | 解决什么问题                                                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| P1-4 | 统一判定器`ota_autoDispatch` 降噪：Boot 分支日志仅模式**跃迁**（`prevMode != NODE_MODE_BOOT`）时打印一次；`bootPending` 仅首次由非等待→等待时打印一次 | 消灭"每轮 PING(~2s) 无限刷屏'转 OTA 判定器'"（死锁日志的噪音来源） |
| P1-5 | `ota_notifyTriggerAck(nodeId)` 增加目标校验：ACK 必须来自最近触发命令的目标节点，否则忽略                                                                        | 多节点并存时他节点 ACK 不再被误当本节点触发确认                    |

### 15.4 P0-3 失败重试耗尽保留固件文件（死锁放大器消除）

- `OTA_FAILED` 且整链重试耗尽：**删除**原 `LittleFS.remove(OTA_FW_FILE)` 逻辑，固件文件保留。
- 文件清理收敛为两条路径（与 8.1#1 S15 一致）：① 节点确认离开 Boot（`PONG,APP` → `ota_notifyNodeApp`）；② 被新固件覆盖（平台/人工重新下载时重写）。
- 效果：上报 202 失败后，判定器在节点 `PONG,BOOT` 时仍可自动重发（自愈），"节点可救却因文件被删而永久僵持"根因消除。
- 平台账目不受影响：202 上报不依赖删文件；窗口期论证结论——**不引入观察窗**，仅延迟"显示失败"不改变结局，属纯冗余复杂度。
- 本节对 2.2 根因链中"失败整链重试耗尽 → 删固件文件 → OTA_IDLE"链节的消除；同步更新 [OTA升级可靠性优化方案.md](./OTA升级可靠性优化方案.md) 3.3.2 措辞。

### 15.8 S26：单字节 EOT 误判 + expectSeq 残留死循环修复（双 EOT 确认 + 语义校验 + 序号对齐）

> 本批对应第 2.3.4 节新增 S26 条目。基于实测新日志的根因闭环：网关反复"转 OTA 判定器"而节点反复 NAK 催发，双向僵持不收敛。

**故障现场（2026-09-09 实测日志，旧代码）**：

```
节点侧：两次打印 "收到EOT, 共14/36包, 校验失败"  → 数据远未收满(36包仅14)却判传输结束
网关侧：全程无一例 "[OTA] EOT 已发送"            → 网关从未真发过 EOT, 0x04 来自空中杂波
节点侧：expect=57 recv=1 → 永久 "序号错位" NAK    → 残留上轮失败序号, 与整链从#1重发冲突
```

**设计定稿（先想清"标准规范"再动手，非一拍脑袋连发两次）**：

- **第一层·语义校验（主）**：Xmodem 语义 = **EOT 表示发送方已发完所有数据**。节点从固件头已知总长 `fwLen`，只有写入量 `totalWrote` 达到 `fwLen - sizeof(FwHeader_t)` 时才可能存在真 EOT；未收满前收到 `0x04` 必为空中杂波/残留字节，直接忽略（连单字节确认都不置位）。从语义上杜绝"14/36 包即结束"。
- **第二层·双字节确认（辅）**：收满后仍要求**连续两个 `0x04`**。依据：Xmodem 规范对不可靠链路的多字节控制符惯例（取消须连发 8 个 CAN），且本项目已有双 CAN 确认（S22 落地），EOT 属同类漏改字节，对齐保持协议内部一致性。期间收到 `SOH` 则取消（网关仍在发包说明未结束）。
- **expectSeq 对齐**：Xmodem 规则"任何重新开始的传输必须从 seq=1 起"。网关每次整链重试/自愈都以 `AT+OTA` 为起点、之后必从 #1 发包（`ota_handler.cpp` 316/367/532/550/778 行多处 `s_seq=1`），因此节点唯一正确对齐点是**窗口内收到 `AT+OTA` 立即重置 `otaExpectSeq=1`**。

**修复（`Node/BootLoader/User/main.c` + `Gateway/ota_handler.cpp`）**：

| 端   | 改动                                                                                                                                                                                                                                                                         | 解决什么问题                                                         |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 网关 | 状态枚举新增`OTA_SEND_EOT2`；`OTA_SEND_EOT` 与 `OTA_SEND_EOT2` 各发送一个 `0x04`（`ota_handler.cpp` 653-669 行），再转 `OTA_WAIT_FINAL_ACK`                                                                                                                      | 节点侧双字节确认的数据来源；不再单发 EOT 靠运气                      |

**效果**：未收满前的 `0x04` 杂波被语义层直接丢弃；收满后双字节确认才结束传输；窗口内收到 `AT+OTA` 时序号对齐回 1 —— "14/36 包即结束"与"expect=57 死循环"两类现象从机制上杜绝。

### 15.9 S27：自愈无脑循环收口（自愈预算）+ OTA 不阻塞 MQTT（双让出）

> 本批对应第 2.3.4 节新增 S27 条目，与 S26 联动（S26 治"单次传输反复失败"，S27 治"失败后网关与节点无限重复发包 + 平台命令接收迟钝"）。用户定调：**自愈机制有必要、无脑循环没必要、阻塞 MQTT 不允许**。参数经确认：自愈预算 3 次、下载循环+AUX 忙等双让出、平台/人工显式触发才恢复自动自愈。

**故障现场（2026-09-09 实测日志，旧代码）**：

```

       → "网关和节点一直在重复性的发包, 云平台下发的命令感觉接收都不灵敏了"
```

**设计定稿（三个子方案，均已按用户确认参数落地）**：

- **3a 下载循环让出**：`downloadFirmware()`（`ota_handler.cpp`）与平台侧 `otaDownloadFile()`（`onenet_ota.cpp`）的流式下载 `while` 循环内，把裸 `yield()` 替换为周期调用 `onenet_loop()`——后者内部 `mqtt.loop()` 保活 + 收下行 + 掉线清标志 + 9s 服务调用截止检查 + OTA 属性降频上报，轻量可安全在下载循环内调用。下载期间 MQTT 不再停顿。
- **3b AUX 忙等让出**：`sendFixedFrame()`（`lora_handler.cpp`）三段 `while` AUX 忙等循环体由空 `{}` 改为周期调用 `onenet_loop()`，超时上限 `LORA_AUX_WAIT_MS=50ms` 语义不变。一发最多 150ms 的忙等窗口内 MQTT 保活不中断。

  - **成功清零**：`OTA_COMPLETE` 时清零该节点预算。
  - **显式清零**：`ota_start()`（平台/人工下载路径）、`ota_startFromFile()` 显式来源（平台固件分发/人工触发）、`ota_cancel()` 均清零预算，恢复自动自愈能力。
  - **来源区分**：`s_selfHealRun` 标志由 `ota_autoDispatch` 置位标记"本次由自动自愈发起"，`ota_startFromFile` 据此区分显式/自动来源；节点切换时新节点独立计数。

**修复（`Gateway/ota_handler.cpp` + `Gateway/lora_handler.cpp` + `Gateway/onenet_ota.cpp` + `Gateway/lora_protocol.h`）**：

| 端       | 改动                                                                                                                 | 解决什么问题                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |

### 15.11 S29：上线即代上报全 0 快照（hasDataFrame 上报门控）

> 本批对应第 2.3.4 节新增 S29 条目（网关侧）。用户定调：**节点端都没上报给他，他凭啥上报给平台呢**——上报时机本质不对，网关不应代报节点未上报的数据。

**故障现场（2026-09-10 实测日志）**：

```
00:58:31 PONG,APP            ← 节点进入 APP
00:58:31 下发 ZombieThreshold=5
00:58:31 ACK (节点已生效 5)
00:58:35 登录成功 → 立即 subPost 上报   ← 上报值 = 0 (节点数据帧未到, 缓存为初始 0)
```

时序上"下发 → ACK 生效"早于"上报"，但上报的却是 0 而非 5——**上报时机语义错位**：ACK 只代表"节点已生效"，不产生任何可上报的真实数据。

**根因**：

1. 上报缓存 `nd.zombieThresholdSec` 只随**节点业务数据帧**更新（`updateNodeFromRaw`）；节点刚升级/重启未发过数据帧时缓存为初始 0。
2. ACK 分支只清下发标志 + 回平台调用结果，**不同步上报缓存**——ACK 到位≠有数据可报。
3. 旧逻辑"登录成功立即 `subPost`"把全 0 快照上报平台，污染平台存储；`ZombieThresholdSec=0` 低于物模型下限（5）被 code=2213 拒绝。

**修复（网关侧三处，仅网关需重烧）**：

| 位置                                    | 改动                                                                                                                                         | 解决什么问题                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `node_data.h`                         | 新增`hasDataFrame` 字段                                                                                                                    | 记录"是否收到过节点业务数据帧"                 |
| `node_data.cpp` `updateNodeFromRaw` | 成功解析数据帧后置`hasDataFrame = true`                                                                                                    | 真实数据到达才解锁上报                         |
| `onenet_handler.cpp`                  | 删除`subPost` 单节点上报；登录 200 分支不再立即上报（改打印"属性待首帧数据到达后上报"）；`subPostBatch` 收集循环加 `hasDataFrame` 门控 | 上报时机语义正确：节点没上报数据，网关就不代报 |

**效果**：平台收到的首个属性快照必来自真实数据帧（阈值是节点确认后的真实值），全 0 垃圾快照与 code=2213 从根上消除。副作用：登录后需等下一轮 LoRa 轮询索要 DATA 才上报，延迟一个轮询周期（秒级），换来平台存储不被污染。

### 15.12 S30：阈值重发收敛到 PONG 统一兜底（一招制敌）

> 本批对应第 2.3.4 节新增 S30 条目（网关侧）。用户定调：**节点每次 PONG 重新上线时按 LFS 保存值重发一次就够兜底**——因为无论 OTA 成功、网关断电重启、节点断电重连/重启，节点都必然先被 PING 再回 PONG，PONG 是所有"重新上线"场景的统一汇合点，其他散落判定算多余。

**背景（承接 S29 讨论中的隐患确认）**：节点端阈值仅存 RAM（重启回默认 3600）。改造前 `thresholdNeedsUpdate` 置位散落三处：

1. **平台主动设置**（`onenet_handler.cpp`）——用户在线设置，必须保留；
2. **LFS 加载**（`node_data.cpp`）——仅网关启动时触发；
3. **OTA 成功后**（`ota_handler.cpp`）——仅升级成功时触发。

漏洞：**节点单独重启/断电重连（网关一直在线）时，标志已被上次 ACK 清除** → 永不重发，用户设置随节点 RAM 丢失，直到节点下次数据帧上报默认值 3600。

**修复（收敛到 PONG 一处）**：

| 位置                                | 改动                                                                                                        | 解决什么问题                                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `lora_handler.cpp` PONG,APP 分支  | `thresholdValue>0`/`sensorDistanceValue>0` 时置位 + 重置重试计数，随后 `pushThresholdUpdate` 立即下发 | 节点每次重新上线都自动恢复用户设置，一处覆盖全部重启场景                                          |
| `node_data.cpp` LFS 加载          | 删除置位，只加载目标值                                                                                      | 重发时机统一由 PONG 决定，加载不再直接置位                                                        |
| `ota_handler.cpp` OTA_COMPLETE    | 删除"升级后重新标记下发"块                                                                                  | 升级后节点重启必回 PONG，已被 PONG 兜底覆盖                                                       |
| `onenet_handler.cpp` 平台设置置位 | **保留**（唯一例外）                                                                                  | 节点在线设置不经过 PONG（走快速路径直接 DATA），且服务调用需等 ACK 同步回复平台，删则在线设置失效 |

**效果**：所有重启/重连/升级场景下用户阈值自动恢复；未设置过的节点不打扰。副作用：节点断线抖动恢复时可能重复下发同一值（无实质影响，ACK 后清标志）。仅网关需重烧。

### 15.13 S31：下线时机颠倒 + ACK 全量匹配因脏字节误判（先代下线再探测 / strstr 关键字匹配）

> 本批对应第 2.3.4 节新增 S31 条目（网关侧）。用户定调两条：**① 设备重启后应先对节点做下线操作，再 PING 探测，不许打时间差交错运行；② ACK 确认改关键字匹配而非全量匹配——无线数据脏点没关系，关键数据没丢就能用**。

**背景 1（下线时机颠倒）**：网关启动时 `lora_triggerDiscovery` 在 `onenet_init` 前手动触发节点发现扫描，PING 先发出；MQTT 连接成功回调虽统一置 `logoutPending`，但串行主循环中 PING 已发出未等结果，MQTT 周期任务随即发下线。实测日志 `[01:54:45.475] PING-> 节点1` → `[01:54:45.538] 子设备下线 节点1` 仅隔 ~60ms，**先探测后下线**顺序颠倒。表面无碍只因 LoRa 有时差（节点 PONG 在下线操作后才回），但平台会话短暂保持"伪在线"，日志交错脏乱。

**背景 2（ACK 脏字节误判）**：节点发送内容本身干净（`bsp_lora.c` L326-344 `LoRa_Node_SendAck` 逐字节构建），但半双工无线链路 payload 首字节受干扰（实测 `�AT+ZombieThreshold`），网关 `strcmp` 全量匹配失败 → 判 ACK 失败 → 重试下发。实测阈值在同一值下连续下发 2 次。

**修复**：

| 位置                                | 改动                                                                                                          | 解决什么问题                                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `onenet_handler.h/.cpp`           | 新增`onenet_logoutPending()`：`!mqtt.connected()` 早退 + 循环扫描 `logoutPending`                       | 判定"存在待代下线且 MQTT 在线"；断网时返回 false，不卡死 LoRa 轮询                                                         |
| `lora_handler.cpp` section 4 开头 | `if (onenet_logoutPending()) return gotData;` 门控                                                          | 全部代下线完成前暂停发下一条轮询命令（控制命令队列/OTA 不受影响），保证 MQTT（重）连后**先全部代下线、再 PING 探测** |
| `Gateway.ino` activeEvent         | 条件增加`\|\| onenet_logoutPending()`                                                                         | 待下线期间按 UPLOAD_MIN_INTERVAL_MS(1s) 快排，缩短 lora_tick 暂停窗口                                                      |
| `lora_handler.cpp` ACK 分支       | 三处`strcmp` → `strstr` 包含匹配命令名（"ZombieThreshold"/"SetLed"/"SensorDistance"，不含 `AT+` 前缀） | 容忍首字节/前缀字节污染：只要关键字未丢失即确认成功，避免无谓重发；命令名长且互不为子串，无跨命令误配                      |

**效果**：重启/重连后平台节点先统一下架、再恢复 LoRa 探测，日志时序干净；ACK 脏字节不再引发重复下发。副作用：平台上行限速 ≤1 次/s，N 节点待下线时需 N×1s 才能全部下架完成，期间 LoRa 轮询暂停（下架越快恢复越快）。仅网关需重烧。

### 15.14 S32：两条阈值命令互斥短路，下发间隔整轮轮询（连续入队）

> 本批对应第 2.3.4 节新增 S32 条目（网关侧）。用户定调：**把需要下发的都连续投递，别让两条命令隔着一整轮轮询**。评估后放弃协议级合并一帧（`AT+SETCFG`）——收益仅在低频的"重连恢复配置"场景省 1 次往返，却要双端改协议 + 处理平台单条设置路径并存 + 未来配置项扩展成本；选网关侧连续入队，节点端零改动。

### 15.15 S33：ACK 归属靠轮询指针猜测致误归属（lastCmdNodeId 根修 + 关键字双重校验）

> 本批对应第 2.3.4 节新增 S33 条目（网关侧）。用户定调：**先问清楚 ACK 到底是谁回的，再谈清标志**——上行 ACK 帧不自带节点地址，网关原靠轮询上下文 `currentNode` 猜归属，命令队列投递与轮询指针推进节奏不同步时必然张冠李戴；并明确只需修网关、节点端零改动（已核查节点端 ACK 帧结构确认无责）。

**背景**：ACK 帧（`LORA_FRAME_ACK`）上行内容为节点回显的命令文本，不带节点身份字段，网关 `handleCompleteFrame` 原以 `uint8_t nodeId = currentNode` 猜测归属。命令队列投递（section 2）与 `currentNode` 推进节奏不同步——发现扫描收 PONG 后 `pushThresholdUpdate` 入队命令，队列投递发出后轮询指针可能已因上一轮响应处理前移到别的节点。实测日志（发现扫描）：

```
50.053  PING-> 节点1 → 收 PONG,APP → pushThresholdUpdate 入队两条命令
50.053  TX 0x0001 OK（ZombieThreshold 发节点1）
50.110  收到<- 节点1 确认: ZombieThreshold → 节点1 阈值下发成功
50.219  TX 0x0001 OK（SensorDistance 发节点1）        ← 地址正确
50.342  收到<- 节点2 确认: SensorDistance           ← 误归属！实为节点1 回复
50.342  节点2 超声波距离阈值下发成功                  ← 清的是节点2 的 slot 标志
50.342  节点发现扫描完成, 恢复正常轮询
50.792  RX 状态机超时 (state=3, 501ms)
52.310  节点1 在线, 下发超声波距离阈值=5cm (重试2/3)   ← 节点1 标志残留
52.495  收到<- 节点1 确认: AT+SensorDistance → 真正成功
```

根因链：① `nodeId = currentNode` 靠猜；② 50.342 处理 ACK 时 `currentNode` 已推进到节点2（命令队列投递与轮询指针推进不同步）；③ `strstr("SensorDistance")` 纯内容匹配，不校验目标节点一致性；④ 误归属清掉节点2 标志，节点1 的 `sensorDistanceNeedsUpdate` 残留 → 52.310 自动重试 2/3 才真正成功。

**修复**：

| 位置                                                                                           | 改动                                                                                                                     | 解决什么问题                                                                                             |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `lora_handler.cpp` 新增静态变量                                                              | `lastCmdNodeId`（最近投递命令目标节点）/ `lastCmdKey`（最近投递命令关键字）                                          | ACK 归属与校验的依据从"轮询指针"改为"实际投递记录"                                                       |

| ACK 归属（`handleCompleteFrame`）                                                            | `header==ACK && lastCmdNodeId!=0xFF` 时 `nodeId = lastCmdNodeId`                                                     | 根修：50.342 场景 ACK 归属节点1 而非已推进的节点2                                                        |
| ACK 分支                                                                                       | `ackKeyMatches` 不符即丢弃（PONG↔PING、ZombieThreshold/SetLed/SensorDistance 与投递关键字必须一致；未知内容保底放行） | 跨命令/跨节点误配拦截                                                                                    |

### 15.16 S34：日志冗长无分级，异常无标记，空口质量不可量化（分级 + 统计汇总 + 语义名）
