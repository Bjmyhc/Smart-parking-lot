## 三、根因 1：0 维标量参数 —— 真正让板子崩掉的那一发

### 3.1 崩溃现场（v1 的日志）

```
I (1031) plate: === LPRNet on ESP32-S3 ===
Guru Meditation Error: Core 0 panic'ed (LoadProhibited). Exception was unhandled.
PC       : 0x420979e5  (fbs_model.cpp:649 get_operation_parameter)
A2       : 0x00000000   ← 待取的目标指针为 NULL
A15      : 0x69726156   ← ASCII "Vari"（PPQ_Variable_ 前缀）
EXCCAUSE : 0x1c         ← LoadProhibited
Backtrace:
  0x420979e2  fbs::FbsModel::get_operation_parameter()  @ fbs_model.cpp:649
  0x42033a1c  dl::Model::load(fbs::FbsModel*)            @ dl_model_base.cpp:170
```

注意：**崩溃发生在节点循环内部取参数的那一行**（`dl_model_base.cpp:170`），而且**没有**打出 `Do not support XXX` 的日志。

### 3.2 反汇编结论：649 行就是在读 dims，且 a2 为 0

`managed_components/espressif__esp-dl/fbs_loader/lib/esp32s3/libfbs_model.a` 里带了 DWARF 行号信息，可以直接把 `get_operation_parameter()` 定位到源码行：

```
fbs_model.cpp:649 (discriminator 1)
   378: beqi  a9, 4, 37e      ; 类型判断
   37b: j     429
   37e: l32i.n a9, a2, 0      ; <== 从 a2 指向的向量读第 0 个元素
   380: bgei  a9, 1, 386
   383: j     489             ; 越界/异常出口
fbs_model.cpp:650
   386: movi.n a10, 56        ; 构造 shape (std::vector<int>)
```

`A2 = 0x00000000` 与 `l32i.n a9, a2, 0` 完全对上：**该参数张量的 dims 向量是空的，`data()` 返回 NULL，函数没有先判空就直接取 `dims[0]`。**

### 3.3 模型侧证据：这 20 个参数确实存在，并且第一个消费者就是"合法算子"

离线解析 v1 的 `lprnet_s3.espdl`（已备份为 `tools/out/lprnet_s3_old_pow_reducemean.espdl`）：

```
$ python tools/inspect_espdl.py tools/out/lprnet_s3_old_pow_reducemean.espdl
!! 20 个 0 维 (dims 为空) 标量参数 ---- 板端取参数时空指针 (实测崩溃点)
   PPQ_Variable_2, _3, _4, _5, _16, _17, _19, _20, _22, _23, _25, _26,
   _28, _29, _31, _32, _34, _35, _37, _38
```

形如 `%PPQ_Variable_17[INT8, scalar]`、`%PPQ_Variable_2[FLOAT, scalar]`。

而节点清单里，**第 4 个节点**（远在第一个 `Pow`（第 6 个）之前）就是：

```
[ 4] DequantizeLinear   PPQ_Operation_4
     in : /AveragePool_output_0, PPQ_Variable_28, PPQ_Variable_29
```

`DequantizeLinear` 在 esp-dl 里是**已注册**的算子（映射到 `RequantizeLinear`，见 `dl_module_creator.hpp:130-132`）。于是执行顺序变成：

1. 节点 0~3（Conv / MaxPool / AveragePool）参数正常，通过；
2. 节点 4 `DequantizeLinear` 的两个输入被判定为参数 → 走 `get_operation_parameter()`；
3. 这两个参数是 **0 维标量** → `fbs_model.cpp:649` 解引用空 dims → `LoadProhibited`，寄存器里残留的正是参数名字符串 `PPQ_Variable_...` → `A15="Vari"`。

**所以 v1 文档 3.4 节那条"未验证次要猜想"是根因本身**，而不是次要问题；它同时解释了"为什么崩在取参数处""为什么没有 `Do not support` 日志""为什么 A15 是 Vari"。

## 四、根因 2：缺算子（v1 的结论，已证实）

判定依据（唯一标准）：运行端注册表 `managed_components/espressif__esp-dl/dl/module/include/dl_module_creator.hpp` → `register_dl_modules()`，共 **47 个**算子。

旧模型 46 个节点，其中 9 个不在表内：

```
Pow          x 4
ReduceMean   x 5
```

`Pow` / `ReduceMean` 没有对应模块，`ModuleCreator::create()` 返回 `nullptr`，`Model::load` 会打印 `Do not support Pow, please implement and register it first.` 并返回 `ESP_FAIL`。**这是与根因 1 完全独立的第二个致命问题**：即使把 0 维标量修掉，只要这两个算子还在，模型一样加载不起来。

来源是原始 `LPRNet.py` 的前向写法：

```python
f_pow  = torch.pow(f, 2)                 # -> Pow        (未注册)
f_mean = torch.mean(f_pow)               # -> ReduceMean (未注册, 且产出 0 维标量)
f      = torch.div(f, f_mean)            #    Div 合法, 但分母是 0 维标量 -> 触发根因 1
logits = torch.mean(x, dim=2)            # -> ReduceMean (未注册)
```

**注意这两条根因是同一条代码链的两面**：`torch.mean(f_pow)` 既产出了不支持的 `ReduceMean`，又产出了 0 维标量常数。这也说明 v1 的"导出端与运行端能力不匹配"这个判断方向是对的。

## 五、根因 3：输入张量布局 CHW / NHWC（v1 完全没提，隐蔽但致命）

esp-dl 内部张量一律 **NHWC**，证据链：

- `vision/image/dl_image_preprocessor.cpp:15-18`：断言 `m_model_input->shape[3] == m_mean.size()`，并用 `shape[1]*shape[2]*shape[3]` 计算像素数 → `shape[1]=H, shape[2]=W, shape[3]=C`；
- 本模型输入声明就是 `%input[INT8, 1x24x94x3]`、`exponents: [-7]`（第 3 维 = 3 通道）；
- `TensorBase::assign()`（`dl_tensor_base.cpp`）只做**逐元素搬运 + 量化**，**不做 NCHW↔NHWC 重排**。

旧 `main.cpp` 用 `TensorBase({1,3,24,94})` 装载 CHW 的 `test_input.bin`，旧 `dump_test_input.py` 也确实是 `np.transpose(img,(2,0,1))` 输出的 CHW，和 `main.cpp` 注释自相矛盾。这种错误**不会报错、不会崩**，只会得到一堆乱码车牌——比崩溃更难查。

## 六、修复内容

### 6.1 模型侧：等价改写前向，不重训（`tools/lprnet_s3_model.py`）

| 原写法 | 替换写法 | 引入的算子 |
|---|---|---|
| `nn.MaxPool3d`（4D 输入，ONNX 非法） | `ChannelSliceMaxPool2d`：通道抽样 + `MaxPool2d` | `Slice` + `MaxPool` |
| `torch.pow(f, 2)` | `f * f` | `Mul` |
| `torch.mean(f_pow)`（全维均值，产出 0 维标量） | `GlobalAveragePool` + `Conv2d(1x1, 权重恒为 1/C)` | `GlobalAveragePool` + `Conv` |
| `torch.mean(x, dim=2)` | `F.avg_pool2d(x, kernel_size=(H,1)).squeeze(2)` | `AveragePool` + `Squeeze` |

要点：
- 全部替换**数值等价**，`state_dict` 与原版逐键一致，直接加载 `weights/Final_LPRNet_model.pth`，**不需要重新训练**；
- 1x1 卷积权重放在普通 dict（`self._mix_cache`）而不是 buffer，避免污染 `state_dict`；
- 链条里**没有 `Reshape`/`Transpose` 这类布局切换算子**，对 esp-ppq 的 NHWC 改写最安全；
- 改写后不再产生 0 维标量，也彻底躲开根因 1。

### 6.2 工具链（`PlateRecognitionIDF/tools/`，全部用训练工程 venv 跑）

| 脚本 | 作用 |
|---|---|
| `lprnet_s3_model.py` | 部署友好模型 `LPRNetS3`（等价改写 + 权重兼容） |
| `export_onnx_s3.py` | 第①关：原版/S3 数值等价性 → 导出 ONNX + `onnx.checker` → onnxruntime 一致性 → 算子白名单体检 |
| `quant_espdl_s3.py` | 第②关：esp-ppq 量化（`calib_algorithm='minmax'`，官方默认 kl 会把归一化分母裁掉、精度暴跌），可选 `--eval-n` 做 int8 精度体检 |
| `inspect_espdl.py` | 离线体检 `.espdl`：算子白名单 + **0 维参数** + **参数数据**三道门禁（有问题 exit 2），`--list-nodes` / `--graph` / `--initializers` |

### 12.2 预处理与训练逐位对齐（关键结论）

训练链路（`tools/quant_espdl_s3.py:41-52` == `predict.py`）是：

```text
cv2.imdecode(...)  -> BGR  -> cv2.resize(94x24, INTER_LINEAR) -> (x-127.5)*0.0078125
```

模型输入 `exponents: [-7]` ⇒ `scale = 2^-7` ⇒ `mean = 127.5, std = 128`。
板端把这三步压成 **一张 768 字节 LUT**，交给 `dl::image::resize()` 在缩放的同时逐像素查表（一次读源、一次查表、一次写目标）：

```cpp
lut[c*256+v] = clamp(round((v-127.5)/128 * 128)) == clamp(round(v-127.5))
dl::image::resize(src /*RGB565 640x480*/, dst /*模型输入张量 int8 94x24*/,
                  dl::image::DL_IMAGE_INTERPOLATE_BILINEAR,
                  DL_IMAGE_CAP_RGB565_BIG_ENDIAN | DL_IMAGE_CAP_RGB_SWAP,
                  norm_lut, {}, &scale_x, &scale_y);
```

两个**极易搞反**的点，已从源码逐位核对：

1. **通道序要 BGR，不是 RGB。**
   `dl_image_color.hpp` 的 RGB565→RGB888_quant 在 `DL_IMAGE_CAP_RGB_SWAP` 分支写
   `dst[2]=R, dst[1]=G, dst[0]=B`，即输出 **BGR**，与 cv2 一致。
   （缩放后的那一步量化 `convert_pixel(Q, pix, 0, norm_lut)` 的 `caps` 被 esp-dl 写死成 0，
   不再交换通道 —— 这里恰好是我们要的行为：顺序原样保留。）
2. **`caps` 必须带 `DL_IMAGE_CAP_RGB565_BIG_ENDIAN`。**
   该 flag 的语义是「**按大端宏解析**」，不是「数据是小端」。判据：
   `conversions/to_jpg.cpp:34` 的 `rgb565_big_endian=true`（esp32-camera 默认，也就是原上传链路能出正确颜色的那条分支）
   其公式 `R=src[i]&0xF8 / G=((src[i]&7)<<5)|((src[i+1]&0xE0)>>3) / B=(src[i+1]&0x1F)<<3`
   与 `dl_image_define.hpp:17-19` 的 `DL_IMAGE_BIG_ENDIAN_RGB565_*` 宏**逐位相同**
   （`src` 的 `uint16` 视图是 CPU 小端读出的）。

#### 12.2.1 两处最容易搞反的判定，已穷举验证（离线，不依赖板子）

用等价的浮点/整型复算，对全部 65536 个 RGB565 取值和 256 个 LUT 项做了穷举：

| 检查项 | 结果 |
|---|---|
| `DL_IMAGE_BIG_ENDIAN_RGB565_BIT1/2/3` 宏 vs `to_jpg.cpp` 的 `rgb565_big_endian=true` 分支 | **65536/65536 完全相同**（所以 `caps` 必须带 BIG_ENDIAN） |
| 同一批数据用 `DL_IMAGE_LITTLE_ENDIAN_*` 宏 | 只有 256/65536 恰好相同 ⇒ 端序选错会大面积错色 |
| `RGB_SWAP` 之后三通道 == `[B,G,R]` | 65536/65536 成立 |
| 板端 LUT == esp-dl `quantize<int8_t>()`（S3 取整） | 256/256 相同 |

> **顺带修掉一个真 bug**：一开始 LUT 用的是 `lroundf()`（C 标准里"半值远离 0"），
> 而 esp-dl 在 S3 上用的是 `tool::round = (int)floorf(value + 0.5f)`（半值向 +∞，见 `dl/tool/src/dl_tool.cpp:69-88`）。
> 由于 `(v-127.5)/128*128` 恰好精确等于 `v-127.5`（256/256 精确），每个取值都落在"半值"上，
> 于是 `lroundf` 版会在 **v ≤ 127 的全部 128 个取值上整体差 1 个 LSB**（如 `v=0`：`-128` vs 正确 `-127`），
> 与已验证的板端 `model_input->assign(float)` 链路不一致。现已改成与 esp-dl 逐位一致的写法：
> `lut[v] = clamp(floor(((v-127.5)/128*128) + 0.5))`，本模型下等价于 `clamp(v-127)`。

```text
I plate: 输入张量 int8: min=-128 max=127 mean=-42.2 (n=6768)
I plate: 裁剪块均值(像素 0..255): B=84 G=85 R=85  (蓝牌应 B 最大)
I plate: 裁剪块缩略图 (左->右, 上->下):
:-::-:::::::::::::-:.:::::::::-:::::::::::-::::
```

21 次裁剪，`B/G/R` 全部几乎相等（78~101），缩略图一律只有 `:-` 两档、**看不到任何字符笔画**。
当时据此推断"白平衡/曝光把蓝牌洗白了"——**这个推断是错的。**

### 14.2 根因：`model->run()` 之后，图输入张量的内存已经还给了内存池

`MemoryManagerGreedy` 按"张量生存期"复用显存，而**图输入张量的生存期终点就是它的最后一个消费者**：

```cpp
// managed_components/espressif__esp-dl/dl/model/src/dl_memory_manager_greedy.cpp:117-131
for (int j = 0; j < op_inputs.size(); j++) {
    ...
    auto out_iter = std::find(graph_outputs.begin(), graph_outputs.end(), name);
    if (out_iter == graph_outputs.end())
        tensor_info[index]->update_time(i + 1);   // free this tensor next step
}
```

于是 `run()` 里任何一个被排到这块内存上的中间张量都会往里写数据。而我们的诊断偏偏放在 `run()` **之后**：

```cpp
model->run();
...
log_input_stats(model_input);   // ← 此刻 model_input->data 已经不是裁剪块了
log_crop_diag(model_input);
```

结论：那三行打印的是**别的张量的数据**，与被喂进模型的东西毫无关系
（"三通道几乎相等"＝读到了一块激活值）。**"裁剪块质量如何"这件事，之前从来没有真正测到过。**

### 14.3 反证：真车牌在同一套缩略图里是清清楚楚的

拿训练集里真实的 94x24 紧裁剪样张（`LPRNet_Pytorch/debug_resized.png`、`dbg_*_resized.png` 共 5 张）
离线复现同一套渲染，字符笔画一目了然，通道均值也是蓝底该有的样子：

```text
===== dbg_precise_resized.png (94x24) 通道均值 73.0 / 139.3 / 221.8 =====
=-+=--=--==-------==----------------------:::.:
+=**=+==%%%*-----#%%*----#+----*%:---=%=----#=:
-+++=+:**-=%=---+#--%=--+%:---=%-----%*----*#::
-****+-+==-%+---*+--*+-=%-----#*----+%:---=%---
...
```

即：**只要裁剪块真是车牌，这三行诊断一定看得见字符**；看不见 ⇒ 当时它们没在描述裁剪块。
另一条独立证据：4 次完全正确的 `京Q06666` 不可能来自"一片灰"的输入。

| 改动 | 位置 | 说明 |
|---|---|---|
| 诊断前移 | `main.cpp` `recognize_once()` | `帧…/输入张量/裁剪块均值/缩略图` 全部在 `model->run()` **之前**打印，并留了大字警告注释，禁止再挪回去 |

### 14.5 新增诊断（都是"喂给模型之前"的真数据）

| 打印 | 怎么读 |
|---|---|
| `整帧均值(像素 0..255): R=.. G=.. B=..` | 直接来自相机帧。蓝牌占据画面时 **B 应明显最大**；三通道相等说明画面本身没有蓝色主导 |
| `车牌色像素 n/307200 = x%` | 全帧通过 `auto_crop_predict.py` 那套蓝/绿阈值的像素占比。只有一小块车牌时应在 1%~10% 量级；>30% 基本是偏色或阈值失效 |
| `候选1..5: … 宽高比 … 密度 … 得分 …` | 得分前 5 的连通域。**密度 = 域格数 / 外接框格数**：真车牌接近 100%，反光/阴影拼出的散块很低 → 一眼看出是不是"又大又稀"的假目标抢了第一名 |
| `ROI: … 宽高比 2.41 (训练样张 94x24=3.92) 框内密度 62% …` | 训练集是 94x24 = **3.92**；框的比例离 3.92 越远，缩放到 94x24 时字符被横向拉得越厉害 |
| `车牌色掩码 (1 字符 = 8x8 像素)` | 80x60 ASCII：`#`=车牌色、`,`=零星、`.`=无、`+`=选中框边框。开机前 3 次会话 + 每次定位失败时打印。**这张图能直接看住"框有没有套在车牌上"** |

原来的 `裁剪块均值` / `缩略图` 保留 —— 前移之后它们才变成有效的证据。

### 14.6 结论：**先不要自己采数据重训**

1. **模型本身没问题**：`data/official_val`（94x24 紧裁剪）上 float 87.50%(175/200)、int8 83.00%(166/200)。
2. **错误形态不是"认错字"**：出现了 4 次完全正确的 `京Q06666`；错误样本多是**多字/漏字**，且同一个框
   前后两帧给出不同结果（276x102 那两次：`沪T6966FTP` / `粤T666FTP`）——典型的"喂进去的图不对/不稳定"，
   而不是"这个字没见过"。
3. **重训治不了 ROI**：框没套准、宽高比 2.1~2.9（应 3.92），这两件事与模型参数无关。
4. **重训的成本不是"拍几张照片"**：要走完 `train_LPRNet.py` → `tools/export_onnx_s3.py` →
   `tools/quant_espdl_s3.py` → 换 `main/models/lprnet_s3.espdl`，三道门禁都要过，还要重新标定 int8 精度。

**什么时候才值得重训**：当 `车牌色掩码` 显示框**确实紧贴车牌**、`框内密度` 接近 100%、
`缩略图` 里字符清楚可辨，而识别仍然错 —— 那才是数据分布问题（相机色彩/曝光/分辨率让笔画与训练集差太远）。
届时补 50~100 张实拍、混进现有 800 张一起微调即可，不必从零训练。

### 15.2 颜色链路全部正确（第十四节的修复生效）

`裁剪块均值` 不再是"三通道几乎相等"，而是真正的蓝牌色（`B=222 G=180 R=112`、`B=241 G=195 R=105`，**B 最大**）。

### 15.3 暴露的问题一：框普遍"太高" —— 宽高比 2.1~2.7，而训练样张是 3.92

> **口径更正（见 16.2）**：3.92 是**模型输入张量** 94x24 的比例，不是"框要去凑的目标"。
> 训练裁剪本身是**车牌四角摆正图**（`extract_ccpd.py:76-90`），真实车牌本体约 **3.1~3.4**
> （`auto_crop_predict.py:75` 的注释也写 3~3.4）。本节"框太高 => 字符被压扁"的结论仍然成立，
> 只是"理想值"应当是 ~3.14 而不是 3.92。

19 次会话里 **没有一次**框的宽高比接近 3.92（`extract_ccpd.py:76-90` 用文件名里的 4 个角点做了 `warpPerspective`，
所以训练集是**摆正**的车牌）。板端用轴对齐外接框：车牌一斜，框高就等于"车牌高 + 宽度 x sin(倾角)"，
再缩放到 94x24 时横向被拉伸 1.5 倍以上 —— 这与模型参数无关，**重训也治不了**。

### 15.4 暴露的问题二：密度是最强的"真/假目标"信号，而得分公式只认面积

- 密度 >=62% 的 4 次：`京Q06666` (对) / `闽Q粤J666` / `闽T666FP`（只差 1~2 字）；
- 密度 <=33% 的 8 次：全乱码（`沪1粤鄂P66`、`粤Q粤6粤粤`、`闽Q粤粤6粤浙6`…）。
  这些框都是**又大又稀**的散块抢下第一名：`score = area / (1 + |ratio-3.4|)` 只认面积，
  例如 `x[64,392) y[356,480) 密度 29% 得分 416`，而同一次里 `x[68,132) y[424,456) 密度 78%` 只有 42 分。
- 同一块车牌连拍三次：`京Q06666` / `云QC鄂666` / `新QC666浙`，三次的框几乎一样（密度 83/83/72%，比值 2.34/2.34/2.21）。
  **结果会跳 说明"喂进去的图不稳定"，不是"这个字没见过"。**

### 15.5 暴露的问题三：亮牌照整体掉出阈值（待办，本轮不动）

`t=52901/57942/62989` 三次：`整帧均值 R=153 G=125 B=91`、车牌色像素仅 0.3~0.4%，掩码上只剩一条斜向的稀疏点迹，

### 15.6 本轮改动（已过离线语法检查：xtensa-g++ `-fsyntax-only -Wall`，exit=0）

| 改动 | 位置 | 说明 |
|---|---|---|
| 旋转矩形 + 摆正（**P5.1**） | `main.cpp` `roi_fit_rotated()` / `sample_quad_to_input()` | **每个候选**都先用 **PCA** 拟合旋转矩形（代替 `cv2.minAreaRect`），按原脚本比例（左右 1%/上下 3%）在 u/v 上收缩得到四角；新增逐点双线性采样器直接写 int8 输入张量，等价训练链路的 `warpPerspective` |

所以不存在"改几何把选框改坏"的风险；密度 <45% 的假目标观测上会自动退回旧路径。


### 15.8 下一批日志要盯的三行 / 待办

1. **`摆正(旋转矩形): 长宽比 x.xx 填充 xx% 倾角 x.x°`**（本轮新增）。理想：长宽比 3.3~4.2、填充 >=70%、倾角与肉眼所见一致。
   若这一行变成 `旋转拟合不可用 -> 退回轴对齐裁剪`，说明连通域密度不够（15.4），下一步就做"阈值放宽 + 密度过滤"。
2. **`>>> RESULT` 后面补打的掩码**（本轮新增）。只在结果不像车牌时打（开机后共 2 次），配合 1:1 缩略图看"框有没有套住车牌"。

4. 密度过滤（`c_dens[k] >= 0.5`，或对 score 加权）已经**有数据支撑**（15.4），但它属于"改选框逻辑"，与本轮"只改几何"分开做，便于归因。

5. 结论不变：**暂时不要自己采数据重训**（14.6）。等 15.8 第 1 条显示"框已摆正、填充很高、缩略图能读字"而仍然认错，才是数据分布问题。

### 15.9 离线自检脚本抓到的一个设计缺陷（已修）：倾斜车牌会被整块判死

`tools/roi_geom_selftest.ps1`（新增：格点级 1:1 复刻 `roi_locate()`，纯 PowerShell，不依赖摄像头/板子）
写完立刻报出一条致命现象：**车牌只要斜得明显一点，整张图就直接"没有 ROI"**。

原因：原脚本的宽高比过滤 `2.0 <= ratio <= 6.5` 是加在 `cv2.minAreaRect` 的**旋转矩形**上的，
而第一版移植把它加在了**轴对齐外接框**上。倾斜会让轴对齐框变高：

| 车牌 | 真实比例 | 斜 20 度后的轴对齐 bbox | 比例 | 结果 |
|---|---|---|---|---|
| 240x64 | 3.75 | 247x142 | **1.74** | 被 `ratio < 2.0` 判死 |
| 200x56 | 3.57 | 225x152 | **1.48** | 同上 |
| 220x60 | 3.67 | 246x156 | **1.58** | 同上 |

这正好解释了实测日志里"有些次框是 2.1~2.6、有些次直接没有 ROI"的分布：
**不是车牌太小，是过滤器把倾斜的整块丢掉了**。
修法：把旋转拟合提到候选循环里（每个候选都算），**优先用旋转比例过滤和打分**，
拟合不出来才退回轴对齐比例（见 15.6 表格）。

## 十七、P5.3：连续实时识别（识别频率 ~0.6 次/秒 => ~1.1 次/秒）（2026-09-28）

### 17.1 结论

原来的节奏是"每 5 秒拍一次"，而且**单次里还有 1 秒是纯粹空转**。现在改成背靠背连续识别：
**周期 200ms < 单次耗时 => 一拍完立刻拍下一张**，实际约 **1.1 次/秒**（0.9s 一轮）。

⚠ **频率的硬上限是推理本身 0.40s**，也就是最多 ~2 次/秒。想再快只能换更小的模型或降输入分辨率 ——
调周期参数是没用的，这一点先说清楚，免得后面白折腾。

### 17.2 时间预算（改前 / 改后，都是实测或按代码可算）

| 环节 | 改前 | 改后 | 依据 |
|---|---|---|---|
| 丢帧 (`camera_discard_frames`) | **10 帧 x 100ms = 1.00s** | **3 帧 x 100ms = 0.30s** | 代码里每帧 `vTaskDelay(100)`；10 帧明显过量，缓冲只有 2 张 (fb_count=2) |
| ROI 定位 | 0.12~0.16s（打掩码时 0.55s） | 0.12~0.16s | 日志 `定位 137/124/138/164 ms`；`548~570 ms` 那几次是在打 80x60 掩码 |
| 预处理 | 0.004~0.011s | 同 | 日志 `预处理 4~11 ms` |
| 推理 | 0.40s | 0.40s | 日志 `推理 397~398 ms`（固定的，模型成本） |
| 串口打印 | 最多 ~0.6s | ~0.05s | 1:1 缩略图 24 行 + 掩码 4800 字符 ≈ 420ms；精简模式不再打 |
| 空等 | 周期 5s - 单次 ~1.7s = **3.3s** | **0**（背靠背） | `next_auto = now + 200ms`，`now` 是开工前取的时间戳 |
| **合计** | **~1.7s/次，但每 5s 才跑一次 => 实际 0.2 次/秒** | **~0.9s/次 => ~1.1 次/秒** | |

### 17.3 改动（4 处，都在 `main.cpp`）

| 改动 | 位置 | 说明 |
|---|---|---|
| 周期 5000 -> 200 ms | `AUTO_PERIOD_MS` (`main.cpp:67`) | 周期小于单次耗时 => 连续。想放慢直接调大（5000 = 每 5s）；0 = 只在开机 + 按 BOOT |
| 丢帧 10 -> 3，启动时 12 | `CAM_DISCARD_FRAMES` / `CAM_WARMUP_FRAMES` (`main.cpp:223`) | 10 帧是"每次识别都等 1 秒"，没必要 —— fb_count=2，丢 3 帧就足以拿到新帧。启动/重启摄像头时反而**多丢** 12 帧等 AE/AGC 稳定 |
| BOOT 按钮改中断锁存 | `boot_btn_isr()` / `app_main()` | 连续模式下短按会被 0.9s 的忙等吞掉；改成下降沿中断置标志 + 电平轮询兜底 |
| 打印分两档（`verbose`） | `roi_locate()` / `recognize_once()` | **详细模式**（开机第 1 次 + 按 BOOT）：掩码 + 1:1 缩略图 + 输入统计，和以前一样。**精简模式**（定时连续）：只打 `会话 / 整帧均值 / 候选 / ROI / 摆正 / RESULT / 耗时` |

为什么必须分档：1:1 缩略图 24 行 ≈ 200ms、一张掩码 4800 字符 ≈ 420ms @115200，
在 1 次/秒的节奏下这些日志会让串口成为瓶颈，而且刷屏到根本看不清结果。

### 17.4 改后的日志长什么样

连续模式每轮约 6~8 行（不再有缩略图和掩码）：

```text

摆正(旋转矩形): 长宽比 3.07 (真车牌约 3.1~3.4) 填充 77% 倾角 -1.4° 四角 (43,245)(539,233)(543,388)(47,400)
```

### 17.5 上板要验证的四点

1. **丢 3 帧够不够**：如果出现"画面明显滞后于当前场景"（例如手挪开了还拍到旧位置），把 `CAM_DISCARD_FRAMES` 调到 5。
2. **开机第一帧是否偏暗**：预热已从自动的 3 帧提到 12 帧，正常应该够；如果第一次识别整帧均值明显偏低，把 `CAM_WARMUP_FRAMES` 加到 20。
3. **串口能不能吃住**：1 次/秒 x ~8 行，115200 完全够；若 monitor 出现丢行，说明打印量还是大，可把候选行也并进 `verbose`。
4. **BOOT 按钮改成中断锁存了**（P5.3 一并改的）：连续模式下每轮要跑 ~0.9s，短按很容易正好落在那 0.9s 里被漏掉，
   所以给 GPIO0 装了下降沿中断（ISR 只置一个 `volatile bool`），循环下一圈消费；**同时保留电平轮询兜底**，ISR 装不上也不影响用。
   若上板后摄像头初始化失败或反复重启，第一件事是回退这一处（把 `io.intr_type` 改回 `GPIO_INTR_DISABLE` 并删掉 `gpio_install_isr_service` 那几行）。

### 17.6 顺带说明：为什么"实时"只能到 1~2 次/秒

- 模型是 int8 的 LPRNet，24x94x3 输入，在 ESP32-S3 上单次 **398ms** —— 这是纯算力成本，和代码无关；
- 再快的三条路（按代价排序）：**降输入分辨率**（如 320x240 + 网格改 4 格 -> 定位更快，但最远识别距离腰斩）、
  **换更小的模型**（要重训，且当前 14.6 的结论是暂不重训）、**多核并行/双缓冲流水**（把"抓帧+定位"和"推理"重叠，理论上能逼近 0.4s/次，
  但要改架构，收益 0.9s -> 0.5s，不划算）。

结论：**1.1 次/秒已经是这套硬件+模型下的合理实时值**；要"录像级"流畅（>10 次/秒）需要换芯片或换更轻的模型，
不是这一轮能解决的事。

## 十八、P5.4：连续实时的第一批现场数据（105 轮 / 92 秒）——"准确率扎心"的两个根因（2026-09-28）

### 18.1 先确认实时本身没问题

### 18.2 根因一（主因）：**车牌被画面边缘切掉了** —— 贴边 25 轮里 24 轮是乱码

98 轮有候选框，其中 **25 轮**（26%）的连通域**顶到了画面右边缘**（原始框 x2 = 640，去掉 1% 边后打印成 636）。
连通域贴边 = 车牌有一截在画面外，裁出来的图必然缺字：

| 贴边的 25 轮结果 | 轮数 |
|---|---|
| 乱码 / 缺字（`粤J999`、`闽T6S6F`、`粤T666F`、`闽Q粤浙66`…） | **24** |
| 侥幸读对（`粤T666FP`） | 1 |

对照：**没贴边**的轮次里同样大小、同样比例（2.5~2.9）的车牌大部分能读对。所以"贴边"本身就是决定性的坏信号。
证据是日志里那两张掩码 —— 选中框（`+`）的右边框正好落在掩码的最后一列：

```text

27 .........................+..,.......,,,,,,,,,,,,,,++++++++++++++++++++++++++++++
28 .......................,.+########,,,##########,#########,,,,,#################+   <-- 右边框 = 画面最右
```

### 18.3 根因二：**省份汉字是模型自己的弱项**（不是定位的锅）

第 30~50 轮（21 轮）是这份日志里唯一"没贴边 + 大小合适（占屏 9~20%）"的一段，结果：

| 结果 | 轮数 | 说明 |
|---|---|---|
| `粤T666FP`（完全正确） | 5 | |
| `闽T666FP` / `粤T666P` / `粤T66P` / `闽T666P` … | 16 | **车身 6 位（T666*P）全对**，只有省份字认错、或漏掉中间的 F |

也就是说：**这一段的裁剪是好的，模型把后面 6 个字都读对了**，唯独"粤"这个字在 粤/闽/京 之间跳。
这跟 14.6 的基线对得上：紧裁剪样张上 int8 本来就只有 83%，而省份汉字是 CCPD（皖占九成）里最弱的一类。

⚠ **不要用"多帧投票"去修省份字**：这一段里 `闽` 出现得比 `粤` 还多（10 : 5），
投票会把错的选成对的。**这是系统性偏差，不是随机噪声**，只能靠数据/模型解决。

（P5.5 补充：这一段的"跳"里还混着**采样欠采样**的成分 —— 见 §19。先把这一条排掉，再看剩下多少真是模型的锅。）

### 18.4 顺带查清：`京Q06666_1.png` 这张样张本身是坏的

## 十九、P5.5：把"单点抽样"换成面积平均 —— 回答用户的两个问题（2026-09-29）

> 用户问：① 能不能不裁剪直接识别？② 能不能把裁剪后的像素大一点儿？

### 19.1 问题② 指到了真问题，但不是"像素不够"

先把口径摆出来（都在 `main.cpp`）：

| 量 | 值 | 谁决定的 |
|---|---|---|
| 模型输入 | 94x24 int8，**写死在模型里** | 训练时定的（`data/load_data.py:42` 的 `img_size`），端侧改不了 |
| 现场好帧里车牌在源图上的尺寸 | 约 304x108 px（占屏 10~20%） | 摄像头 / 距离 |
| 缩到 94x24 的倍率 | **3.2x4.5 倍降采样** | 上面两行 |

所以近处的牌**不是像素不够**，是 3~4 倍富余；真正不够的是**远处的牌**（开机那一帧只有 60x28 px，
是 1.6 倍上采样，插出来的都是虚像素）。

### 19.2 真正的漏洞：降采样时没有做平均（训练 / 端侧不一致）

- 训练链路：`data/load_data.py:42` 是 `cv2.resize(Image, self.img_size)`，默认 `INTER_LINEAR` ——
  缩小时 OpenCV 会把滤波核按缩放比放大，**等于对源像素做面积平均**（抗锯齿）；
- 端侧：`sample_quad_to_input()` 原来是**每个输出像素只取一个双线性点**，是点采样；
- 后果：320x102 降到 94x24，白字笔画（源图里只有 2~6 px 宽）会随采样相位**时有时无**。
  现场表现完全对得上 —— 同一块牌、框只挪了一格，结果就在 `粤T666FP` / `闽T666FP` / `粤T666P`
  之间跳、`F` 这种细笔画时有时无（18.3）。

### 19.3 改动（`main.cpp`）

`sample_quad_to_input()` 现在按"这个输出像素在源图上覆盖多长"决定子采样数：

1. 每个输出像素先求出单元的三条边 → 宽向 / 高向矢量长度 `len_x, len_y`（单位：源像素）；
2. `nx = clamp(round(len_x), 1, SS_MAX)`，`ny` 同理（`SS_MAX = 4`）；
3. 在单元内取 `nx*ny` 个子样点（子样点直接落在四边形上，**所以斜的牌也自动跟正**），取平均后再过 LUT；
4. **足迹 < 1 像素时 `nx=ny=1`，与改前逐字节等价** —— 远处的牌不会被弄糊。

日志多一个字段：`预处理 4 ms | 推理 397 ms | 面积平均 3x4`。
这个数字 < 1 就说明"牌太小、信息本来就不够"（别怪模型）；≥3 说明降采样重、抗锯齿正在起作用。

### 19.4 离线验证（机制级）

把新旧两套采样 1:1 翻成 JS，用合成的蓝底白字车牌（320x102 → 94x24，同现场尺寸）做对照：

| 实验 | 旧（单点抽样） | 新（面积平均） |
|---|---|---|
| 整幅平移 0.5 px 后输入张量的 rms 变化 | 21.33 | **11.72（降 45%）** |
| 同上，最大单点变化 | 120 | **50** |
| 平移 1.0 px 的 rms | 38.35 | 23.11 |
| 同一张图里 7 个**完全相同**的字符之间的灰阶差异 | 20.91 | 16.63 |
| 小牌（足迹 0.64x0.79 < 1）与旧算法的差异 | — | **0 字节（逐字节等价）** |

第四行值得单独说：**旧采样把同一张图里 7 个一模一样的字，画成了 7 个不同的样子** ——
这就是"同一块牌相邻两轮结果在跳"的机理。新采样下这 7 个字的差异明显收窄。

⚠ 这是**机制级**验证（抖动确实小了、小牌行为不变），**不等于准确率一定涨**。
准确率要等上板实测，而且 18.3 的省份汉字问题**不会**被这一条全部解决。

### 19.5 回答"能不能不裁剪直接识别"

端侧现有模型**做不到**：它是"整块车牌铺满输入"训练的序列识别器（输入固定 94x24，输出 68x18），
把 640x480 整帧塞进去，车牌只占 ~10 px 宽，字必然糊成一片；而且没有定位，输出也无从对应到画面位置。
（`main.cpp:989-991` 的注释早就写着这一条，§13 也复现过："不裁剪时结果乱跳"。）

但这条路你其实**已经有一个版本**了：`PlateRecognition/PlateRecognition.ino` ——
拍整图 → JPEG → 百度 OCR，**云端 OCR 自己带车牌检测，所以不用裁剪**。
端侧要复刻它，就得再上一个小检测模型（两段式：检测 + 识别），工作量远大于现在这条路。

折中方案是"松裁剪"（多留一圈余量），但实测已经证明**框越高越容易认错**（18.3 的比例相关性），
所以方向应该是**更紧**，不是更松。这也指向下一件事：紧裁剪。

### 19.6 待办（按优先级）

1. **上板实测 P5.5**：看 `面积平均` 字段 + 同一位置连拍若干轮，`粤T666FP` 的出现比例是否上升；
2. **紧裁剪**：把框收到车牌本体（比例 2.4~2.9 → 3.1 左右），这是 18.3 里"框越高越认错"的直接解；
3. **省份汉字**：上面两条都做完还不稳，才是真的模型问题 —— 那时再回 14.6 的门禁评估重训；
4. 亮牌照阈值（`V>=100 && B-R>=15 && B-G>=5`）—— 一直在等密度门槛上线，现在可以上了。

## 二十、P5.6：裁剪到底准不准？—— 用现场日志把它量出来（2026-09-29）

> 用户问：你是靠"蓝色区域"这种启发式定位的吧？那裁剪得准不准？

### 20.1 先交底：这条链路里没有任何学习成分

`roi_locate()`（`main.cpp:609` 起）是一条**纯颜色启发式**流水线：

1. 逐像素判车牌色 —— `roi_is_plate_color()`：色相 蓝 [200,248]° / 绿 [70,170]°，且 S≥43、V≥46
   （复刻 `auto_crop_predict.py` 的 `cv2.inRange`，`main.cpp:375`）；
2. 累加到 **1/4 粗网格**（`ROI_GRID_STEP 4` → 160x120 格），一格内 ≥25% 像素是车牌色才算"蓝格"（`ROI_CELL_NEED`）；
3. 连通域 → 按 面积 / 宽高比 / 填充率 打分 → 选一个；
4. PCA 拟合旋转矩形（等价 `cv2.minAreaRect`）→ 取四角（左右各去 1% / 上下各去 3%，`ROI_TRIM_X/Y`）
   → 交给 `sample_quad_to_input()` 双线性摆正采样。

所以"裁剪准不准"**完全等于**"蓝色块找得准不准"。

### 20.2 量化结果（现场 105 轮里的 82 个摆正四边形）

| 指标 | 实测 | 说明 |
|---|---|---|
| 候选框贴到画面边缘 | **28 / 98 = 29%**（其中贴右 25） | 车牌被画面切掉 → 裁剪必然错（P5.4 已改成直接拒识）|
| 摆正四边形贴边 | 19 / 82 = 23% | 同上 |
| 非贴边四边形的长宽比 | **中位 2.81**（真车牌 3.14），范围 2.19~6.00 | 2.81 是**已去掉 1%/3% 边之后**的值，反推蓝色块本身是 **2.70** |
| 落在真车牌比例带 3.0~3.3 | **22 / 63 = 35%** | 即 **2/3 的框比例是偏的** |
| 尺寸中位 | 354 x 132 px | 同宽的真车牌高度应约 113 px → **上下共多出约 19 px** |
| 旋转矩形填充率 | 71~73% | 见 20.3-1，这个数字本身是个反证 |

### 20.3 为什么会偏（三种可能，修法完全不同）

1. **连通域把车牌和"看着像蓝"的邻居连成一块**。连通域没有任何形状约束，PCA 取 u/v 极值时用的又是
   **min/max**（`main.cpp:489-492`，不是分位数），所以角上多挂几格就能把框拉长。
   这条同时解释两件事：① 比例被拉低；② 填充率仍有 71~73% —— 如果上下真多吃了"非蓝背景"，
   填充率该掉到 55~60%，而 71~73% 恰好等于"蓝底挖掉白字"的期望值（并进来的也是蓝的，所以不掉）。
2. **4 px 格点 + "一格 ≥25% 就算蓝"**：边缘天生外扩，期望约 1.5 px/边，量级偏小，解释不了 19 px。
3. **PCA 只会拟合矩形**：斜着拍时车牌在画面里是**梯形**，矩形拟合只能折中。
   比例 2.81 换算成偏航角是 **27°**（3.14·cos27°≈2.80）。现场 25 轮贴右边缘说明那一段拍摄本来就偏，
   斜拍很合理。

### 20.4 这一轮只加了"让它自己回答"的东西

`roi_probe_profile()`（`main.cpp`）：沿选中的四边形**自己的高度方向**打 12 段，每段在宽度方向取 9 个点，
报告其中有多少个是车牌色。**纯诊断，不参与任何判断。**

- 顶/底两端明显偏低（比如 2/9、4/9） → **框太胖**，按这个比例收紧就能修；
- 从头到尾都 ~8-9/9 → **框是紧的**，那比例偏低就是斜拍的梯形问题，要改**真四角透视校正**
  （`sample_quad_to_input()` 本来就能接受任意四边形，缺的只是"从轮廓取四个真角点"而不是"PCA 矩形"）。

打印时机：详细模式（开机 / 按 BOOT）、以及结果可疑时（那次本来就会补打裁剪缩略图）。

### 20.5 结论与下一步

- 现在的裁剪**不够准，而且错法是系统性的**：2/3 的框比例偏离真车牌，另有 29% 直接贴边；
- **不要盲目"紧裁剪"**：如果原因是 20.3-3（斜拍梯形），收紧只会把省份字切掉。必须先看剖面 / 缩略图定性；
- 零成本替代验证：用手机在**同一位置、同一角度**拍一张车牌照片（原图即可，不用裁剪），
  量一下蓝色区域的比例就是答案（≈3.14 = 正对；≈2.8 = 斜拍 27°）；
- 若确认是 20.3-1（连通域并块），修法是"行/列剖面紧裁剪"：只保留覆盖率高的一段，切掉尾巴。

### 22.2 新发现（很可能是主因）：车牌被拍"白"了 —— 有量化对比

用像素统计比对"样张里的蓝底"和"现场抓到的蓝底"（同一判据）：

| 来源 | 蓝底均值 (B, G, R) | 说明 |
|---|---|---|
| 样张 `粤T666FP.jpg` | **167, 89, 14** | 深蓝，正常 |

## 二十五、P5.12：日志精简 + 把画面直接发到串口助手预览（2026-09-29）

### 25.1 用户这轮要什么

两件事：

1. **日志太乱**，一屏里全是掩码/候选表/缩略图，找不到有效信息；
2. **能不能把图片从串口发出来**，用他自己的「BY串口助手」实时预览 —— 比看文字直观。

背景澄清（用户本轮纠正）：素材是**电脑屏幕上显示的车牌**，实际显示尺寸和实体车牌差不多大，
不是手机小屏。所以“太小认不出”的锅不能全甩给拍摄距离。

### 25.2 日志精简：连续模式每帧只剩 1~2 行

之前连续模式每帧会打好几十行。真正的刷屏源是“结果不像车牌时补打一次诊断”
（掩码 60 行 + 覆盖率 12 行 + 1:1 缩略图 24 行 ≈ 8 KB）。实测那 8 KB 在 115200 上要 **0.9 s**
（掩码每行时间戳间隔 8 ms，正好是线速 11520 B/s），也就是说**串口本身就在拖慢识别**。

改法：

| 内容 | 之前 | 现在 |
|---|---|---|
| 整帧均值行 / 候选表 / “形状像车牌但填充不足” 等 | 每帧都打 | 只在 `verbose`（按 BOOT）打 |
| 掩码 + 缩略图 + 覆盖率剖面 | 结果不像车牌就自动打 | 只在 `verbose` 打（且还剩 12 次预算） |
| ROI 明细行、摆正行 | 每帧都打 | 只在 `verbose` 打 |
| 合成摘要行 | 无 | 每帧 1 行（带帧号 `#n`） |
| 定不到位 | 打一堆失败原因 | **1 行**：`#n 跳过推理: <原因> (定位 N ms)` |

合成摘要行长这样（定位到车牌时）：

```
#12 ROI 280x110 占屏9.4% 收边[6%,94%] | 定位 74 预处理 4 推理 397 ms | 平均3x4 归一x1.42 | B108 G96 R92
#12 >>> RESULT: 京Q06666
```

一帧两行，一行看“喂进去的料好不好”，一行看“认出来什么”。没定位到就一行 + 一张图。

### 25.3 串口图片：协议（与 BY 助手逐字节对齐）

参考文件 `BY串口助手/serial_img_tool.py`（已逐字节核对 `_serial_reader` 的状态机）：

```
"$IMG,<len>\r\n" + JPEG 二进制(恰好 len 字节) + CRC32(大端 4 字节) + "$END\r\n"
```

- `len` 是十进制字节数；CRC32 = zlib CRC-32，即 Python `binascii.crc32(img) & 0xFFFFFFFF`；
- 助手端把 CRC 当硬门槛：**不过就整帧丢弃**。所以从写帧头到写完帧尾之间**绝不能打任何 LOG**；
- 助手是**流式**状态机（WAIT_HEADER→READING_BIN→READING_CRC→WAIT_END），帧前后夹普通日志文字
  不会破坏切帧；这也意味着“日志精简”和“发图”是互相成就的关系；
- 助手侧要勾 **「图片预览」**，解析模式选 **「二进制帧」**（默认就是它）。

为什么绕这么大一圈（逐条都是硬约束）：

1. GC2145 驱动只能出 RGB565 / YUV422，**出不了 JPEG**（`components/esp32-camera/sensors/gc2145.c`）；
2. `esp_new_jpeg` 的编码器**不吃 RGB565**（`esp_jpeg_common.h` 明确写 `RGB565_* : Encoder un-supported`）
   → 必须自己转 RGB888；
3. 转换后的缓冲必须 **16 字节对齐**（S3 上编码器按 128bit 读）；
4. 640x480 RGB565 = 614 KB，在 115200 上要 53 秒 → 先 **2x2 平均降采样到 320x240**，再 JPEG(q70)。

实测每帧 JPEG **4.2~4.3 KB**，在 921600 上约 47 ms，整体帧率约 **2 帧/秒**。
顺带：预览图上会用**绿色框**画出这一帧定位到的 ROI（能摆正时画旋转后的四角，否则画外接框）；
**没定位到也照发**，正好让用户看见“相机到底看见了什么”。

### 25.4 坑 1：控制台波特率改不动（Kconfig 的 prompt 有条件）

```

    prompt "UART console baud rate" if ESP_CONSOLE_UART_CUSTOM   # <-- 这里
```

选了“默认 UART0”时这个符号**不可见**，sdkconfig 里写的值会被忽略、回落到默认 115200。
改法：改成 CUSTOM 模式并把它的附属项一起补齐（缺一项都可能被 kconfig 重新推导）：

```
# CONFIG_ESP_CONSOLE_UART_DEFAULT is not set
CONFIG_ESP_CONSOLE_UART_CUSTOM=y
CONFIG_ESP_CONSOLE_UART_CUSTOM_NUM_0=y
CONFIG_ESP_CONSOLE_UART_TX_GPIO=43      # S3 默认值, 显式写一遍
CONFIG_ESP_CONSOLE_UART_RX_GPIO=44
CONFIG_ESP_CONSOLE_UART_BAUDRATE=921600
```

`sdkconfig.defaults` 也同步补了这几行（否则删掉 sdkconfig 重建时又不生效）。

**验证方式（必须做）**：改完 build 完去翻 `build/config/sdkconfig.h`，
看到 `#define CONFIG_ESP_CONSOLE_UART_BAUDRATE 921600` 才算真的生效 —— 只看 sdkconfig 会骗人。

### 25.5 坑 2（关键）：stdout 会把二进制里的 0x0A 变成 0x0D 0x0A

第一版用 `fwrite(..., stdout) + fflush(stdout)` 发图，结果**助手一帧都收不下**。
自己抓包对账（COM9, 921600）：

```
declared len 4353  received body 4386        <- 多了 33 字节
0x0a count 29  0x0d count 47
crc bytes(in stream) = 9a5def49
crc32(received)      = 33158954              <- 对不上
把 body 里的 "\r\n" 全换成 "\n" 之后:
   len = 4353 (正好)  crc32 = 9a5def49 (正好对上!)
```

也就是说**字节内容没错，是控制台的换行转换把每个 0x0A 扩成了 0x0D 0x0A**（JPEG 里 0x0A 很常见，
4.3 KB 的图里约 30 个）。出处是 IDF 自己的 `esp_rom_output_putc`（`components/esp_rom/patches/esp_rom_sys.c`）：

```c
void esp_rom_output_putc(char c) {
    if (c == '\n') { esp_rom_output_tx_one_char('\r'); esp_rom_output_tx_one_char('\n'); }
    ...
}
```

**修法**：图片帧整个不走 `stdout`，改用 ROM 的“原样发一字节”底层函数 `esp_rom_output_tx_one_char()`
（`#include "esp_rom_uart.h"`），它在 ROM 里直接把字节塞进 UART FIFO，不做任何转换：

```c
static void img_tx_raw_write(const uint8_t *p, size_t n) {
    for (size_t i = 0; i < n; i++) esp_rom_output_tx_one_char(p[i]);
}
```

写帧之前先 `fflush(stdout)` 把 stdio 里积压的日志冲干净，之后就只剩原样字节。
（日志本身继续用 ESP_LOG，走 `\r\n` 无所谓 —— 助手对帧头/帧尾都做了 `strip("\r\n")`。）

> **教训**：往串口发二进制，别再图省事用 `printf/fwrite`。要么用原样字节接口，要么走 base64。

### 25.6 上板实测（2026-09-29，COM9 @921600）

自己按 `serial_img_tool.py` 的状态机写了个抓包脚本，8 秒抓了 66 KB：

```

sizes [4173, 4190, 4173, 4241, 4289, 4268, 4302, 4304, 4285, 4250, 4290, 4238, 4247, 4212, 4260]
```

## 二十六、P5.13：框切得太贴边 —— 把"最后一个字被挤掉"修掉（2026-09-29）

### 26.1 用户的现象

预览图里车牌清清楚楚、绿框也套得很准，但识别出来不对。典型输出：
`京Q06666` 被读成 `京Q0666`（少最后一个 6）、`京Q70666`、`京QA0666`。

### 26.2 先把"是不是我们这一端的锅"钉死

串口空出来后抓了 35 帧现场画面（320x240 预览），把车牌原样裁出来看：是一块干净、摆正的
`京Q·06666`（存图见可视化目录 `inputs/in00_warp.png`）。

再把这块裁图喂**训练工程里的浮点 ONNX**（不是板上的 int8）：

```
35 帧里只有 2 帧读对；30 帧都少最后一个 6 (京Q0666)
```

=> 不是量化、不是端侧代码、也不是"拍得不够清楚"，是**模型没看见最后那个 6**。

### 26.3 根因：我们的框是"蓝区紧贴边"，字符在 94 宽的张量里被拉宽了

- 端侧 ROI 取的就是蓝底车牌本身，还要再去 1%(横) / 3%(竖) 边 —— 字符正好顶到
  `94x24` 张量的最左/最右列；
- 训练素材（`data/official_val` 的 94x24 图）里字符不顶边；
- 结果：最后一个字被边缘挤掉，CTC 输出就少一位。

验证方式是"把框向外扩一圈再送模型"，同一批 35 帧：

| 外扩 | 正确 | 主要错法 |
|---|---|---|
| 0%（改之前） | 2/35 | `京Q0666` ×30 |
| 4% | 10/35 | `京Q0666` |
| **8%** | **28/35** | `京Q06666` |
| 12% | 0/35 | `皖RQ06666L`（画面里的东西也被框进来，多认字） |

拆开看：只扩横向 8% → 18/35；只扩纵向 → 基本没用；横竖都 8% → 28/35。所以**主因是横向尺度**。

### 26.4 改动（`ROI_CROP_PAD`）

采样时把 u/v 区间整体向外扩 8%（`quad_eval` 是双线性外插，等价于把四边形同心放大），
旋转摆正和轴对齐回退两条路都改；同时把每个输出像素覆盖的源面积按 (1+2*8%) 修正，
否则平均降采样会欠采样（走样）。越界由 `sample_rgb565_bilinear` 夹回画面内，安全。

### 26.5 新冒出来的小尾巴：多认一位

外扩之后字符全对了，但 21 帧里有 12 帧在**尾巴上多挂一个字母**（`京Q06666L` / `京Q06666U`）——
画面外沿的暗边被当成了一个字。用一条硬规则收掉：

```c
// 蓝牌永远是 7 位(省 + 字母 + 5 位); 绿牌是 8 位, 不动。
// 10 字节 = 1 个汉字(3) + 7 个 ASCII, 正好是"多了一位"的情形。
if (plate.size() == 10 && cm_b > cm_g) plate.pop_back();
```

（`cm_b > cm_g` 是"蓝底"的判据，裁剪块均值早就算好了；绿牌 G 占优，不会误伤。）

### 26.6 上板实测（2026-09-29，COM9 @921600，持牌正对）

- 改之前：连续 28 帧里只有 1 帧全对；
- 只加 8% 外扩：21 帧推出 21 帧，`京Q06666` 全对的核心 21/21，但 12 帧尾巴多一位；
- 再加语法修正：**21 帧里 20 帧完全正确（95%）**，剩 1 帧 `京Q6666L`（漏了 0）。

指标行（对照用）：`ROI 390x136 占屏17.6% 收边[0%,92%] | 定位106 预处理138 推理398 ms | 平均5x6 归一x1.20`。

### 26.7 还没做的 / 下一步

- **跨牌复核**：以上都是在 `京Q·06666` 这一块牌上量的，必须换 `粤T666FP` 再测一遍，
  确认 8% 不是对这一块牌过拟合；
- 数据层面的短板照旧：训练集 800 张里"4 个相同字符连着"的只有 1 张、验证集 0 张，
  `06666` 这类号牌模型天生不擅长 —— 想再往上走要靠补数据，不是靠调参；
- 摄像头不要贴边：蓝底车牌好认，但**屏幕的蓝白背景也会被判成"车牌色"**，
  它一旦连到画面边沿，帧会被当成"车牌被切掉"直接拒掉（表现为大面积"跳过推理"）。

### 26.8 跨牌复核（粤T666FP）：省份字稳定读错，根因是训练集只有"皖"

换 `粤T666FP` 再测（同一固件，21 帧）：

```
皖T666FP   x17     <- 后 6 位全对, 省份字错
皖YT666FP1 x2
皖YT666F   x1
```

后 6 位 20/20 全对，但省份字 **20/20 稳定读成"皖"**。这不是 8% 留白造成的：
用户更早那份日志（还没有留白改动的固件）#445/#446 就已经是 `皖T666FP`。

去数训练素材的省份分布，答案很直接：

```
data/official_train  800 张: 皖760 苏13 浙10 豫5 鲁4 沪3 粤2 京1 川1 闽1
data/official_val    200 张: 皖196 川1 湘1 苏1 豫1
data/test           1000 张: 皖956 苏14 浙10 豫6 鲁4 沪3 川2 粤2 京1 湘1 闽1
```

**这套"官方"素材 95% 是安徽牌，粤只有 2 张、京只有 1 张。** 模型实质上是个"皖牌识别器"：
见到没学过的省份简称就往 皖（或别的多数类）上靠。所以：

- `京Q06666` 能做到 20/21 已经是运气好（京在训练集里只有 1 张）；
- `粤T666FP` 的省份字**必错**，而且再怎么调裁剪/归一化都不会好 —— 模型没见过这个字。

结论：**省份字这一项只能靠补数据微调解决**，和裁剪、留白、归一化都无关。
（这也解释了用户早先的疑惑："百度 API 就很准" —— 百度见过全国的牌。）

可操作的补数据路径（`LPRNet_Pytorch` 里已有 train/export/quantize 全套脚本）：

1. 用这台设备自己采：BY 助手勾「自动保存到文件」就能把收到的图自动落盘（`saved/images/IMG_*.jpg`）；
2. 每个要支持的省份 + 每种场景（屏幕翻拍 / 实拍 / 顺光 / 逆光）各采几十张；
3. `train_LPRNet.py` 微调 -> `_diag_mcu.py` 重新导出 ONNX -> `quant_espdl_s3.py` 量化成 espdl
   （量化需要校准集，用采到的图最合适）-> 替换 `main/models/lprnet_s3.espdl` -> 重编固件。

在补数据之前，任何平台上的正确率都会卡在"省份字"这一步上。

## 二十七、P5.14：拍摄角度的容忍度实测 + 采图工具的顺序坑（2026-09-29）

### 一、角度容忍度（离线模拟，浮点 ONNX，`京Q06666` 35 帧）

做法：拿已裁好摆正的 35 张京牌裁剪图，人为加"透视变形 / 滚转 / 俯仰"再丢回整条流水线
（检测 -> 摆正 -> 94x24 -> 解码）。不加变形时基线 30/35。

| 变形 | 参数 | 正确 | 主要错法 |
|---|---|---|---|
| 左右"歪"（滚转，图是斜的） | 15° / 25° / 30° | 30 / 29 / 30 | — |
| 左右"斜看"（偏航，远端被压缩） | f=0.99（≈10°，1 m） | 30/35 | — |
| " | f=0.97（≈14°，1 m） | **17/35** | `京RQ06666` |
| " | f=0.94（≈20°） | **8/35** | `京RQ06666` |
| " | f=0.87（≈30°） | 0/35 | `京RQ066`（少字） |
| 上下"俯仰"（远端被压窄） | f=0.94（≈20°） | 29/35 | 基本没事 |
| " | f=0.90（≈25°） | 29/35 | 基本没事 |
| " | f=0.86（≈30°） | 4/35 | 前面多认一个字 |

`f` = "远端高度 / 近端高度"。同一角度下，**离得越近 f 越小**：44 cm 的车牌在 1 m 处偏 30°
约 f=0.80，在 3 m 处偏 30° 才 f=0.93。所以"能容忍多少度"取决于距离，本质是看远端被压缩了多少。

结论（对用户的话）：
- **歪着拍随便**（±30° 都行）—— 流水线里有主轴拟合，会把车牌摆正；
- **斜着拍要克制**：偏 15° 就开始掉，±20° 勉强，≥30° 基本废；
- **上下俯仰比左右偏航宽容**（到 25° 还稳）；
- 真机还有运动模糊/反光，实际比上表更紧一档。

为什么会这么脆：模型输入只有 94x24（每个字约 5x12 像素），横向压缩 3% 就相当于整张图上
挪了 1.5 个像素，CTC 直接多吐/少吐一个字符。想彻底解决"随意角度"，要么(1)补角度样本微调，
要么(2)把现在的"旋转矩形"升级成"真四角 + 透视校正"（现在是 PCA 主轴 + u/v 外接区间，
只能去滚转，去不了梯形）。

### 二、`tools/prep_collect.py` 的顺序坑（已修）

采图整理脚本第一版是"先擦绿框 -> 再找车牌"，离线复核只有 6/35。原因：inpaint 会在车牌边沿
留一圈发绿的渗色，蓝|绿掩码一取，最小外接矩形就从"车牌本体"涨到"绿框外沿"（长边 226 -> 234，
约 +5%），叠加 8% 留白变成 ~13% —— 又回到第 26 章那个"字被挤出张量"的坑。

修法：**先找车牌 -> 裁剪摆正 -> 再在裁剪图上擦绿框**（且绿牌跳过这步，否则底色被抹掉）；
找车牌时绿牌色先 `erode 3x3`，把那条 1~2 px 的绿框细线从掩码里去掉。

修完后同一批 35 张：**30/35**（错的 5 张全是省份字读成 苏/皖/沪，即第 26 章的老问题）。
拼图预览：`out_jing3/montage.png`（绿框干净、字符四周留白一致）。

### 三、P5.15：绿框改成 BOOT 开关（用户提议，已改）

用户的质疑是对的：绿框是我们自己画的，采数据时最干净的做法就是**别画**，而不是事后拿 inpaint 擦。
之前画的理由只有一条 —— 正常跑的时候用它肉眼确认"ROI 框套得准不准"（这个调试价值是真的，
掩码 ASCII 图和 `ROI 280x110` 这种数字行都不如绿框直观）。所以不做"永远不画"，改成**开关**：

| 动作 | 行为 |
|---|---|
| 短按 BOOT（<1 s） | 切换绿框开关，串口打一行 `绿框: 开/关`，并立刻拍一帧（这样马上能看到效果） |
| 长按 BOOT（>=2 s） | 详细模式识别一次（掩码 + 候选表 + 缩略图），不动开关 |
| 1~2 s 之间 | 空档：什么都不做，只打一行说明（防误触 —— 想短按却按久了 / 想长按却没按够，都不会误动作） |

实现要点（`main/main.cpp`）：

- GPIO 中断从 `GPIO_INTR_NEGEDGE` 改成 `GPIO_INTR_ANYEDGE`，ISR 里按下记 `boot_press_us`、
  松手记 `boot_release_us`，主循环消费锁存时算时长来区分短按/长按（`esp_timer_get_time`，IRAM 安全）；
- `static volatile bool g_draw_box = false;` 默认**关** —— 连续帧是要存成训练素材的图，默认就得干净，
  免得"想采数据但忘了关框"；
- `img_tx_send(..., (has_roi && g_draw_box) ? &box : nullptr)`。

连带的好处：`prep_collect.py` 里那套"擦绿框"从主路径降级成兜底（只对付开关打开时抓的老图），
绿色阈值那步的 3x3 腐蚀也变成纯粹的保险（真绿牌只缩 1 px）。干净帧上擦除是零开销。

固件产物：`build/plate_recognition.bin` = 1,908,256 B，`build/p515_merged.bin` = 1,973,792 B（8 MB 从 0x0 一次烧）。

## 二十八、P5.17：离线复核链修好了 —— 之前的"3/64"是工具错，不是端侧错（2026-09-29）

### 一、起点：用户交回 97 张实拍

`G:\All_Project\AI_Project\BY串口助手\dist\saved\images\`，按车牌号分文件夹：

| 文件夹 | 张数 | 真值标签 | 说明 |
| --- | --- | --- | --- |
| `京Q-06666` | 66 | `京Q06666` | 文件夹名里的 `-` 是 BY 助手加的，标签要显式给 |
| `粤T-666FP` | 31 | `粤T666FP` | 同上 |

时间戳 02:16~02:24，都早于 P5.16 的编译时间（02:34），所以这批是 **320x240 预览图，不是模型输入块**。
素材本身是"电脑屏幕显示的车牌照片再翻拍"，原图质量很好：车牌占画幅 25%~35%，端正清晰。

### 二、发现一：`tools/prep_collect.py` 的找车牌算法是坏的（已重写）

老版本直接用 `cv2.inRange(H 100~124, S>=43)` 取**最大轮廓**再 `minAreaRect`。实测在同一批 97 张上：

- 该掩码在车牌**内部只覆盖 5%~36% 的面积** —— 屏幕翻拍的蓝牌被冲淡，掩码碎成小块；
- 于是"最大的一块"只是车牌的某个局部，裁出来是**放大的一角**；

另外一个独立的坑：`minAreaRect` 对这批图返回的角度接近 **-90°**，而老代码用 `boxPoints` 的角点顺序去推
宽高（"左上-右上"的距离当宽），90° 附近这个顺序会翻，于是把车牌裁成**竖条**。

所以第二十七章那批"离线正确率 3/64""预览图分辨率不够"的结论**作废** —— 那是裁剪错了，不是端侧不行，
也不是预览图不够（预览图 94 宽的张量完全够用）。

新算法（`tools/prep_collect.py`，P5.17 重写）：

1. 蓝占优掩码 `B-R > 25 且 B > 90`（对"发白的蓝"也成立，不要求饱和度）；
2. 取最大**连通块**（不是最大轮廓），再闭运算把白字造成的洞补上；
3. `minAreaRect` 之后显式处理 90° 翻转（`w < h` 时换轴并 `+90°`），宽高不靠角点顺序推。

### 三、发现二：修好之后，同一批图的离线正确率

评测用 `tools/out/lprnet_s3.onnx`（与固件同权重的浮点 ONNX，int8 量化前的版本），
预处理与训练/`predict.py` 完全一致（resize 94x24 → `(x-127.5)/128` → CHW），CTC 贪婪解码
（**blank = 67，即 `len(CHARS)-1`**，不是 68 —— `CHARS[67]` 那个 `-` 和 blank 共用下标，这是训练集的历史遗留）。

**对照实验（证明评测链本身没错）**：`data/official_val` 200 张 = **87.5%**，与第 26 章记录的 float 基线一致。

| 裁剪几何 | 正确率 |
| --- | --- |
| 蓝区紧贴边（scale 1.00） | 61.9%（60/97） |
| 工具默认（横向 1.05 / 纵向 0.95） | **78.4%（76/97）** |

分牌照：`京Q06666` 50/66 = 75.8%，`粤T666FP` 26/31 = 83.9%。
错误几乎全是**长度错位**，不是不认识字：`京Q0666`（少最后一位）7 例、`沪京Q06666`（多一位）4 例、
`粤T666FFP`（多一个 F）5 例；省份字现在基本都对。

### 四、发现三：模型对"裁剪几何"极其敏感（这是最重要的一条）

同一批 97 张图，只改裁剪框的缩放，其他一律不动：

| 横向 sx \ 纵向 sy | 0.85 | 0.90 | 0.95 | 1.00 | 1.05 |
| --- | --- | --- | --- | --- | --- |
| 0.90 | 48.5% | 45.4% | 43.3% | 42.3% | 38.1% |
| 0.95 | 32.0% | 27.8% | 30.9% | 26.8% | 23.7% |
| **1.00** | 67.0% | 63.9% | 63.9% | 61.9% | 61.9% |
| **1.05** | 77.3% | 73.2% | **78.4%** | 76.3% | 74.2% |
| 1.10 | 35.1% | 28.9% | 26.8% | 22.7% | 22.7% |
| 1.15 | 7.2% | 8.2% | 8.2% | 7.2% | 6.2% |

横向差 5%（1.05 → 1.10）就能从 78% 掉到 35%。这说明当前模型把"车牌在 94 宽张量里占多宽"背死了。
端侧的框是设备自己算的（`ROI_CROP_PAD = 0.08`，即采样范围外扩 16%），**和离线复现的框不可能逐像素一致** ——
所以"靠调框参数去凑"这条路天生很脆，也解释了为什么上板精度时好时坏。

（注意：sx 很大时部分图像的车牌本来就贴到画面边缘，外扩会越界被 `BORDER_REPLICATE` 拖影，
表格最右下角那几个数有这一层成分；但 1.00 → 1.05 → 1.10 这个"先升后崩"的形状是真实的。）

### 五、发现四：微调试了一版，暂时不要用（`tools/finetune_s3.py`）

思路：实拍裁剪图 + CCPD 训练集 replay，强几何增强（横纵 0.88~1.14、平移 ±10%、旋转 ±3°）+ 光度抖动，
小学习率从 `weights/Final_LPRNet_model.pth` 接着训 25 轮。

结果（留出 20 张实拍 / CCPD 验证 200 张）：

- 微调前基线：实拍留出 **85.0%** / CCPD 验证 **87.5%**；
- 25 轮后：CCPD 验证掉到 **77%~81%**，实拍留出在 75%~95% 之间来回跳，**没有净收益**。

结论：**不换模型**。两个原因：(a) 2 块牌 97 张样本太少，靠增强硬凑容易把通用能力带偏；
(b) 真正该拿来做训练素材的是"模型真正吃到的那块图"（P5.16 的模式 2 输出），而不是我们去猜的框。
脚本留着，等有模式 2 的素材再用。
